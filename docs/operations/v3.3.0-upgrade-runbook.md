# v3.3.0 アップグレード運用手順 (O1〜O4)

v3.3.0 は**全 CMIS + RAG 再索引が必須**で、10 万文書規模では **10 時間級**になる
([`v3.3-release-blockers.md`](../design/v3.3-release-blockers.md) の RX1)。
その長さゆえに出てくる運用上の穴 4 件に答える。

**本書の記述はすべてコードを読んで確かめたもの**で、行番号を添えてある。
未検証のものは「未検証」と明記した。断定していない箇所を断定に読み替えないこと。

関連: [`CLAUDE.md`](../../CLAUDE.md) の「v3.3.0 へのアップグレード」、
[`.claude/skills/acl-epoch/SKILL.md`](../../.claude/skills/acl-epoch/SKILL.md)。

## O1. 全再索引に再開手段は無い — 分割するなら folder 単位で

### 事実

- **全再索引は必ず索引を消してから始まる。** `startFullReindex` は
  `clearIndex(repositoryId)` を呼ぶ (`SolrIndexMaintenanceServiceImpl.java:210`)。
  `clearIndex` の呼び出しは**プロダクション経路ではここ 1 箇所だけ**。
- **進捗は JVM 内にしか無い。** `reindexStatuses` は `ConcurrentHashMap`
  (`SolrIndexMaintenanceServiceImpl.java:101`)。プロセスが落ちれば消える。
- したがって **10 時間の途中で JVM が落ちると、やり直しになる**。しかも次の実行が
  また索引を消すので、**部分的に出来ていた索引も失われる**。
- 実行中はずっと検索結果が不完全である。

**`CLAUDE.md` に書いてあった「時間帯で分割実行」は、全再索引では成立しない。**
本書に合わせて記述を直した。

### 分割するなら (folder 単位)

`startFolderReindex` は **`clearIndex` を呼ばない** (上記のとおり呼び出しは 1 箇所)。
よって subtree 単位に分けて、任意の時間帯に分散できる。ただし 2 つ落とし穴がある。

1. **`reindexFolderRecursive` は渡されたフォルダ自身を索引しない。**
   引数のフォルダの**子**から始める (`SolrIndexMaintenanceServiceImpl.java:431`)。
   全再索引はルートを別途 1 件だけ索引して補っている (同 :218)。
   分割するときは同じ補いを自分で入れること。
2. **RAG の扱いが違う。** 全再索引は `skipRAGIndexing=true` で走らせ、最後に
   `triggerFullRAGReindex()` をまとめて呼ぶ (同 :254)。folder 再索引は
   `skipRAGIndexing=false` なので**文書ごとに RAG を張り直す** (同 :318)。
   分割経路では RAG の一括再索引は不要だが、1 文書あたりは重くなる。

**1 リポジトリにつき同時に 1 本しか走らない** (`status == "running"` なら拒否、同 :272)。
順番に流すこと。

```bash
# 0) 一度だけ明示的に消す (以降のステップは消さない)
curl -u admin:admin -X POST -H "X-Requested-With: XMLHttpRequest" \
  "http://HOST:8080/core/api/v1/cmis/repositories/REPO/search-engine/clear"
```

```bash
# 1) ルート直下 (ルートの子。トップレベルのフォルダ自身と、直下の文書を拾う)
curl -u admin:admin -X POST -H "X-Requested-With: XMLHttpRequest" \
  "http://HOST:8080/core/api/v1/cmis/repositories/REPO/search-engine/reindex/folder/ROOT_ID?recursive=false"
```

```bash
# 2) ルート文書そのもの (誰の子でもないので 1) では拾えない)
curl -u admin:admin -X POST -H "X-Requested-With: XMLHttpRequest" \
  "http://HOST:8080/core/api/v1/cmis/repositories/REPO/search-engine/reindex/document/ROOT_ID"
```

```bash
# 3) トップレベルのフォルダごとに、都合のよい時間帯で 1 つずつ
curl -u admin:admin -X POST -H "X-Requested-With: XMLHttpRequest" \
  "http://HOST:8080/core/api/v1/cmis/repositories/REPO/search-engine/reindex/folder/TOP_FOLDER_ID?recursive=true"
```

`recursive` の既定は `true` (`SearchEngineResource.java:478`)。

**上のコマンドは実際に叩いて確認した** (2026-08-14、canopy)。
1) は HTTP 202 → `completed` で `indexed 3/3`、2) は HTTP 200。

**ただし分割経路そのものは本番規模で未実測。** 全再索引と同じ結果になることは
コードから読めるが、所要時間の合計や、途中で更新が入った場合の挙動は測っていない。

### 分割した場合の後始末

- 分割中に**削除された文書**の索引エントリは残る。
  `POST .../search-engine/purge-orphans` で掃除する
  (CouchDB に 404 で存在しないものだけを消す。読めなければ 409 で全体を拒否)。
- **初期 epoch stamp は最後**。順序は再索引 → stamp で、逆順は
  `remainingUnfenced` が増え続ける形で現れる。

## O2. multi-replica ではどのレプリカで打つか

### 事実

再索引と epoch migration の進捗は**どちらも JVM ローカル**である。

- `reindexStatuses` (`SolrIndexMaintenanceServiceImpl.java:101`)
- `runs` (`AclEpochMigrationService.java:92`)

### 手順

**再索引・初期 stamp は 1 台に固定し、ロードバランサを経由せずそのレプリカを直接叩く。**
`/search-engine/status` も**同じレプリカ**に問い合わせること。別のレプリカに聞くと
「このプロセスは走らせていない」という答えになり、進捗が分からない。

**ただし `verdict` は例外で、レプリカを跨いでも正しい。** 実行記録が無い場合
(`p == null`) は Solr の索引そのものを読むように書かれている
(`AclEpochMigrationService.java:283-292`)。再起動やレプリカ跨ぎで
「終わった移行が未完了に見える」ことを避けるための設計。

- 進捗を見る → **打ったレプリカに聞く**
- 完了を判定する → **どのレプリカでもよい** (`verdict` を読む)

## O3. `verdict: COMPLETE` は「索引に全文書が在る」ではない

### 事実

`verdict` が答えているのは「**索引に在る**文書が全部 epoch を持っているか」であって、
「全文書が索引に在るか」ではない (`AclEpochMigrationService.java:279-305`)。

**完全に空の索引は捕まえられる。** `indexedCmisObjects == 0` なら `EMPTY_INDEX` を返し、
しかも「残り 0 件」の判定より**先に**評価している (同 :297-299)。
「stamp してから再索引した」という順序間違いはここで露見する。

**部分的に出来ている索引は捕まえられない。** 5,000 文書中 10 文書しか索引されておらず、
その 10 件に epoch が付いていれば `COMPLETE` になる。

### 手順

`verdict` を単独で完了判定に使わないこと。**必ず件数と突き合わせる。**

```bash
# 索引された件数 (再索引を打ったレプリカで)
curl -s -u admin:admin -H "X-Requested-With: XMLHttpRequest" \
  "http://HOST:8080/core/api/v1/cmis/repositories/REPO/search-engine/status"
```

```bash
# 索引側の CMIS オブジェクト数 (RAG 文書を除く)
curl -s "http://SOLR:8983/solr/nemaki/select?q=repository_id:REPO+-doc_type:\[*+TO+*\]&rows=0"
```

`indexedCount` / Solr の件数 / CouchDB の content 件数の 3 つが揃って初めて完了である。
`/search-engine/health` の結果も併せて見ること。

## O4. ロールバック

### 事実 (確認したもの)

| 変更 | 旧バージョンに戻したときどうなるか |
|---|---|
| **Solr schema** | フィールドが **3 つ増えるだけで、削除は 0** (`effective_acl_epoch` / `content_generation` / `content_incarnation`。master と HEAD のフィールド名集合を比較)。旧コードは知らないフィールドを無視するので**障害にならない** |
| **CouchDB `_design/_repo`** | `Patch_JoinedGroupsSingleEmit` が `joinedDirectGroupsByGroupId` の map を 20 emit → 1 emit にする。**consumer は `startkey/endkey = [id, 0]` しか読まない**ので、旧コードが新しい view を読んでも同じ 1 行が返る (`Patch_JoinedGroupsSingleEmit.java:25-33`)。**障害にならない** |
| **epoch stamp (Solr の追加フィールド)** | 旧コードは読まない。**障害にならない** |
| **パッチ履歴** | 適用済みとして記録されるので、旧バージョンで再適用されることはない |
| **再索引そのもの** | 戻す必要は無いが、**費やした 10 時間は戻らない** |

### 手順

**ダウングレードは実際に試していない。** 上の表はコードとスキーマの差分から読める範囲で、
「戻せるはず」であって「戻して確認した」ではない。したがって:

1. **アップグレード前にバックアップを取る。** CouchDB の全データベースと、
   Solr のデータボリューム (`SOLR_HOME=/var/solr/data` の名前付きボリューム) の両方。
   WAR だけ戻しても、design document の書き換えと索引の作り直しは戻らない。
2. 切り戻しは**バックアップからの復元**を第一手段とする。
3. WAR だけの差し替えで戻す場合は、上の表の 5 点が自分の環境で成り立つことを
   **ステージングで先に確認**すること。

**`docker compose restart` は使わない** — WAR はイメージビルド時にコピーされるので、
`restart` では古い WAR のまま動く。`--build --force-recreate` を使うこと。

## チェックリスト

- [ ] バックアップ (CouchDB 全 DB + Solr データボリューム)
- [ ] 全再索引の所要時間を見積もる (10 万文書で 10 時間級)。分割するなら O1 の手順
- [ ] multi-replica なら打つレプリカを 1 台に固定 (O2)
- [ ] 再索引 → **その後に** 初期 epoch stamp (順序厳守)
- [ ] `verdict` が `COMPLETE` / `COMPLETE_EXCEPT_ORPHANS` であること。
      **かつ**件数が揃っていること (O3)
- [ ] RAG 有効なら RAG 再索引も (`POST .../search-engine/rag/reindex`)
- [ ] 分割したなら `purge-orphans` で削除済みエントリを掃除
