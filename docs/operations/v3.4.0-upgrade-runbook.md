# v3.4.0 アップグレード運用手順

対象は **3.3.x から 3.4.0 へ**上げる場合。3.3.0 より前から上げるときは
[`v3.3.0-upgrade-runbook.md`](v3.3.0-upgrade-runbook.md) を**先に**通してください
(Solr 10 移行と ACL-in-Solr の初期 stamp はそちらの手順です)。

利用者向けの変更点は [`../../RELEASE_NOTES.md`](../../RELEASE_NOTES.md) の 3.4.0 節。
取込側の残る限界の一覧は [`../design/v3.4-release-readiness.md`](../design/v3.4-release-readiness.md)。

## O0. 全再索引は要りません

- Solr の `schema.xml` は 3.3.x から**差分がありません** (master と本リリースで確認)。
  3.3.0 のような「公開前に全再索引」は **3.4.0 では不要**です。
- **言えるのはそこまで**です。3.3.0 を経ていない環境は、そちらの再索引が先に要ります。

## O1. 起動 1 回目に、設定行の移行が走ります (**止められません**)

`Patch_ConnectorDefinitionDeterministicIds` が、コネクタ定義と取込プロファイルの
**生成 ID の行を確定 ID へ移します**。この patch は意図的に

- **常時実行** — 冪等で、失敗した行は次の起動で再試行します
- **履歴を残さない** — 「壊れた状態で 1 度走った」結果を恒久化しないため
- **CMIS ビューのゲートを通らない** — `_all_docs` と ID 指定の取得しか使わないため。
  ゲートは索引が壊れた起動でこそ拒否しますが、この移行が閉じる窓はまさにその起動で
  開きます

### 運用として見るもの

**起動ログに ERROR が出ていないか**を確認してください。

```
grep -i "connector-definition-deterministic-ids" <tomcat のログ>
```

- **食い違う双子** (生成 ID の行と確定 ID の行が**別の内容**を持つ) は、
  **毎回の起動で ERROR に出続け、自動では解決しません**。どちらを残すかを選ぶと
  もう一方の設定が黙って消えるためです。**運用者が中身を見て片方を消してください。**
- 消さない限り ERROR は出続けます。「出なくなった」が完了の合図です。

## O2. 起動時に Mango 索引が 1 本増えます

`Patch_IngestMangoIndexes` が `nemaki_conf` に **`idx_type_dlqId_id`
(`type`, `dlqId`, `_id`)** を登録します。DLQ 一覧のページ順を決めるためのものです。

- 登録が済むまでの間、`GET /dlq` の応答に **`"stableOrder": false`** と説明が付きます。
  一覧は従来どおりの並びで返りますが、**`offset` でページを繰ると行の重複・取りこぼしが
  起こりえます**。1 リクエストで読み切れる範囲 (`limit` は最大 500) は影響を受けません。
- `nemaki_conf` は小さい DB なので、索引の構築は通常すぐ終わります。

## O3. 応答コードが変わった入口があります (**監視の見直し**)

3.4.0 では「読めなかった」を **503**、「再試行では直らない」を **409 / 403** に
分けた入口が多数あります。**従来 400 だったものが 503 / 409 / 403 になります。**
一覧は RELEASE_NOTES の 3.4.0 節にあります。特に:

- 取込 (`POST /core/api/v1/repo/{repositoryId}/ingest`) は JSON / multipart とも、
  ストアが答えなかった場合に **503**
- **取込入口の 503 は、失敗の理由を応答に入れません** (委譲の認可を確かめる前に返るため)。
  **理由はサーバログに出ます** — 障害調査ではログ側を見てください
- webhook 受信は、セレクタ障害中は 401 / 404 を **503** に揃えます

「4xx はクライアント起因」と決め打ちした監視・アラートがある場合は、
**503 を再試行対象、409 / 403 を運用者の対応対象**として見直してください。

## O4. 上げたあとに知っておくこと (既知の限界)

いずれも RELEASE_NOTES の 3.4.0 節に記載があります。

| 事象 | 運用上の意味 |
|---|---|
| DLQ の再実行が 409 になることがある (bytes が届いていても) | コネクタから取り直してください。安全側ですが過剰な拒否です |
| purge は 1 回で先頭 1,000 行しか走査しない | 応答は続きがあることを言いません。繰り返し実行してください |
| 取込後のリンクの認可は**フェッチ開始時**のプロファイル行に対して行う | 取込中に委譲を取り消しても、そのフェッチのリンクには即座には効きません |
| 読みの失敗が「無い」という断定に使われない一覧は、今も空に見えうる | 一覧が 0 件のとき、それが「本当に 0 件」とは限りません |

## O5. 証拠まわりで運用の判断が要るもの

3.4.0 は証拠 (evidence) 側に**運用者が決めないと決まらない**ものを入れました。
既定はどれも**弱い側ではなく、黙らない側**に置いてあります。

### O5-1. 真正性レポートの読み方（`ABSENT` と `UNAVAILABLE` は別の事実）

レポートは **8 節**（`identity` / `content` / `custody` / `ledger` / `duplications` /
`versions` / `access` / `environment`）を**必ず全部出します**。構成の有無に関わらず
省略されません。**節が無いこと自体が起こらない**ので、「出ていない＝該当なし」と
読む余地がありません。

各節は自分の状態を答えます。**この 2 つは別の事実で、運用者の行動も違います。**

| 値 | 意味 | 運用者がすること |
|---|---|---|
| `ABSENT` | **読めたが、該当が見つからなかった** | **節による。** `custody` の空は「記録が無い」と「記録に失敗した／retention で purge された」を**区別できない**（レポート自身の限界文がそう言っています）。取込を通したはずの記録で `custody: ABSENT` なら**調査**してください |
| `UNAVAILABLE` | **読めなかった** | **`access` 以外は調査**してください（接続・認証・保存先）。**`access` は設計上どの配備でも常に `UNAVAILABLE`** — 監査ログはアプリケーションログに出て API から読み戻せません。これは故障ではなく、このレポートの限界です |

**`access: UNAVAILABLE` を毎回調べないでください。** 解消できない調査を繰り返すと
「`UNAVAILABLE` は無視してよい」と学習し、**本物の `ledger: UNAVAILABLE`**（台帳に届かない）
を見逃します。片方に寄せると、運用者は存在しない接続不良を調べるか、本当の障害を見逃します。

> **3.4.0 の途中で入れた「11 段の一覧」は取り下げました。** `PACKAGE` / `RFC3161` /
> `OTS` などの 11 行は、**どの収集器も作らない名前**だったため、構成に関係なく
> **常に `ABSENT`** と出ていました（RFC 3161 が動いていても `RFC3161: ABSENT`）。
> **段のはしごは package verifier のもの**で、そこでは各段が実際に行う検査に対応します。
> 1 件ごとのこのレポートには `CHECKPOINT_CHAIN` や `OTS` のデータが元からありません。
> **上げたあとにこの 11 行は出ません。** 正典 §6 の R64。

### O5-2. 失効材料の収集は**既定 off**。有効にすると外へ出ます

TSA 署名者の失効材料（CRL）を**発行時に**集めるかどうかは、設定キー
**`anchor.rfc3161.revocation.collect-at-issuance`**（既定 **`false`**）で決めます。
3.4.0 の途中まで、この setter には呼び出し側が無く「有効にできない」状態でした。
**先に取得経路を送信時固定の外向き経路（`AdapterHttpClient.sendPinned` — 一回送信、リトライ無し）に
載せ替え、その順序を錠で固定してから**、キーを配線しています（正典 §6 の R65。ガードが先、つまみが後）。

| 値 | 意味 | 運用者がすること |
|---|---|---|
| `NOT_ATTEMPTED` | **何も訊いていない**（既定。キーが `false`） | **なし。** 独立 verifier は P3 を `INDETERMINATE` と答えます |
| `UNAVAILABLE` | 訊いて**答えが来なかった** — 届かない・非 200（503 も。再試行しません）・空・**8 MiB 超**（`CRL_TOO_LARGE`）・**本文が 20 秒で来ない**（`CRL_READ_TIMEOUT`）・ガードが拒否 | **運用者が直す問題**です。`detail` に理由が入ります |
| `CAPTURED` | 取れた。取得時刻と digest が receipt に入る | — |

**on にする前に知っておくこと。**

- anchoring のたびに、**TSA 証明書が名指す CRL distribution point** へ HTTP を出します。相手は
  運用者ではなく TSA が決める URL です。そのため取得は**送信時に再解決して検証済みアドレスに固定**する
  経路（他の外向きと同じ `SsrfGuard` の分類）を通り、**HTTP はネットワーク層で固定されます**。
- **前提: JVM に `-Djdk.httpclient.allowRestrictedHeaders=host`。** HTTP の固定は URI を検証済み IP に
  書き換えて元のホスト名を `Host` に載せるため、JDK にこの flag が要ります。**Docker 配備は設定済み**
  （`docker/core/Dockerfile` の `JAVA_OPTS` と各 compose の `CATALINA_OPTS`）。素の Tomcat に WAR を
  置いた配備では、この flag 無しに on にすると `http://` の distribution point は**毎回 `UNAVAILABLE`**
  （`detail` は `IllegalArgumentException: restricted header name: "Host"`）。flag は JVM 起動時に
  要ります — 起動後に足しても、最初の `HttpClient` が作られた時点で JDK 側の一覧は固定されています。
- ガードに運用者向けのスイッチはありません。テスト用の JVM プロパティ `nemaki.ingest.allowLocalhost=true` は
  **loopback だけ**を通します（127.0.0.1 / ::1。他の宛先の検証と固定はそのまま。2026-09-22 まではガード
  全体を外していました）。本番で立てないでください — 立っていれば最初の loopback 宛て送信時に WARN が出ます。
- **HTTPS は TLS 境界まで**です。TCP-connect の窓（内部ホストへの接続試行）は**閉じていません** —
  これは他の外向き経路と同じ既知の残余で、この版で閉じたとは言いません。
- **上限 8 MiB。** 超えた CRL は `UNAVAILABLE`（`CRL_TOO_LARGE`）で、切り詰めた材料を `CAPTURED` にしません。
- **本文の上限 20 秒。** 要求の timeout はヘッダ到着までしか覆いません。ヘッダの後、本文が 20 秒で
  届き切らなければ `UNAVAILABLE`（`CRL_READ_TIMEOUT`）です — distribution point が 1 byte 送って止まっても、
  anchoring を待つ管理 API の呼び出しは戻ります。
- **503 / 429 は再試行しません。** コネクタ用の経路は `Retry-After`（最大 120 秒）を最大 3 回待ちますが、
  この取得は管理 API の要求 thread 上で走るので、「今は無理」は即 `UNAVAILABLE` です。
- **on にしても P3（`TRUSTED_RFC3161_V1`）は `VERIFIED` に届きません。** この版の verifier は集めた材料を
  **評価しない**（`REVOCATION_NOT_PARSED`）。集めるのは**後の版が評価できるように**です。
- OCSP は集めません。CRL の署名・有効期間の検証もしません（収集と評価は別）。

### O5-3. 受け取る側は NemakiWare 無しで検証できます

E-ARK package は `evidence-verifier-cli` で検証できます。**exit code が interface** で、
**`0` は `VERIFIED` だけ**です。`3` (`INDETERMINATE`) は成功ではありません。

**trust profile は package の外から渡します** (`--trust-profile`)。package が自分の
trust anchor を名乗れるなら、署名を差し替えた package は差し替え先の発行者を名乗って通ります。
**渡さなければ PKIX 検査は `NOT_PRESENT`** で、成功に昇格しません。

手順とファイル形式は [独立 verifier のリリース手順](evidence-verifier-release.md)。

### O5-4. この版が**やらないこと** (成功扱いにしない)

| やらないこと | 運用上の意味 |
|---|---|
| 内容を失う側の 6 経路 (アーカイブ・cold 移送・物理削除・内容の削除) を台帳に記録すること | 記録されるのは**内容を持つ書き込み 9 経路**です。「全部の操作が台帳に在る」とは読まないでください |
| ERS の **renewal の実行** | 評価 (dry-run) だけです。hash-tree renewal は保管済みオブジェクトを全部読むので、いつ走らせるかは運用のコスト判断です |
| 提示された checkpoint が**最新である**ことの保証 | package からは分かりません。**外部で保持した checkpoint** と突き合わせて初めて rollback が検出できます (`--expected-checkpoint`) |
| 認定タイムスタンプ事業者かどうかの判定 | 暗号からは推論できません。契約と登録簿の事実です |

## O6. デプロイ手順そのもの

通常どおりです。**`docker compose restart` は使わないでください** (古い WAR のまま
動きます)。WAR を作り直して `docker/core/core.war` にコピーし、
`--build --force-recreate` で上げます。詳細は `.claude/skills/build-deploy/`。
