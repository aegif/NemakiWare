# P1-2 — Fixity service

作成 2026-08-24。ロードマップ §4 Phase 1 の 2 番目。前提は P1-1 (捕獲の来歴) が
通っていること — **fixity は「保存されたものが変わっていないか」しか言えず、
「最初に正しく取られたか」は P1-1 の担当**である。

---

## 0. 何を主張し、何を主張しないか

**主張する**: **記録された digest を持つ添付について**、いま保存されているバイト列を
読み直して SHA-256 を計算し、記録値と一致するかを言える。結果は journal に残り、
運用 API は**検証した範囲**を必ず添えて答える。

**主張しない**:

- **改竄の証明ではない。** 式は公開の SHA-256 で、`nemaki:contentHash` は
  CouchDB に直接届く者には書き換えられる。**digest と本体を同じ主体が書き換えれば
  一致は保たれる**。恒久解は外部アンカー (P1-3 / P2) であり、この作業ではない
- **「全部を検証した」とは言わない。** digest を持たない添付は検証できない。
  それは失敗ではなく**検証対象外**で、両者を同じ数に混ぜない (§2)
- **改竄の修復はしない。** 乖離は隔離して報せるだけで、復元は運用判断
- **content の意味的な同一性ではない。** バイト列の同一性だけ

> **P1-1(d) R3 の教訓をそのまま引く。** 記録された digest は**取込が fetch した
> バイト列**の digest であり (`DigestSubject.INPUT`)、「リポジトリが保持している
> バイト列」ではなかった。**fixity は初めてその主語を「保持されているバイト列」に
> できる作業**である。だから記録側にも `DigestSubject` の新しい値が要る
> (§4) — さもないと「読み戻して確かめた」と「取り込むときに計算した」が
> 同じ形で並ぶ。

## 1. 何を検証するのか — 対象の定義

| | |
|---|---|
| **単位** | 添付 (`AttachmentNode`) 1 つ。document ではない — 版ごとに別の本体を持つ |
| **記録値** | その document の `nemaki:externalIntegration/nemaki:contentHash`。無ければ**検証対象外** |
| **計算値** | いま保存されている本体を読み直して SHA-256 |
| **範囲** | ACTIVE 層と **cold 層 (S3)** の両方。ロードマップ §Phase3 原則 3 の「遮断した層こそ誰も見ていないのだから fixity が要る」 |

### 1.1 cold 層で S3 の ETag を使わない理由

S3 の ETag は **multipart アップロードでは MD5 ではない** (パートごとの MD5 を
連結して再ハッシュした値で、パートサイズに依存する)。したがって ETag 比較は
「同じ S3 実装・同じパートサイズで put し直したか」しか言えない。
**自前で SHA-256 を計算する。** S3 の `checksum-sha256` メタデータが在れば
それを**取得のたびに検証する追加の層**として使えるが、無い配備があるので
主たる根拠にはしない。

## 2. 三値ではなく四値 — 「検証していない」を数に混ぜない

再索引の `verdict` の教訓 (`COMPLETE` は「索引に全文書が在る」ではなく
「索引に在る文書が全部 stamp 済み」だった) をそのまま適用する。

| 結果 | 意味 |
|---|---|
| `MATCH` | 記録値と再計算値が一致した |
| `MISMATCH` | 一致しなかった。**「改竄」ではない** — §0 |
| `UNVERIFIABLE` | 検証を試みたが答えが出なかった (本体を読めなかった、cold から取り出せなかった) |
| `NOT_RECORDED` | 検証すべき記録値が無い。**失敗ではない** |

**`NOT_RECORDED` を `UNVERIFIABLE` に混ぜない。** 混ぜると、digest を持たない
古い文書が大量にある配備では「検証できないものが山ほどある」と読め、本物の
`UNVERIFIABLE` (読めなかった) が埋もれる。これは capture verify で
`ABSENT` を `UNVERIFIABLE` から分けたのと同じ判断であり、同じ理由 —
**恒久に出る値を運用者は読み飛ばすようになる**。

### 2.1 走査の verdict

1 件ごとの結果とは別に、**走査そのもの**の verdict を返す。

| 走査 verdict | 意味 |
|---|---|
| `NOT_RUN` | この JVM で走らせていない |
| `RUNNING` | 実行中 |
| `COMPLETE` | 対象範囲を最後まで見た |
| `PARTIAL` | 上限・時間切れ・中断で**途中まで**しか見ていない |
| `FAILED` | 走査自体が失敗した。個々の結果からは何も結論できない |

**`PARTIAL` を `COMPLETE` に丸めない。** 「MISMATCH 0 件」は
「壊れていない」ではなく「**見た範囲では**壊れていない」であり、
どれだけ見たかを言わない 0 は嘘に近い。

## 3. いつ走るのか

**leader-gated の定期ジョブ**、既存のスケジューラパターン
(`LineagePurgeScheduler` / `CaptureIntentSweeper`) に揃える。

- 既定は **off** (`fixity.enabled=false`)。全添付の再ハッシュは I/O が重く、
  既定で有効にするなら先に規模別の実測が要る (ロードマップ §2-3 と同じ理由)
- 有効時の既定周期は日次、1 回あたりの件数に上限
- **leader gate に依存しない正しさ**: 複数レプリカが同じ添付を検証しても、
  読むだけなので結果は同じ。gate は費用のため
- **手動起動の API** を用意する — 演習と、疑いが生じたときの即時確認のため

## 4. 記録 — `DigestSubject` に主語を足す

P1-1(d) R3 が `DigestSubject` を作った理由は「何の digest か」を言わせるため
だった。その時点で意図的に**存在しなかった** `STORED` を、この作業が初めて
作れるようになる。

```
DigestSubject {
  INPUT,                     // 取込が fetch したバイト列
  INPUT_MATCHED_RECORDED,    // 上記 + 記録値と一致した
  STORED_REVERIFIED          // ★ P1-2: 保存されているバイト列を読み直して計算した
}
```

**`STORED` ではなく `STORED_REVERIFIED`。** 「保存されている」だけだと、
取込時に「保存したはず」の意味で使われかねない。**読み直した**ことが
この値の全部である。

fixity の結果は journal イベントとして残す (`FIXITY_VERIFIED` process type)。
乖離した場合も**同じイベント型**で結果だけ違う — 別型にすると
「MISMATCH のイベントが無い」が「検証していない」と区別できなくなる。

## 5. 受入条件 (負のコントロールつき)

| # | 条件 | 負のコントロール |
|---|---|---|
| 1 | 記録値と一致する添付は `MATCH` | 比較を外すと落ちる |
| 2 | 本体を差し替えると `MISMATCH` | 再計算を記録値の再読み込みに変えると落ちる |
| 3 | digest を持たない添付は `NOT_RECORDED` であって `UNVERIFIABLE` ではない | 2 つを同じ値にすると落ちる |
| 4 | 本体が読めない添付は `UNVERIFIABLE` であって `MISMATCH` ではない | 読み失敗を不一致に潰すと落ちる |
| 5 | 上限で止めた走査は `PARTIAL` であって `COMPLETE` ではない | 丸めると落ちる |
| 6 | 走査 verdict は件数と**別に**返り、`MISMATCH 0` だけでは完了と読めない | verdict を落とすと落ちる |
| 7 | `STORED_REVERIFIED` は fixity 経路でしか作られない | 取込側から作れるようにすると落ちる |
| 8 | 既定 off — 設定しない配備の挙動は変わらない | 既定を on にすると落ちる |

---

## 6. やらないこと

- **改竄の証明** — 外部アンカー (P1-3 / P2)
- **修復・自動復元** — 隔離して報せるだけ
- **content の意味的同一性** — バイト列だけ
- **cold 層からの自動 restore** — `restoreArchiveGuarded` が拒否する設計は変えない。
  cold の検証は「取り出せたら検証する」であって「検証のために取り出す」ではない
  (取り出しは課金と時間を伴う運用判断)
- **既定 on 化** — 規模別の実測 (ロードマップ §2-3 と同じ前提) の後
