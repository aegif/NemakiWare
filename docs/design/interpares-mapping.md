## 0. この表の読み方 — 先に 4 つ

**(1) 「準拠」とは言えない。** 準拠を認定する**公式な制度は確認できなかった** (§4 の未確認
事項を参照 — 「制度は無い」と明示否認した文言は見つかっておらず、certify の用法と、IP2 が
監査枠組みを外部に委ねている事実からの推論である)。原典で certify が使われるのは
「preserver が記録のコピーを certify する」意味のみ。**本書では準拠・認証を標榜しない。**
言えるのは **「要求事項に対応付けた (mapped to)」「に依拠して設計した (informed by)」** まで。

**(2) A 系と B 系で「部分適合」の意味が違う。** 原典 p.3 に明記されている。

| | 充足様式 | 部分適合の意味 |
|---|---|---|
| **Benchmark (A.1〜A.8)** | **累積的 (cumulative)** | 満たした数と充足度が高いほど真正性の**推定が強まる**。部分適合に意味がある |
| **Baseline (B.1〜B.3)** | **全件必須 (all-or-nothing)** | 全部満たさなければ preserver はコピーの真正性を attest **できない**。**部分適合を「B に部分準拠」として示さない** — ただし「個々の統制に価値が無い」という意味ではなく、能力の充足状況は別枠で報告してよい |

→ **「B を 80% 満たす」は原文の枠組み上そもそも成立しない主張。** B 系の行に達成率を
書かないのはこのため。

**(3) 製品単体では満たせない。** ATF Report p.27-28 が、要求は**自動化手段と手作業の
組合せ**を前提にしていると明記している。よって各行を 3 者に分ける:

| 記号 | 誰 | 意味 |
|---|---|---|
| **C** | Creator (記録を作る組織) | 記録を作る側の手続。製品は場を提供するだけ |
| **N** | NemakiWare (この製品) | 製品が機構として提供できる部分 |
| **O** | 導入組織 (preserver として) | 規程・体制・監視など、導入組織の運用に残る部分 |

**評価者は常に preserver (O)**。実施主体と評価主体が分離しているのが原典の設計。

**(4) 条件付き要求がある。** A.6 / A.7 / A.8 は無条件ではない。条件が成立しない組織では
そもそも要求されない。**A.2〜A.5 と同列に置かない。**

**サブ要求の所在**: 細目 (a, b, ...) が存在するのは **A.1 (11 項目)・B.1 (3 項目)・
B.2 (4 項目) だけ**。A.2〜A.8 と B.3 は各 1 文の要求である。

### A.2 アクセス権限の定義と実施

| | |
|---|---|
| **責務** | **C** 権限方針を定める / **N** ACL 機構 + 監査証跡 / **O** 権限設計と**定期監視**。preserver は自らの保管下で確立・実装・定期監視する義務を負う |
| **条件** | 無条件 |
| **現状** | CMIS ACL、ACL-epoch fencing、レプリカ間キャッシュ無効化 (既定 5 秒ポーリング)、監査メトリクス |
| **主張** | **(a)** 権限は CMIS ACL として実施される。**(b)** `audit.enabled=true` の構成では、**監査対象として分類され、かつ `AuditLogger` に到達する** WRITE / DELETE / ACL 変更は、READ の記録レベル設定にかかわらず記録対象になる — 記録は構造化 JSON の監査ログ (`audit.log`) で、時刻・利用者・操作・対象・結果を持つ。**「すべての書込が常に残る」とは言わない**: `AuditLogger` に到達しない書込経路の棚卸しが未了であり、到達しても ⑴ 操作単位・利用者単位の除外設定が先に効き、⑵ **ロガーのレベル設定でも落ちる** — 成功イベントは INFO が要る。失敗イベントは `audit.log.failures.as.warn=true` のとき WARN、そうでなければ INFO。**つまり INFO は常に必要で、上記が true の構成では WARN も必要**、⑶ ログの構築・出力の失敗は **fail-open** である。**(c)** **CMIS の applyAcl・move・ACL reconcile の再駆動**は epoch fence を通る。**(d)** multi-replica の反映遅れは、**共有 CouchDB と両レプリカの poller が健全で publish が成功している間は**、およそ 2 ポーリング間隔 (既定 5 秒) 以内に収まる |
| **主張しないこと** | ・「**すべての** ACL 書込が epoch fence を通る」とは言わない — **import 経路 (`FilesystemImporter` / `ZipImporter`) は `updateInternal` で ACL を直接書き、AclService を通らない**<br>・「反映遅れに上限がある」とは無条件には言わない — **publish も poll も失敗を警告して次回へ持ち越す**ので、障害中は上限が無い<br>・**ACL-epoch の migration verdict (`COMPLETE` 等) は初期 stamp の完了判定**であって、個々の ACL 変更が収束したことの判定ではない<br>・単発の成功は上界の証明にならない<br>・監査ログについて「網羅している」とは言わない — **到達しない経路・除外設定・ロガーのレベル設定・出力失敗の 4 つの穴があり、下記④は 1 件が記録されたことしか示さない**。`audit.enabled=true` だけでは足りない |
| **手順で示せる範囲** | 下記の手順が示すのは **applyAcl 1 件と監査ログ 1 行**まで。(b) の分類・到達範囲、(c) の全経路、(d) の上界は**手順では示せない** — これらは**コードを読んで確認した設計上の期待**であって、実証ではない。経路別のテストと位相を制御した反復試験が要る (未実施) |
| **検証手順** | ① レプリカ A で CMIS の applyAcl を行う。② **ポーリング間隔の 2 倍以上** (既定なら 10 秒以上) 待つ — A が次の poll で publish する直前に B が poll 済みだと、B の検知は更に次の poll になるため。③ レプリカ B で同じオブジェクトを CMIS で読み、権限が反映されていることを見る。④ `audit.log` に当該 ACL 変更の行が在ることを見る。⑤ 反証 1: ②の待ちを入れずに③を行うと旧権限が返りうる。⑥ 反証 2: import 経由で ACL を設定すると、①と違って epoch fence を通らない |
| **ギャップ** | (a) `audit.enabled` の既定は構成次第で、**除外設定・ロガーのレベル設定でも落ち、出力失敗は fail-open** — いずれも真正性に影響するので、導入組織は設定 (`audit.enabled` / 除外 / `audit.log.failures.as.warn` / ロガーレベル) を固定して監査対象にし、出力失敗を監視すること。(b) 監査は**ログファイルであって検索 API ではない** (`/core/rest/all/audit/metrics` はカウンタ)。(c) **原典 A.2 が求める「閲覧を除く全相互作用」を満たしているかの棚卸しと実証がまだ無い** — READ 系は `audit.read.level` で粒度が変わる。(d) 上記の epoch fence を通らない ACL 書込経路の整理 |
| **計画** | 棚卸しの結果を待って計画行を決める。3.4 の計画行は**未確定** |

### A.3 喪失・破損からの保護手続き

| | |
|---|---|
| **責務** | **C** 保護要件を定める / **N** 永続化・削除アーカイブ・復旧手順 / **O** バックアップ運用と**復旧演習** |
| **条件** | 無条件 |
| **現状** | CouchDB 永続化、削除アーカイブ (`/core/rest/repo/{repositoryId}/archive`)、バックアップ**作成**手順の文書 |
| **主張** | **`archive.create.enabled=true` の構成では**、削除は物理消去ではなくアーカイブに移り、復元できる。既定は true だが**設定で切れる** |
| **主張しないこと** | 「バックアップと復旧の手順が文書化されている」とは言わない。**文書にあるのはバックアップの作成 (EBS snapshot / CouchDB replication) までで、復元して整合性を確かめる手順は無い。** これはギャップである |
| **検証手順** | ① `archive.create.enabled` の値を確認する (既定 `true`)。② 対象オブジェクトの content を取得して SHA-256 を控える。③ 削除する。④ `GET /core/rest/repo/{repositoryId}/archive/index` に現れることを見る。⑤ `PUT /core/rest/repo/{repositoryId}/archive/restore/{id}` で復元する — **`{id}` は元のオブジェクト ID ではなく、④の index が返す `archives[].id`** (**CSRF 必須** — `-H "X-Requested-With: XMLHttpRequest"`)。⑥ 復元後の content の SHA-256 が②と一致することを見る。⑦ 反証: `archive.create.enabled=false` にすると④に現れない — **この設定は真正性に影響する**ので、導入組織は値を固定して監査対象にすること |
| **ギャップ** | (a) **fixity 再検証が無い。** 保存済みバイトが読めるか・変わっていないかを定期的に確かめる機構が存在しない。「壊れていない」と言う根拠が現状は**書いた時点の成功だけ**である。(b) **復元演習の手順が無い** — バックアップから戻して整合を確かめる公開手順を書く必要がある (上記⑤⑥は単票の復元であって、システム全体の復旧演習ではない) |
| **計画** | **P1-2 (fixity)**。「読めない」と「不一致」を区別すること、初回 baseline、周期、隔離、リストア後の全検証まで設計対象 |

## 2. Baseline Requirements (B) — 全件必須

**B 系は attest の可否については「全部満たすか、できないか」である。** 3 行のうち 1 つでも
欠ければ、preserver はコピーの真正性を attest できない。**ただし「部分的な実装に価値が無い」
という意味ではない** — 原典が言うのは attest の条件であって、統制の評価ではない。
能力の充足状況を報告するのは構わないが、**「B に部分準拠」という示し方はしない**。

**主語に注意**: preserver は**導入組織 (O)** であって製品ではない。よって本書が言えるのは
**「NemakiWare を保存機構として用いる導入組織は、現状の製品機能だけを根拠に B 系の
attest を行えない」**まで。**「B.1〜B.3 が未充足である」とは断定しない** — 原典は自動化と
手作業の組合せを前提にしており、組織が外部機構や手続で満たしている可能性を、
製品コードの確認だけでは否定できない。以下の各行が書くのは**製品側の現在地**である。
製品側からこの制約を外すには 3.4 の Phase 3 完了が前提になる。

> **B 系は「保存者側の最低条件」。** ただし **preserver は法人格 (juridical person) であって
> 受け側のソフトウェアではない** — RODA や Archivematica に取り込んだだけでは責務は移らない。
> **同一組織が運用する別システムへ入れても preserver は変わらない。** 責務が移るのは
> **custody が組織として実際に移った場合**に限る (移管先組織が受領を引き受けたとき)。
> NemakiWare が軽量 Archive を務める構成では、導入組織が自ら B 系を負い続ける。

### B.1 移転・維持・複製の管理 <sub>(細目 3 項目)</sub>

| | |
|---|---|
| **責務** | **N** 機構 / **O** 手続として確立し実施していることの立証 |
| **現状** | lineage journal + 外部カタログ (Purview / Atlas) 照合 |
| **主張** | **実効モードが `journaled` の構成で、対象経路の操作は発行を試み、terminal に達したイベントは保存期間内 journal に残る** (`direct` は publish のみで journal に書かない)。 対象経路は `LineageProcessType` のうち**実際に producer がある**もの — 外部取込 (chat / mail / note / business record / file share)、import / export、archive (local / cold)、cloud sync |
| **主張しないこと** | ・「操作が成功すればイベントが残る」とは言わない。**発行は fail-open** — 例えば export は ZIP 完成後に `emitSafely` を呼び、**発行に失敗しても業務操作は成功として返る**<br>・「取込・**移動**・**複製**が残る」とは言わない。**一般の CMIS move / copy に対応する process type は存在しない**<br>・「通常の CMIS 作成が残る」とも言わない (出ない)<br>・「enum に列挙された全経路」とも言わない — **`FILE_SHARE_SYNC_UPLOAD` は予約済みで producer が禁止**されている<br>・`lineage.mode` の**既定は `disabled`**。既定構成では何も残らない<br>・**既定 90 日で purge される** (`lineage.retention.days=90`)。「追記専用で残り続ける」ではない<br>・**terminal に達していない v1 の `PENDING` / `FAILED` 行は保存期間より早く落ちうる** — 再試行回数・経過時間・文書数・サイズの閾値で discard される |
| **検証手順** | ① **実効モードが `journaled` であることを確認する** (`direct` も「有効」だが journal に書かないので以下は成立しない)。② 対象経路の操作を 1 件行う (例: 外部取込)。③ `GET /core/api/v1/admin/lineage-journal/events` にそのイベントが在ることを見る。④ 反証 1: CMIS で普通に文書を作成し、③に**現れない**ことを見る。⑤ 反証 2: CMIS で move し、③に**現れない**ことを見る |
| **検証根拠** | 下記の手順が示すのは **1 経路の例**まで。**対象経路の一覧 (producer のある型) と全経路での挙動は、コードを読んで確認した**もの |
| **手順の限界** | `dead-letters` が空でも「取り逃しが無い」証明にはならない — そもそも発行されなかった / purge 済み / 対象外経路だった、を排除できない。`stats` も**今 journal に在る件数**の集計であって、在るべき件数との突合ではない。**「網羅している」ことの検証手順は現状書けない** |
| **ギャップ** | (a) **journal の改竄検知が無い** (discard + purge がある)。(b) 対象経路が limited で、B.1 が求める「移転・維持・複製の管理」を覆えていない。(c) 網羅性を機械検証する手段が無い。(d) **発行の fail-open** — 業務操作の成功と証拠の存在が結び付いていない。これを結び付けるのが **P1-1(a) の outbox** |
| **計画** | **P1-3** (配送 journal と evidence ledger の分離 + hash chain)、P3-1 (SIP) |
