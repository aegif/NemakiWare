2026-11-11 作成。3.4.1（2026-11-04）の後のパッチ。ブランチは `release/3.4.2`（`v3.4.1` = `656d6073b` から）。

条件 11 と件数の正は [`v3.4-release-readiness.md`](v3.4-release-readiness.md)（錠が読む場所）。

### Phase 1 — R260（`$expand=children`。測定 1〜2 時間 + バッチ半日）

**1-0 原因の測定（製品は変えない）— 2026-11-11 に測った。** `CmisEntityProcessor.expandChildren` は
`navigationService.getChildren` の 12 番目の引数（フォルダ自身を返す holder）に null を渡していた。配備中の WAR のクラスを
単独で呼ぶと、holder が null のとき `NavigationServiceImpl.getChildren` は 122 行目（`parentObjectData.setValue`）で
`NullPointerException` を投げ、holder を渡すとその行を通る。`expandChildren` の全体が `catch (Exception e) { }` なので、
例外は握り潰され、`Link` が足されず、serializer が `children: []` を書いていた。

nb33 で `$expand` の形を 38 通り測った（直す前、再起動をはさんで同じ答え）。壊れていたのは `children` だけではない。
- 正しく答える: `Folders(F)?$expand=parent`、`Documents(D)?$expand=parents`、`Relationships(R)?$expand=source,target`。
- 誤った答え: `children` は子が 3 件でも 101 件でも 0 件。`$expand=*` と `Documents(D)?$expand=parent` は、在る親を `null`。
  `children($top=1)`・`parent($levels=2)` などは、項の option を黙って落とす。
- 一覧（`Folders?$expand=children` など）は 200 のまま、展開の鍵ごと落とす（行ごとに関係する物を読んでから捨てていた）。

**1-1 直し。** §3 の D3 の形で 1 バッチ。次を錠にする。
- 子が在るフォルダに `children: []` を答えない。
- 答え切れない（頁を越える・読めない）ときに、黙って一部や空を答えない。
- 実体集合の一覧に `$expand` が付いたとき、鍵ごと落として 200 を答えない。

nb33 では、子 3 件のフォルダ・子 0 件のフォルダ・文書の `$expand=parents`・一覧の `$expand` を、直す前と後に 2 回ずつ測る。

RELEASE_NOTES の見出しの案（挙動の変更は「200 だったものが 400・404 になる」を必ず書く）:
1. OData の `contains()` が 400 になっていたのを直した（3.4.1 の既知の赤）。`contains`・`startswith`・`endswith` は、性質と文字列のリテラルの形だけを訳す。
2. OData は、訳せない URL を条件を外した答えで返さず 400 にする（型キャスト・ナビゲーション・function に付けた `$filter` や頁の option・Types / Users / Groups・`$apply`・引数の別名）。
3. OData の頁で切った答えは続きを示す（`nextLink`、`$top=0`、`$skiptoken`、件数）。
4. OData の書き込みと action は、名指した実体集合に属する実体にだけ届く。
5. CMIS の読みと削除は、内部の文書の id を無い id と同じ 404 で答える。
6. API v1 の `/documents`・`/folders`・`/items` は、自分の基底の型の実体だけを答える。
