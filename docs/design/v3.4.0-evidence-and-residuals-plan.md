## 0. 目的

3.4.0 で見送った残件を閉じ、既にある真正性の部品を
**第三者が NemakiWare を起動せずに検証できる、版付きの証拠プロファイル**へ組み直す。

完成とする連鎖:

```text
SIP の payload bytes
  → RecordContentStatementV1（正準 digest）
  → EvidenceLedgerEntry（entryHash）
  → Merkle inclusion proof
  → covering checkpoint →（chain）→ anchor target checkpoint
  → RFC 3161 / OpenTimestamps（trust profile）
  → RFC 4998 ERS と長期検証材料
```

「SIP の中の値どうしが一致する」だけでは完成にしない。
payload・記録状態・台帳 entry・checkpoint・外部 anchor が**同じ事実と同じ checkpoint** を
指していることを検査できて初めて、外部検証可能な証拠とする。

JIIMA **申請は入れない**。custody の **HTTP 押し出しは入れない**（都度 SIP/bag API と
状態機械は 3.4 にある。パイプラインは RODA / Archivematica 側）。
文書 1 件ごとに TSA を買うことは入れない（段 3 は台帳チェックポイント）。

## 4. 絶対条件

### 4.1 言ってよいこと

- SIP の payload bytes が、package に記録された digest と一致する
- record content statement の正準 digest が、台帳 entry の `payloadDigest` と一致する
- 当該 entry が、指定 checkpoint の Merkle root に含まれる
- checkpoint chain が、外部 anchor の対象 checkpoint まで連続している
- 指定した trust profile の必須検査が全て通った
- アンカー済み区間について、外部で保持した checkpoint を基準に事後変更を検出できる
- この成果物は、明示した版の verifier と profile で検証された
- RFC 3161 token がある、署名が検証できる、指定 trust anchor へ path が構築できる、
  という個別事実

### 4.2 言ってはいけないこと

電帳法対応 / JIIMA 認証済み / 認定タイムスタンプである（製品の自動判定） /
改ざん防止 / 管理者でも変更できない / 取込前の内容が真実 /
全て漏れなく取り込まれた / 提示 checkpoint が最新 /
未提示の記録が存在しない / ERS が個別 PDF の長期署名 /
CSIP validator や RODA を一度通ったことを E-ARK 全般や全 archive との相互運用と主張する

### 4.3 成功・失敗・不明を潰さない

各 check: `PASS` / `FAIL` / `NOT_PRESENT` / `NOT_CHECKED` / `UNSUPPORTED` / `RESOURCE_LIMIT`

全体 verdict は三つだけ:

| verdict | 意味 |
|---|---|
| `VERIFIED` | 選択した profile の**必須** check が全て PASS |
| `FAILED` | 入力された証拠の矛盾・改変・形式不正を確認した |
| `INDETERMINATE` | 必須材料が無い、読めない、未対応、信頼判断不能 |

`NOT_PRESENT` や `NOT_CHECKED` を成功にしない。
既存互換で boolean `verified` を残すなら `verdict == VERIFIED` のときだけ `true`。

## 5. 脅威モデル（Phase 0 で文書化）

想定: anchor 後に DB を変えられる管理者、SIP を改変する保管者、古い正当 checkpoint の提示、
TSA URL 差し替え、ZIP bomb / path traversal、package 内 root を信頼根拠にさせる、
payload と PREMIS digest の同時差し替え、別文書の proof の組み合わせ。

信頼するもの: 入手経路を確認した verifier とその digest、package **外**から与えた
trust profile、profile 1 の凍結済み正準化。

信頼しないもの: SIP 内の自己申告、package 内だけの root、repository の `latest`、
operator の accreditation 文字列、未アンカー区間、`nemaki:contentHash` 単独。

証明しないもの: capture の完全性、metadata の真実性、source の真正性、
endpoint の組織的独立、法令適合、package が最新であること
（package 外の expected checkpoint があれば rollback は検出する）。

成果物: `docs/security/evidence-profile-v1-threat-model.md`

## 6. 証拠 profile

RODA 6.3.0 で実測した互換を維持し、Nemaki 独自の証拠は `metadata/other` に置く。
存在しない anchor 種別の stub DER は入れない。

| Profile | 必須にするもの | 主張しないこと |
|---|---|---|
| P0 `PACKAGE_INTEGRITY_V1` | 安全な ZIP、METS 参照の完結、全 payload ↔ PREMIS fixity の一対一 | 台帳・外部 anchor |
| P1 `RECORD_LEDGER_V1` | P0 + statement 正準化、entryHash 再計算、inclusion proof、covering checkpoint | 外部の暗号的信頼 |
| P2 `ANCHORED_CHECKPOINT_V1` | P1 + covering→anchor target の chain、expected checkpoint があれば rollback 検出 | token の PKIX |
| P3 `TRUSTED_RFC3161_V1` | P2 + token parse / CMS / EKU / PKIX / policy / **発行時の**失効材料 | 認定業務であること |
| P4 `ANCHORED_OTS_V1` | P2 + `.ots`。blockchain 側を offline で確認できなければ `INDETERMINATE`。既定 no-network | — |
| P5 `LONG_TERM_ERS_V1` | P3 または P4 + RFC 4998。data object は `checkpoint.c14n` | 個別文書の長期署名 |

package 内 root だけでは trust anchor にしない。
`revocationDataCapturedAt=never` のままなら P3 は `VERIFIED` にしない。

## 7. Profile 1 の package contract（要約）

配置の正本は fixture で commons-ip2 の実 path に固定する。概念:

```text
metadata/other/nemaki-evidence/
  profile.json
  bundle-manifest.json
  record-content-statement.json + .c14n
  ledger-entry.json + .c14n
  inclusion-proof.json
  covering-checkpoint.json + .c14n
  checkpoint-chain.json
  anchor-target-checkpoint.json + .c14n
  anchors/  （無い種別は file を置かず manifest に NOT_PRESENT / NOT_CONFIGURED / UNAVAILABLE）
```

`RecordContentStatementV1` の必須: `repositoryId` / `objectId` /
**immutable な版キー**（`versionObjectId` または Phase 0 の inventory で決めた同等） /
content stream id / `contentDigest` / `contentLength` / `commitmentKind`
(`CAPTURED` / `UPDATED` / `OBSERVED`) / `captureIntentId`（外部取込のみ） /
`recordedAt`（台帳へ書いた時刻。source の作成時刻ではない）。

正準化は JSON の field 順に依存しない。`.c14n` を同梱する。

台帳: `SubjectKind.RECORD_CONTENT_STATE` を追加。`payloadDigest` は statement digest。
package に entryHash 再計算に必要な全 field を入れる（`subjectId` を省略しない）。

covering checkpoint と anchor target を分ける。同一なら chain 長さ 1。
欠落・重複・逆順・covering が target より後は `FAIL`。

## 8. 内容状態を台帳へ記録する（新しい残件 E1。R5 ではない）

**R5 を再開しない。** R5 は委譲のゲートと書き込みの間の認可窓であり、
店にトランザクションが無いことは据え置き。ここで扱うのは
**content bytes と台帳 entry が別物を指さないこと**で、残件 ID は **E1**。

CouchDB と台帳 DB をまたぐ単一 transaction は前提にしない。
Phase 0 の architecture spike で案 A（同一 revision 上の outbox marker）か
案 B（durable commitment intent）を fault injection で選ぶ。選定条件:

- bytes と statement が別物を指さない
- write 成功後の gap が永続的に観測できる
- retry が同じ statement を二重記録しない
- 失敗を業務の失敗へ誤変換しない
- 次の版へ進んだあとに古い intent を新しい bytes で閉じない

**この増分で「全 content write を記録した」とは書かない。**
Phase 0 で経路を列挙し、列挙できたものだけを G3 の対象にする。
列挙できなかった経路は残件 1 行であり、成功扱いにしない。

最低限の列挙対象: 外部取込、CMIS `createDocument` / `setContentStream` / `checkIn`、
versionable と非 versionable、PWC。到達できなかった経路は表に「未到達」と書く。

既存記録は backfill しない。admin の `observe-current-state` だけが
`commitmentKind=OBSERVED` を作る。「この観測時点で存在し、その後 anchor された」まで。
受領時から不変だったとは書かない。`OBSERVED` を `CAPTURED` と表示しない。

DLQ payload 機械（R35 / R43 / D1）は **証明 chain が要っても凍結のまま**。
開くならユーザーの明示。

## 9. Export は immutable な EvidenceBundle

`EarkSipExporter` が部品ごとに `latest()` を読む構造をやめ、最初に bundle を固定する。
以後の package build は bundle だけを使い、DB を再読しない。

既存 API の既定は壊さない。assurance は明示パラメータ:

`BEST_AVAILABLE` / `REQUIRE_PACKAGE_INTEGRITY` / `REQUIRE_RECORD_LEDGER` /
`REQUIRE_ANCHORED_CHECKPOINT` / `REQUIRE_TRUSTED_RFC3161` / `REQUIRE_LONG_TERM_ERS`

`REQUIRE_*` は満たなければ package を返さない（500 ではなく 4xx/409 + reason code）。
現行の応答 field は削除せず、`evidenceProfile` / `verdict` / `reasonCodes` を加算する。

METS を source of truth にする。suffix で最初の `premis.xml` を拾わない。
derived copy に原記録と同じ claim を持たせない。

## 10. 外部 verifier

Maven モジュール `evidence-verifier-core` / `evidence-verifier-cli`。
core / Spring / CouchDB / CMIS / WAR に依存しない。
product writer と同じ hash helper を呼んで一致したことにしない
（Enforcer または architecture test）。

```text
nemaki-evidence verify <sip.zip> --profile ... --trust-profile ... [--expected-checkpoint] [--json] [--allow-network]
```

既定 no-network。exit 0=`VERIFIED` / 2=`FAILED` / 3=`INDETERMINATE` / 4=usage / 5=internal。
ZIP/XML/JSON/ASN.1 の資源制限。制限到達は crash ではなく `RESOURCE_LIMIT`。

独立 test vector を `docs/evidence-profile/v1/vectors/` に置く。
Java writer・Java verifier・test-only の独立 reference の三者が同じ vector を出すことを CI にする。

Release artifact: jar、SHA-256SUMS、detached signature、SBOM、provenance、
result schema、profile spec、vectors。package が verifier の download URL を
信頼根拠として埋め込まない。

## 11. RFC 3161 / trust / ERS

維持: nonce、imprint、policy、CMS、embedded cert、configured trust anchor への PKIX、
accreditation 文字列を事実として読まない。

追加して保存: token DER、imprint/CMS アルゴリズム、chain、policy OID、genTime、
**発行時の** CRL/OCSP raw + digest + retrieval time。
後から取った current OCSP を発行時取得済みのように扱わない。

trust profile は package 外。認定業務であることは cryptography から推論しない。
runbook にサービス名・契約・policy OID・認定範囲を運用資料として置く。

ERS: 新規の組立はせず、**export bundle 全体で checkpoint を一つに固定**し、
`checkpoint.c14n` を data object として同梱し、external verifier が同じ hash を覆うことを確認する。
real token で RODA round-trip。stub DER は出荷しない。無い構成は `NOT_PRESENT`。
renewal は自動実行せず dry-run と明示実行。

## 15. 必須の負のコントロール（B。要約）

Package: payload だけ変更、payload+PREMIS 同時変更、METS が別 payload、未参照追加、
PREMIS/evidence 二重化、ZIP path 重複・traversal・bomb。

Binding: objectId / 版キー / length の改変、statement と payload の別文書組み合わせ、
entry field と entryHash の片方だけ・両方変更。

Checkpoint: sibling 変更、root 変更、field+hash 同時変更、chain 欠落・逆順、
古い正当 checkpoint を expected に反して提示。

RFC 3161: imprint 不一致、偽署名、cert 差替え、trust anchor / policy 不一致、revoked、
失効材料不在（strict は `INDETERMINATE`）、package 内 root だけで信頼。

ERS: 別 checkpoint.c14n、renewal が前を覆わない、unknown algorithm は `INDETERMINATE`
（不一致と呼ばない）。

集約: digest PASS + path NOT_PRESENT → `INDETERMINATE`。何も調べない → 同。
必須の一つが NOT_CHECKED → 同。全必須 PASS → `VERIFIED`。

Crash: E1 の各 transition 後に停止し、再開後を固定する
（intent 前後、content 後、ledger 後、CHAINED 前、次版へ進んだあとの recovery）。

互換: 3.4.0 SIP は `legacy`。記録 binding が無い旧 SIP を `VERIFIED` にしない。
P0 相当だけ検査して limits を出す。既存 export の既定 shape を保持。TCK。

相互運用: commons-ip2、DILCIS corpus、**real** RFC 3161 + real ERS で RODA 6.3.0、
取り出した artifact を CLI で再検証。Archivematica は E-ARK 専用解釈をしていない現状を明記し、
通常 ZIP としての保持確認は別 test。

## 18. RC の完了定義

- トラック A 完了
- profile 1 凍結
- payload → statement → entry → checkpoint → anchor が通る
- verifier が WAR・サーバ・repository 網を必要としない
- 必須 check 不在を成功にしない
- real RFC 3161、real ERS、real RODA round-trip を測定（未測定は残件であり PASS にしない）
- 失効不明を明示
- 旧データを capture 時の証拠として backfill しない
- 禁じ手が product / docs / UI / RELEASE_NOTES に無い
- RELEASE_NOTES に、何が証明でき何ができないかを同じ強さで書く
- open P0/P1 が 0

名乗れる文（全必須 profile が成立した package についてのみ）:

> この SIP に含まれる対象 bytes は、同梱された record content statement と一致し、
> その statement の digest は証拠台帳 entry に結び付いています。当該 entry から
> checkpoint までの inclusion proof、checkpoint chain、および指定 trust profile による
> 外部 anchor の検証を、NemakiWare を起動せずに再実行できます。

必ず併記:

> この検証は、取込前の内容の真実性、対象が漏れなく取り込まれたこと、
> 提示 checkpoint が最新であること、法令適合、JIIMA 認証、または管理者による
> 変更の防止を証明しません。外部で保持した checkpoint または trust profile を基準に、
> 提示された証拠範囲の事後変更を検出するものです。
