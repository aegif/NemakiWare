## 1. 出す前に直す

### B1 (blocker ✔筆者確認済み): 全再索引が索引を消したまま「完了」を返しうる

**機構** (3 つが噛み合う):

1. `ContentDaoServiceImpl.getChildren` は例外を握り潰して**空リストを返す**
   (`core/src/main/java/jp/aegif/nemaki/dao/impl/couch/ContentDaoServiceImpl.java:1143-1146`
   — `return new ArrayList<Content>(); // Return empty list on error`)
2. `startFullReindex` は **件数カウント → `clearIndex` → 走査** の順
   (`SolrIndexMaintenanceServiceImpl.java:138-150`)
3. 走査は folder ごとに catch するが、上記のとおり**例外が来ない**ので `errorCount` も増えない
   (`SolrIndexMaintenanceServiceImpl.java:401-407`)

結果: `children` view が引けない状態で再索引を打つと、**Solr を空にした後に「子が居ない」と
見えて、errors=0 / status=completed のまま空の索引が残る**。しかも完了後の健全性チェックは
同じ走査で母数を作るので **missing=0 / healthy=true** と答える。

**なぜ v3.3.0 で現実的か**: 初回起動で `Patch_JoinedGroupsSingleEmit` (F4) が `_design/_repo` を
書き換え、CouchDB が**全 view を再構築する**。手順書は起動後に全再索引を打てと言う。
再構築中の view クエリはタイムアウトしうる (既知: 起動ログに
`Error getting patch history ... _repo/patch - timeout` が出ることがある、と RELEASE_NOTES に記載済)。

**直し方 (最小・低リスク)**:
- `startFullReindex` の**先頭で view の可用性を確認**し、駄目なら `clearIndex` に到達させず失敗させる。
- 走査側は「子 0 件」と「取得失敗」を区別する。少なくとも**再索引の経路だけは**
  `getChildren` の握り潰しに依存しない (失敗を伝播させる or 明示的に失敗を数える)。
- **完了判定に独立な母数**を使う。`countDocumentsRecursive` と本走査が同じ壊れ方をする限り
  健全性チェックは意味を持たない。CouchDB の `_all_docs` 総数など、走査と独立な数を突き合わせる。

**検証の形**: `children` view を一時的に引けなくした状態 (design doc をリネーム等) で
再索引を打ち、**修正前は completed/errors=0 で空になること**、修正後は失敗すること。
陰性対照が取れる形にする。

### H1 (high ✔検証済み): V2 のインスタンス検査は CMIS 経路にしか無い

`TypeResource.java:530-533` の `@DELETE /repo/{repositoryId}/type/delete/{typeId}` (管理 UI が使う)
は `typeService.deleteTypeDefinition` を**直接**呼び、`TypeManagerImpl.deleteTypeDefinition` の
ガードを丸ごと迂回する (`TypeResource.java:613`)。

RELEASE_NOTES の「インスタンスが残っているタイプは削除できなくなりました」は
**主要経路で偽**。直すか、記述を経路限定にするかの二択で、**直す**方を採る
(検査を `TypeService` 側に下ろすか、REST 経路も TypeManager 経由にする)。

### H2 (high・未検証): CMIS 例外素通しで「本当の失敗」が 404 になる

`TypeManagerImpl.deleteTypeDefinition` は constraint / invalidArgument 以外の**あらゆる例外を
`CmisObjectNotFoundException` に包み直す** (`TypeManagerImpl.java:4089` 付近)。
今回入れた `CmisBaseException` 素通し (`RepositoryServiceImpl.java:494`) はこれもそのまま通すので、
**これまで 500 だった削除の失敗が 404 (=既に無い) としてクライアントに届く**。
クライアントが「消えている」と誤認する。

**着手前に再検証**: 包み直しの範囲と、404 を成功扱いする実クライアントの有無。

### H3 (high・一部検証済み): secondary type はインスタンス検査を通らない

`countByObjectType` の map は `emit(doc.objectType, doc)` で、secondary の適用先は
`Content.secondaryIds` という別フィールド。したがって**使用中の secondary type は今も削除できる**。
V2 が塞いだ穴が secondary では開いたまま。RELEASE_NOTES の書き方もこれに合わせる。

### H4 (medium ✔検証済み): `getChildrenNames` の握り潰しで名前重複が通る

`ContentDaoServiceImpl.java:1416-1418` が catch → 空リスト。消費者は
`ExceptionServiceImpl.java:1384` (作成) と `ContentServiceImpl.java:2871` (リネーム)。
**CouchDB が一瞬落ちると名前一意性チェックが黙って通り、重複名が作られる**。
existContent で直したのと**同じ fail-open**。同じ理屈で塞ぐ。

## 2. 出した後でよい (ただし R1 は所要時間として周知が要る)

### R1 系: 全再索引スループット劣化 (Codex 調査、10.3 → 2.6 文書/秒)

Codex の診断は筆者も一次確認した。**主因は「未コミットのバッチを通常クエリで検証している」こと**:

1. **T1 (very high・長年の欠陥、今回の範囲外)**: `flushBatch` はバッチを
   `commitWithin=5000ms` で投げた**直後**に、通常の `solrClient.query()` で検証する
   (`SolrIndexMaintenanceServiceImpl.java:451,546`)。全再索引は先に `clearIndex` するので
   古い可視コピーも無い。→ **ほぼ全件が「missing」と判定され 1 件ずつ再索引される**
   (`:573`)。つまり**全文書が 2 回索引される**。個別再索引は `commitWithin=1000` なので
   ソフトコミットが延々走り、索引が育つほどマージ負荷で遅くなる = **劣化の形になる**。
   - **決定的な確認**: 再索引を 1 回回して `silentDropCount` を見る。総文書数に迫れば確定。
   - 直し方: realtime GET (`/get`) で検証するか、強制コミット後にまとめて検証する。
2. **T2 (high・**今回の C8 で入れた退行**)**: `indexDocumentsBatch` が文書ごとに
   Solr realtime GET + **キャッシュを迂回した CouchDB GET** を足した。
   `ContentIncarnation.resolve` は**既に incarnation を持っていても必ず先に読む**
   (`ContentIncarnation.java:88-93`)。列挙済みの `Content` は既に `content_incarnation` を
   持っているのに取り直している。T1 と重なると 1 文書あたり 2 倍。
   - 直し方: 100 件分の Solr 状態を 1 回で先読みし、incarnation も手元の値を使う
     (fence の意味論は保つ)。
3. **T3 (high・長年)**: 添付が文書あたり **3 回**の CouchDB 往復
   (`extractTextContent` の メタデータ GET + 本体 GET、そして `getContentLength` の
   **もう 1 回のメタデータ GET**)。取得済みの添付オブジェクトが既に length を持っている。
4. **T4 (low)**: 個別 fallback が文書ごとに INFO を数行出す。DEBUG に落とす。

**リリースとの関係**: 正しさには影響しない。ただし v3.3.0 は全再索引が**必須**なので、
**10 万文書で 10 時間級**という所要時間は RELEASE_NOTES に明記する (済)。
T1 だけでも直せば体感で倍近く戻る見込みだが、**索引の可視性に触る変更**なので
リリース後の腰を据えた対応にする。

### O 群: 運用手順 (未検証・要再検証)

- **O1**: 10 時間級の再索引に**再開手段が無い** (毎回 `clearIndex` から、進捗は JVM 内のみ)。
  CLAUDE.md の「時間帯で分割実行してください」は full reindex には成立しない。**記述を直す**。
- **O2**: multi-replica で再索引・初期 epoch stamp を**どのレプリカで打つか**がどの手順書にも無い。
  どちらも JVM ローカル状態。
- **O3**: verdict `COMPLETE` は「索引に在る文書が全部 stamp 済み」であって
  「索引に全文書が在る」ではない。B1 と組み合わさると**空の索引でも COMPLETE**。
- **O4**: ロールバック手順が無い。
