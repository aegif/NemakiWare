## 0-C. `getChildrenNames` の裏取りは撤回した (TCK がハングした)

Codex の High 指摘を受けて Mango の裏取りを入れたところ、**CMIS TCK が CrudTestGroup で
停止**した。原因は自明だった: **空フォルダは異常ではなく最も普通の状態**で、
`getChildrenNames` は作成・改名のたびに走る。`parentId` に索引が無いため、
**空フォルダ 1 つにつき全件走査**が発生していた。

Codex は Medium #5 で「索引の無い Mango 走査」を指摘しており、私は
「条件付き経路のみ」と退けた。**その判断が誤りだった** — パッチ履歴 (起動時のみ) や
`existContent` (稀な型削除) では条件付きだが、`getChildrenNames` はホットパスだった。

**その後 (9de2e2a72) に、判定条件を変えて閉じた。** 誤っていたのは「この parentId が空か」を
signal にしたことで、**空フォルダは異常ではなく最も普通の状態**だった。判定を
**リポジトリ全体**に移してある: `childrenNames` が 1 行でも返るならこの parent の空は本物、
全体が 0 かつデータベースに文書が 10 を超えてある場合だけ一意性チェックを拒否する。
読むのは view の行数だけで、文書は読まない。keyed query が例外を投げる場合は元から
fail-closed。**したがってこの穴は閉じている。**

## 1. 出す前に直す

### ✅ B1 (blocker) — **2026-08-13 に再現し、修正した**

**実機で再現した** (`tools/acl-probe/reindex_wipes_index_probe.py`、canopy に 164 文書を入れて):

| | 修正前 | 修正後 |
|---|---|---|
| status | **completed** | **error** |
| totalDocuments / indexedCount | 1 / 1 | 1 / 0 |
| errorCount | **0** | 0 |
| Solr の文書数 | **164 → 1** | **1610 → 1610 (無傷)** |

**障害の注入方法で 2 回外した**。記録しておく:

1. **view を削除する → 効かない。** core を再作成すると起動時に `Patch_StandardCmisViews` が
   走って **view を作り直す** (実測: rev 9 → 10)。この経路はシステムが自己修復する。
2. **map を構文エラーに → CouchDB が PUT を 400 で拒否**。
3. **map を実行時に throw させる → 効く。** そして重要なのは、view クエリが
   **HTTP 200 で `rows:[]`** を返すこと。

3 が設計を決めた。**エラーが起きないので、例外を伝播させる形の修正では閉じない。**
これは推測ではなく実測。したがってガードは**「今 Solr に在る CMIS オブジェクト数」**という、
同じ障害では黙らせられない物差しと突き合わせる形にした
(`-doc_type:[* TO *]` は RAG と CMIS を分ける正典の判別子)。

- 走査が今の索引の 1/10 未満しか見つけなければ **clearIndex に到達させず error で止める**
- Solr に問い合わせられないときは **0 ではなく「不明」として扱い、やはり止める**
  (失敗を空の索引と読むと、まさに塞ぎたいケースを通してしまう)
- 少数 (20 未満) と初回再索引は対象外 — 失うものが無いため

回帰テスト `ReindexRefusesToWipeIndexTest` は**実際の `startFullReindex` を駆動**し、
`clearIndex` の delete が呼ばれないことを検証する。ガードを外すと 2 件落ちる (確認済み)。

### ✅ PX1 (旧「B2」・**実地で observed**): パッチの再適用でシステムフォルダが二重になる

> **ID 注記**: 当初 `B2` と付けたが、台帳の既存 B2 (epoch 簿記 4 putBack) と衝突していたため
> `PX1` に改めた (`RX1` と同じ方針)。

レビューが**未検証**として挙げていた `PatchUtil.isApplied` の fail-open
(「パッチ履歴 view の照会に失敗したら『未適用』を返す」、`PatchUtil.java:77`) が、
B1 の作業中に**実際に起きた**。推測ではなく観測。

**観測した内容**: bedroom の root に `.system` フォルダが **2 つ**できた。

| id | created | 中身 |
|---|---|---|
| `34169aaa-…` | 2013-01-01 (初期データ) | `users` / `groups` |
| `c61374d7…` | **2026-08-13 12:07:36** | **空** |

`Patch_SystemFolderSetup` が再適用され、空の `.system` を作っている。結果として
**CMIS TCK の `rootFolderTest` が落ちる** — 「id で取ったオブジェクトと path `/.system` で
取ったオブジェクトが一致しない」。パス解決は 1 つしか選べないため。

**引き金**: このとき canopy の design document を書き換えていた。パッチ履歴 view
(`_repo/patch`) は**書き換え対象と同じ design document に同居**しているので、
照会が失敗し「未適用」に倒れたと考えるのが自然。**F4 のパッチ
(`Patch_JoinedGroupsSingleEmit`) は `_design/_repo` を書き換える**ので、
**v3.3.0 の初回起動はまさにこの状況を作る**。

**なぜ blocker 候補か**: v3.3.0 のアップグレードで、
(a) F4 パッチが design doc を書き換える →
(b) 全 view が再構築される →
(c) その間に走る他のパッチの `isApplied` が「未適用」に倒れる →
(d) パッチが再適用され、システムフォルダやコンテンツが二重になる。
本番リポジトリで重複が生まれると、**TCK が落ちるどころか CMIS のパス解決が壊れる**。

#### 切り分け結果 (2026-08-13): 歯車は 3 つで、いずれもコードで確認した

レビューの指摘どおり **`isApplied` の catch だけ見ても閉じない**。

1. **履歴照会が「無い」と「引けない」を区別しない** —
   `ContentDaoServiceImpl.getPatchHistoryByName` は try の末尾でも catch でも `null` を返す。
   `PatchUtil.isApplied` はその `null` を「履歴なし = 未適用」と読む。**catch は 3 番目の歯車**で、
   その手前で既に情報が失われている。
2. **存在確認が同じ view を引く** — `Patch_SystemFolderSetup.findExistingSystemFolder` は
   `client.queryView("_repo", "children", ...)` を直に叩く。B1 で実測したとおり
   **rebuild 中の view は HTTP 200 で `rows:[]`** を返すので、原本があっても「無い」と読む。
3. **名前一意性も空** — `getChildrenNames` の握り潰し (H4) により、同名 `.system` が
   CMIS 制約をすり抜ける。

**裏づけとなる痕跡** (推測ではない): bedroom には
`system-folder-setup-20250805` の**パッチ履歴が 2 件**ある。`createPathHistory` は
既存を探してから作るので、**その照会も null を返していた**ことになる。`.system` の重複と
合わせ、同じ fail-open が 2 箇所で起きた証拠。

**因果を広げない**: 「canopy の design doc を壊したから bedroom に出た」とは書かない。
レビューの指摘どおり、**core 再起動時に bedroom 側で F4 が当たった**方が単純。
なお `log.info("Applying patch: ...")` は `isApplied` チェックの**前**にあるので、
起動ログに 12 本並ぶことは「12 本が再適用された」意味ではない (紛らわしいので記録)。

#### 直したこと

- **`getPatchHistoryByName` は照会失敗で throw する** (`null` は「無い」だけを意味する)
- **`isApplied` は照会できないとき APPLIED を返して当該パッチを飛ばす**。
  起動を止めるより安い: 本当に未適用なら次回起動で当たる。**冪等でないパッチの二重適用は
  待っても戻せない**
- **`.system` の存在確認を view から外した**。設定に記録済みの `system.folder` id を
  **`nemaki_conf` の `_all_docs`** で読む — view でもなければ、F4 が書き換える design document と
  同じデータベースでもない。記録が無い/指す先が消えている場合だけ従来の探索に落ちる

回帰テスト `PatchHistoryFailClosedTest` は 4 件。fail-open に戻すと 1 件落ちる (確認済み)。

#### 第 2 ラウンド (レビュー指摘): 例外経路だけでは閉じていなかった

最初の修正は **`throw` する経路しか塞いでいなかった**。実際に起きた障害は例外を出さない —
**rebuild 中の view は HTTP 200 で `rows:[]`** を返す (B1 で実測)。したがって
`getPatchHistoryByName` は今も `null` を返し、`isApplied` はそれを「未適用」と読み、
**`.system` 以外の非冪等パッチは無防備のまま**だった。

`patch` view が 0 行を返したときだけ、**Mango (`_find`) で裏を取る**ようにした。Mango は
`_design/_repo` を読まないので、同じ rebuild では黙らない。両方が「無い」と言ったときだけ
absent と報告する。**view が答えられた通常の起動では Mango を引かない** (テストで固定)。

回帰テスト `PatchHistorySilentlyEmptyViewTest` 4 件。裏取りを外すと 2 件落ちる (確認済み)。

#### 第 3 ラウンド: 冪等でないパッチの棚卸し (Codex、41 本全数)

**Unsafe 14 / Safe 27 / Unknown 0。** レビューの「15 本以上が巻き添え」はほぼ当たっていた。

共通機構は 1 つ: **存在確認が `_design/_repo` の view 依存で、作成が CouchDB 生成 id**。
両方が要る — view が空を返すから「無い」と判定し、id が決定的でないから CouchDB も
conflict で弾けない。だから `catch (conflict)` を足しても守れない。

不安全な 14 本 (worst first): `initial-content-setup` (フォルダ・文書を `_repo/children`
だけで判定)、`nemakiware-standard-types`、`mcp-service-account` (ユーザを
`userItemsById` で判定)、`Test User and Group Initialization`、secondary type 系 7 本
(`message-metadata` は 11 プロパティ + 型を重複させうる)、`ingest-relationship-types`、
`external-integration-source-fields`。

**14 本を個別に直さず、入口に 1 つゲートを置いた。** 15 本目や将来のパッチも守れるため:

`PatchUtil.cmisViewsAreAnswering` — **データベースに文書があるのに中核 view が 1 行も
返さないなら、view は動いていない**。B1 の再索引ガードと同じ形。新鮮なリポジトリは
どちらも空なので止めない。`AbstractNemakiPatch.apply` が repository ごとに通す。

**ここで 1 つ間違えた**: 最初カナリアに `children` view を使ったが、これは `_count`
reduce を持ち、`queryViewCount` が読む `total_rows` が reduce 応答には無い。結果
**健全な bedroom に対して 312 回拒否**した。ユニットテストは (モックなので) 素通り。
実機のログを見て気づき、reduce の無い `childrenNames` に変えて **0 件**を確認した。
モックだけで確かめると、こういう「本物とだけ食い違う」誤りは通る。

**残っていること**: 14 本の個別修正はしていない。ゲートは「view が死んでいるときに

### ✅ PX2 (旧「B3」・**実地で observed → 修復手段を用意**): 削除済み文書が索引に残り、クエリに出る

B1 の作業中に TCK の `Query Smoke Test` が落ちて判明。原因は**孤児の索引エントリ**。

bedroom の Solr に PWC が **3 件** あり、**3 件とも CouchDB では削除済み**だった
(`task_72.txt` / `task_24.txt` / `task_22.txt`)。CMIS のクエリはこれらを返し、

**まだ確定していないこと (原因を私の作業に断定しない)**:
- これらが**製品の欠陥** (PWC の削除が索引に伝わらない) なのか、**私が今日コンテナを

**なぜリリース前に見るべきか**: 削除した文書が検索結果に出続けるのは、内容によっては

同じ経路が通常文書で起きるなら話が違う。

#### 切り分け結果 (2026-08-13): 機構は特定できた

削除は **CouchDB → Solr の順**で、Solr 側は**非同期 + JVM 内リトライのみ**:

- `ContentServiceImpl.deleteDocument` :3116 / `cancelCheckOut` :1755 が
  `solrUtil.deleteDocument(...)` を呼ぶ (CouchDB の削除が先に確定している)
- `SolrUtil.deleteDocument` は `CompletableFuture` + `asyncSolrExecutor`。失敗すると
  `.exceptionally(...)` が `scheduleRetry(task, documentId, 1)` を呼ぶ
- `scheduleRetry` は `SOLR_INDEX_MAX_RETRY` で打ち切り、**`onPermanentFailure` フックが
  あれば**そこで耐久化できる — **削除経路は 3 引数版を呼んでおり、フックを渡していない**。
  つまり**リトライを使い切ったら ERROR ログだけ**で孤児が恒久化する

**なぜ今回それが起きたか**: 私が B1 / PX1 の作業でコンテナを**繰り返し強制再作成し、
再索引を kill した**ため。リトライは JVM 内にしか無いので、プロセスが死ねば消える。
**つまり「私の汚染」でもあり「製品の性質」でもある** — 通常運用でも、Solr 障害中に
削除して JVM が落ちれば同じ孤児が残る。

**なぜ黙って残るのか**: 完了後の健全性チェックは CouchDB 側の母数を**走査**で作るので
(B1 と同じ `getChildren`)、「CouchDB に無いのに Solr に在る」は検出できる方向のはずだが、
今回それも `healthy=true` を返していた。

#### どう決着したか (2026-08-13)

当初「reconcile のどの Operation で積むか」を設計判断として保留したが、**調べれば決まる話**
だった。調べた結果:

- `SKIPPED_DELETED` は「完了」扱いで索引を消さない → **`ACL_REINDEX` の再利用は不可**
- purge レーンは `purgeRagBlockForObject` のみ → **RAG 専用で CMIS 文書は消せない**

そこで **reconcile の語彙には触らず**、管理エンドポイント
`POST .../search-engine/purge-orphans` を足した。健全性チェックは既に孤児を
**検出**できていた (`orphanedInSolr`) のに、**修復手段が無い**のが本当の欠落だった。

**存在確認は `existsStrict`** — CouchDB が 404 を返したときだけ「不在」とし、それ以外の
失敗は例外にして purge 全体を拒否する。`contentService.getContent` も
`CloudantClientWrapper.get` も**読めなかったときに null を返す**ので、それで確認すると
CouchDB 障害中に版や PWC が全部「不在」に見える — 対策のつもりで
「失敗＝無い」をまた書くところだった (レビュー指摘)。

**B1 と同じガードも掛かる**: 孤児候補が索引の 1/10 を超えるような食い違いは
「はぐれ者の掃除」ではないので、何も消さずに 409 で拒否する。

**残る本質的な穴**: これは**事後の掃除であって予防ではない**。リトライ中に JVM が死ぬ窓は
塞がっていないので、孤児は今後も生まれうる。生まれたものを再索引 (10 時間級) 抜きで
消せるようになった、というのが今回の到達点。本当に閉じるには ACL の outbox と同じく
「先に耐久義務を書いてから消す」形が要り、これは設計変更であってパッチではない。

**運用への影響**: 削除した文書が検索に残りうる。PWC は作成者しか見えないので今回の
3 件の実害は小さいが、**通常文書で起きれば情報の露出**になる。

**後始末**: 今回の 3 件は Solr から除去済み。

## 2. 出した後でよい (ただし R1 は所要時間として周知が要る)

### R1 系: 全再索引スループット劣化 (Codex 調査、10.3 → 2.6 文書/秒)

Codex の診断は筆者も一次確認した。**主因は「未コミットのバッチを通常クエリで検証している」こと**:

1. **T1 (very high・長年の欠陥、今回の範囲外)**: `flushBatch` はバッチを
   `commitWithin=5000ms` で投げた**直後**に、通常の `solrClient.query()` で検証する
   (`SolrIndexMaintenanceServiceImpl.java:451,546`)。全再索引は先に `clearIndex` するので
   古い可視コピーも無い。→ **ほぼ全件が「missing」と判定され 1 件ずつ再索引される**
   (`:573`)。つまり**全文書が 2 回索引される**。個別再索引は `commitWithin=1000` なので
   ソフトコミットが延々走り、索引が育つほどマージ負荷で遅くなる = **劣化の形になる**。
   - **決定的な確認**: 再索引を 1 回回して `silentDropCount` を見る。総文書数に迫れば確定。
   - 直し方: realtime GET (`/get`) で検証するか、強制コミット後にまとめて検証する。
2. **T2 (high・**今回の C8 で入れた退行**)**: `indexDocumentsBatch` が文書ごとに
   Solr realtime GET + **キャッシュを迂回した CouchDB GET** を足した。
   `ContentIncarnation.resolve` は**既に incarnation を持っていても必ず先に読む**
   (`ContentIncarnation.java:88-93`)。列挙済みの `Content` は既に `content_incarnation` を
   持っているのに取り直している。T1 と重なると 1 文書あたり 2 倍。
   - 直し方: 100 件分の Solr 状態を 1 回で先読みし、incarnation も手元の値を使う
     (fence の意味論は保つ)。
3. **T3 (high・長年)**: 添付が文書あたり **3 回**の CouchDB 往復
   (`extractTextContent` の メタデータ GET + 本体 GET、そして `getContentLength` の
   **もう 1 回のメタデータ GET**)。取得済みの添付オブジェクトが既に length を持っている。
4. **T4 (low)**: 個別 fallback が文書ごとに INFO を数行出す。DEBUG に落とす。

**T3 (文書あたり 3 回の CouchDB 往復) は着手しない**。`extractTextContent` が取る添付は
既に length を持っているので `getContentLength` の 3 回目は冗長だが、**正しさには影響せず、
F3 (接続リーク) の修正経路に触れる**。しかも直前に RX1 で「速くなる」と書いて A/B に
否定されたばかりで、**未測定の性能変更をリリース直前に入れる理由がない**。
規模依存の劣化の真因が分かってから、測定付きで扱う。

**リリースとの関係**: 正しさには影響しない。ただし v3.3.0 は全再索引が**必須**なので、
**10 万文書で 10 時間級**という所要時間は RELEASE_NOTES に明記する (済)。
T1 だけでも直せば体感で倍近く戻る見込みだが、**索引の可視性に触る変更**なので
リリース後の腰を据えた対応にする。
