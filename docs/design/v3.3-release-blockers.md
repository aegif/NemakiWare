## 0. 判定基準 (プロダクトオーナーと合意済み)

1. **大規模リポジトリで伝播に時間がかかること自体は許容する** (非同期なら数時間でも可)。
2. **その処理がアプリケーション全体の性能を落とすことは許容しない** (隔離が合格条件)。
3. **「いま伝播中である」「あとどれくらいで収束するか」が管理画面か、
   せめてログから判断できること** (可観測性が合格条件)。
4. 権限の**剥奪**が効くまでの遅延は、上限が有界かつ説明可能であること。

**初回判定 (2026-08-09)**: **1 は合格** (権威データは読み取り時継承のため伝播不要、
検索側のみ非同期追いつき)。**2 は不合格** (§2.2)。**3 は不合格** (§2.4)。
**4 は CMIS 経路は合格、ただし例外が 3 つ** — C4 (revoke 窓の 400)、
multi-replica のキャッシュ (D 群)、RAG 経路 (R1、seed ゲートは確認済みだが
未評価領域が残る)。

**作業後の状況 (2026-08-12)** — **§7 の再判定を通した後の状態**:

| 基準 | 初回 | 現在 |
|---|---|---|
| 1 伝播に時間がかかること自体 | 合格 | 変わらず |
| 2 全体の性能を落とさない (隔離) | 不合格 | ✅ **再測定して合格** (§7)。caller-runs 64 回に対し委譲 64 回、リクエストスレッドは 1 本も走査しなかった。**この再測定の過程で move 経路に委譲が一切無いことが判明し、修正した** |
| 3 可観測性 | 不合格 | ✅ **再測定して合格** (§7)。931 ノード / 15.6 秒の伝播で、判定窓の 91% が ETA ±20% 以内 |
| 4 剥奪の遅延が有界 | CMIS 合格・例外 3 | ✅ C4 は staleness ゲート、D 群は cross-replica 実測済み (ACE 0.25–1.33 s / グループ 5.4–8.4 s、**上限ではない**)、R1 は 7 経路を陰性対照付きで実測して残差なし |

**「該当項目が着地した」と「基準を満たした」は別物**である — この区別は実際に効いた。

## 1. 現状の伝播モデル (実測で確認済みの事実)

改善を論じる前に、何が**既に正しく速い**かを固定する。

### 1.1 認可 (getObject / ナビゲーション) は即時

実効 ACL は子孫に保存されず、読み取りのたびに祖先を辿って合成される
(`AclSemantics.effectiveAcesInternal` の再帰、AclSemantics.java:225-252)。
親の ACL を変えても子孫の CouchDB 文書は `_rev` ごと不変で、変わるのは読み取り結果だけ。

- 実測: 8 段上の親に applyACL → 子文書の CouchDB 実体は `acl={"entries":[]}` のまま、
  CMIS getAcl は 17ms 後に新 ACE を `isDirect=false` で返した。
- 実測: 122 ノードのサブツリーで applyACL 直後の getObject が 120/120 成功
  (陰性対照ユーザは全期間 403 / 0 件)。
- コスト: warm 1.7ms (深さ非依存、aclCache に memoize)、cold 約 1.4ms/hop
  (depth 60 で 84.8ms)。AclServiceDelegate.java:63-74。

この即時性は applyAcl 内の**同期キャッシュ退避 BFS** (AclServiceImpl.java:1081-1111)
が支えている。ここを非同期化・有界化すると即時性が壊れる。**触るなら代替の無効化
機構とセット**でなければならない (§3 P1-3 — これは基準 1 ではなく**基準 4 の問題**)。

### 1.2 検索 (Solr readers) だけが非同期で追いつく

Solr の `readers` フィールドは実効 ACL の非正規化で、親の ACL 変更後は
子孫 1 件ずつ書き直される (AclServiceImpl.java:489 → :905-1060)。

- 可視化の上乗せは経路で異なる: **readers の fenced write は commitWithin=1000ms
  (AclEpochIndexWriter.java:64,:308) で約 1 秒以内**。autoSoftCommit maxTime=3000ms
  (最大約 3 秒) が効くのは commitWithin を付けない全文書索引経路
  (SolrUtil.indexDocument) だけ。
- 端到端の実測 (applyACL 発行 → 非 admin の検索に全件出るまで、可視化ラグ込み。
  フォルダ ACE 2〜3 件・深さ 1・relationship 無しの条件、陰性対照つき):

  | 子孫数 | GRANT 検索収束 | REVOKE 検索収束 | GRANT getObject | applyACL 応答 |
  |---|---|---|---|---|
  | 10 | 1.01 秒 | **0.06 秒** | 0.08 秒 | 147 / 153 ms |
  | 100 | 2.25 秒 | **0.18 秒** | 0.08 秒 | 204 / 218 ms |
  | 348 | 5.93 秒 | **0.53 秒** | 0.59 秒 | 258 / 259 ms |

  3 点は **T ≈ 1.0 秒 (commitWithin 下限) + S × 約 14ms (書込 ≈ 70 docs/s)** の
  線形にほぼ正確に乗る (予測 1.1 / 2.4 / 5.9 秒)。applyACL 応答は S にほぼ非依存
  (+約 0.3ms/子孫 — B1 の同期 BFS ぶん)。
- **書込レートは ACE 数と深さに強く依存する**。経路解析時の別測定 (ACE 11 件・
  relationship 検査込み) では 41 件 ≈ 4.3 秒、120 件 ≈ 3.58 秒と、1 ノードあたり
  約 100ms (≈10〜30 docs/s) まで落ちた。1 ノードのコスト内訳は CouchDB 生 GET
  2×(1+深さ) 回 + principal lookup 2×ACE 数 + relationship view 2 回 +
  Solr RTG/atomic update 各 1 回 (A3/A4)。
- 外挿: 子孫 10 万件の GRANT 検索収束は **ACE 少なめ・浅い構成で約 25 分、
  ACE 多め・深い構成で 1〜3 時間**。基準 1 により時間そのものは許容範囲 —
  問題は隔離 (§2.2) と可観測性 (§2.4)。

### 1.3 GRANT と REVOKE は非対称 (REVOKE が安全側)

非 admin のクエリは Solr で `readers` fq により絞られ、その後 in-memory の
`getFiltered` (PermissionServiceImpl.java:532-566) が**取り除く方向にだけ**再検査する。

- **REVOKE は即時に効く**。実測: 剥奪直後 t+0.06 秒で検索 0 件 (Solr readers に
  剥奪済みトークンが残った状態でも)。getObject は 65ms で 403。
- **GRANT だけが readers 書き換え + soft commit を待つ**。実測 t+1.0 秒 (S=10)。
  この間「getObject では読めるのに検索に出ない」窓が開く (§2.4 E5)。
- ただし REVOKE にも例外がある: 伝播完了までの間、`numFound` は stale-permissive の
  まま過大で、**ACL scan cap を跨ぐと 400 になる** (C4)。結果行は正しいのに
  「検索が壊れた」ように見える。

### 1.4 applyACL の同期応答時間は子孫数にほぼ依存しない (現規模では)

実測: 子孫 0 件で約 215〜232ms、10 件 147ms、122 ノード 207ms、348 件 258ms、
depth60 チェーン 278ms。
支配項は子孫走査ではなく **ACL-epoch の簿記** (§2.2 B2) と **ACE 数** (+8ms/ACE、
1 ACE 180ms → 22 ACE 363ms。原因は ACE ごとの非キャッシュ principal view lookup、
AclSemantics.java:312-378 → cached 側 PrincipalDaoServiceImpl.java:107-134 が素通し)。

ただしキャッシュ退避 BFS はフォルダごとに `getChildren` view クエリを発行するため
(AclServiceImpl.java:1098)、**子孫が数万件になれば応答時間はそこに支配される**。
上限・ページング・バッチは無い (§2.2 B1)。

## 3. 改善計画

### 凍結制約との整合 (最初に明記する)

CLAUDE.md は「**ThreadPoolExecutor の構造 (キューサイズ・CallerRunsPolicy 等) は
バックプレッシャー維持のため変更不可**」と定める。本計画はこれを次のように解釈し、
**逸脱する提案は明示的にオーナー判断を仰ぐ**:

- キューサイズ・CallerRunsPolicy・キュー実装は変更しない (P1-1 第一段が準拠)。
- `ragAclExecutor` の並列化 (max=1 → N) は fenced write の順序前提の証明なしには
  不可。P1 の主軸は**構造を変えない範囲でのスループット向上** (P1-2) とし、
  並列化はオーナー承認 + 設計精査を条件とする第二段。

### P0 — 権限の正しさ (最優先。性能より先)

**P0-1 (C1): ACLPropagation の意味論を正直にする。objectonly の拒否は行わない。**
初版の「constraintAclPropagationDoesNotMatch で拒否」は**撤回**する。理由は 2 つ:
(1) CMIS 1.1 §2.1.12.3 は propagate 宣言が objectonly の支持を含むと読め、拒否は
逆に非適合を作り込む恐れがある。(2) **自社 UI の継承ブレークが objectonly を送る**
(PermissionResource.java:229-231 が breakInheritance=true で OBJECTONLY を強制、
UI → `services/cmis.ts:1690-1706` → この経路)。拒否すれば継承ブレークが全滅し、
AclResourceIT.testApplyAcl_WithObjectOnlyPropagation_ReturnsOk も赤化する。
代わりにやること:
1. ~~PermissionResource.java:229-231 の **OBJECTONLY 強制を撤去**~~ → ✅ 着地済み
   (継承ブレークの実体は inherited=false 拡張であり propagation 値は無関係)。
   `AclDirectFlagAndPropagationTest.breakingInheritanceDoesNotForceObjectOnly` で固定。
2. ~~capability 宣言を `REPOSITORYDETERMINED` へ変更するかをオーナー判断に掛ける~~
   → **決着 (2026-08-12): PROPAGATE を維持**。継承リポジトリとして正しい箱であり、
   CMIS 1.1 §2.1.12.3 は propagate が objectonly のサポートを含むと読めるので、
   値を受理すること自体は非適合ではない。実装しないのは objectonly の**区別**であり、
   それを「未対応」と明記する。全 3 値の受理は維持し、constraint 拒否は導入しない。
3. 空の `constraintAclPropagationDoesNotMatch` には「全値受理は設計判断」の
   コメントを付ける (無言の no-op をやめる)。
*検証*: 自作の統合テストで propagation 3 値それぞれの応答と保存 ACE を assert。
**TCK は検証にならない** (ACLSmokeTest は aclPropagation=null を送り、checkACL は
principal/permissions の非空しか見ない — TCK 緑維持の確認のみ)。

**P0-2 (C2): direct フラグの反転を直す (整理レベル)。**
applyACL で保存する ACE は常に direct=true にする (`new Ace(principalId, permissions,
objectOnly)` → `true`)。**実機再現は陰性で確定済み** — 永続層が direct を保存しない
(CouchContent.java:354-366) ため既存データの移行は**論理的に不要**、wire は compileAcl が
リスト所属から再計算するため互換影響なし。修正の意味は、in-memory 期間・orphan 分岐
(AclSemantics.java:238-247)・ZipExporter 出力 (:321,:363) に残る誤値の除去と、
CMIS §2.1.12.1 (direct=TRUE は直接付与) との整合。hotfix 前倒しは**不要**。
*検証*: 再現テスト (陰性のまま) + orphan 分岐のユニットテスト。

**P0-3 (C4): REVOKE 窓の 400 — staleness でゲートした限定縮退。実装済み。**

cap そのものは緩めない。変えたのは「多すぎる」と「伝播中で数え過ぎている」を
区別できるようにした点だけ。

1. cap 超過を検出したとき、**そのときだけ** `AclPropagationStaleness` に問う。
   本レプリカで走行中の伝播 (`PropagationProgress`、メモリ内で無料) か、
   耐久化された reconcile キューが空でないか。どちらも無ければ従来どおり 400。
   **通常経路は 1 命令も変わらない** — cheap-reject (rows=0 プローブで $top=1 でも
   安価に拒否) が保たれ、追加コストは元々失敗する予定だったクエリだけが払う。
2. 縮退時は cap 内の確定行を返し、`truncatedByAclScanLimit` 拡張を付け、WARN を出し、
   メトリクス `queriesDegradedByAclScanLimit` を増やす。行そのものは in-memory gate を
   通っているので正しい。変わるのは「総数」の意味だけで、numItems は下界になる。
3. `hasMoreItems` は元々 cap 内の確定集合に対して計算されるので、窓の終端で false に
   なる。**0 行 + hasMoreItems=true を返す組み合わせは発生しない**。
4. 信号が読めない (キュー照会が失敗した) ときは fail-closed で「収束済み」とみなし、
   従来どおり 400 にする。検証できない言い訳で部分結果を返さない。

*検証*: SolrQueryProcessorScanCapTest — 伝播中のみ縮退すること、伝播していなければ
従来どおり拒否すること、cap 内のクエリは伝播中でも truncated にしないこと
(無関係なクエリまで疑わしくすると全ページが信用できなくなる)、rows=0 プローブと
cap 上限のフェッチが維持されること。既存 9 件は「縮退を許さない」で全て通る。

**P0-4 (C5): 深さ 50 打ち切りを「静かな失敗」から「観測される失敗」へ。**
(a) WARN に加えメトリクスカウンタ、(b) **打ち切り結果は短 TTL (例 30 秒) の隔離
キャッシュに入れ、通常の joinedGroupCache には入れない** (負キャッシュ全面禁止だと
該当ユーザの全リクエストが毎回 50 ラウンド × view クエリ ≈ 1 秒を再実行する恒常
負荷源になる)。実装注記: 現在の `List<String>` 戻りでは cached 層が打ち切りを判別
できないため、打ち切りシグナルの伝搬手段 (戻り値型 or スレッドローカル) が要る。
上限 50 自体は**作業量上限として**残す (サイクル対策ではない — それは visitedGroups
の仕事。§0 基準 4 の「50 段超は想定外」合意が残置の根拠)。
**決定 (計画からの逸脱を明示)**: 「短 TTL の隔離キャッシュ」は作らず、**打ち切り結果を
一切キャッシュしない**方針にした。打ち切りは誤った答えであり、キャッシュすると
一時的な設定ミスが恒久的な認可エラーになる。再計算コスト (該当ユーザだけ 1 リクエスト
約 1 秒) は、鎖を浅くした瞬間に自動回復することと引き換えに受け入れる。グループを
作れるのは管理者だけなので、一般利用者から到達できる負荷面ではない。

**この修正が直さないこと (明示)**: 深さ 51 段以上のユーザは**依然として上位グループの
ACE を失う** (検索 0 件・getObject 403)。§0 の合意により 50 段超は想定外とし、
直すのは「静かに失敗する」ことだけである。打ち切りは WARN + メトリクス
(`groupResolutionTruncations`) で必ず表面化する。

*検証*: TruncatedGroupResolutionTest (型・カウンタ・cached 層が打ち切りを
キャッシュしないことの配線)。55 段の実挙動は tools/acl-probe/group_depth_cliff.py。

**P0-5 (C6): 親子サイクルを潰す — ただし move ガード単独では防げない。**
1. moveObject に「移動先が自分自身または自分の子孫なら constraint」ガードを追加。
   **TOCTOU 対策**: 当初は「移動対象と移動先の 2 つを ID 順に write lock」で足りると
   考えたが、**これは不十分**。並行レビューの指摘どおり、A を B の**子**の下へ、
   B を A の**子**の下へ動かす組は、ロック集合が {A, B_child} と {B, A_child} で
   交差しないため互いを排除できず、両方がガードを通過してサイクルを作れる。
   ロック集合を広げても解決しない (押さえるべきは祖先チェーン全体で、それこそが
   相手の変更対象)。したがって**フォルダの move はリポジトリ単位の write lock で
   直列化する**。稀な管理操作であり、サイクルの代償 (配下の実効 ACL が計算不能に
   なる) に見合う。文書の move は子を持たずサイクルを作れないので並行のまま。
2. ガード自身の祖先ウォークにも visited + hop 上限 (既存サイクルで無限ループしない)。
3. AclSemantics の読み取り側にも hop 上限 128 + visited を入れ、到達時は epoch 側
   (AclEffectiveEpochService.java:640-675) と同じく **throw = fail-closed**
   (縮退して読めるより、読めない方が安全)。
*検証*: ConcurrentFolderMoveCycleTest — 実スレッド 2 本で敵対的にインターリーブし、
**旧実装 (オブジェクト単位ロックのみ) ではサイクルが再現すること**と、
**直列化するとサイクルが成立しないこと**を両方向で示す。加えて実機で自己子孫 move の
409、自分自身への move の 409、正常な move の 201 を確認済み。

**P0-6 (B3/B4): 世代フェンスでキャッシュ再投入レースを閉じる。実装済み。**
write lock 化では対象オブジェクト自身の窓しか閉じない (子孫の読み手は別ロックキー、
祖先ウォークは無ロック、退避 BFS も無ロック)。押さえるべきはサブツリー全体で、
それは走査中ずっと保持できない。代わりに**計算に日付を付ける**:

1. 読み手は祖先を辿る前に世代を記録し、`aclCache` への put はその世代がまだ現行の
   ときだけ行う (`AclServiceDelegate.putIfStillCurrent`)。掃過を跨いだ計算は
   公開を断られ、次の読みで再計算されるだけで済む。
2. 世代を上げるのは `clearCachesRecursively` の**冒頭** — 退避より前。後ろに置くと
   掃過中の読み手が「まだ現行」と判定される窓が残る。呼び出し元 (applyAcl / move /
   reconcile) を一括で覆える位置でもある。
3. 世代を記録し忘れた呼び出しは fail-closed で拒否する。
4. B4: applyAcl の退避失敗を捕捉し、move 経路と同じ CACHE_EVICTION_FAILURE で
   enqueue する。**索引リフレッシュは提出しない** — 退避できなかったキャッシュから
   readers を再計算すると、その stale 値を Solr に焼き込んで恒久化してしまう。

*検証*: AclCacheGenerationTest — 実スレッド 2 本で「読み手開始 → 書き手が世代を上げて
掃過 → 読み手が公開を試みる」を走らせ、再投入されないことを確認。あわせて
`aclCache.put` がファイル内に 1 箇所 (ガード付き) しか無いこと、世代 bump が退避より
前にあることも固定する。

**P0-7 (D3): applyAcl 迂回経路の stale。**
cached DAO の update() 系に aclCache 退避を追加する (最小修正)。
**フォルダ ACL を書く迂回経路は無いことを確認済み** (ZipImporter:552,:1238 /
FilesystemImporter / CanonicalImportServiceImpl とも document・relationship のみ) —
子孫走査の挿入は不要。性能影響は「ACL を変えない update でも退避が走る」ことによる
次回認可時の warm 再計算 ~1.7ms で無視できる。
*検証*: importer で ACL 付き取込 → 同一 JVM で即座に calculateAcl が新 ACL を返す
テスト (新規取込・再取込の両方)。

### ✅ F3 (接続リーク): 主因を特定して除去 (スイート 1 周で 0 件)

**メタデータのために添付本体を丸ごと落としていた経路を 4 つ塞いだ。** いずれも
「存在確認」「長さ」しか要らないのに `getAttachment` を呼び、返ってきた
`InputStream` を読みも閉じもしていなかった (= 呼ぶたびに 1 接続リーク + 添付の
フルダウンロード)。

| 経路 | 何をしていたか |
|---|---|
| `SolrUtil.getContentLength` | 索引対象の全文書で、文書に載っている長さを読むために本体を落としていた。**再索引のリークの正体** |
| `ExceptionServiceImpl` の contentStream 必須チェック | 存在確認だけのために本体を落としていた。content 必須型の作成・更新すべて |
| `ContentServiceImpl.getAttachmentRef` | javadoc が「without stream」と書きながら、ストリームを開く DAO を呼んでいた。`CompileServiceImpl` (ObjectData compile の高頻度経路) がこれを信用していた |
| `McpToolsProvider` | 非対応 MIME の早期 return が try-with-resources より前にあり、開いたストリームが漏れていた |

DAO に本物のメタデータ専用経路 (`getAttachmentRef`) を足し、上記を全部そちらに向けた。

**この 4 つでは足りなかった。** 修正版で全スイートを 1 周してなお**約 5,000 件**の
leak 警告が出た。個別に測った経路 (コンテンツ取得 / getObject / getChildren / query /
content 付き createDocument、GC 強制のうえ各 20 回) は全て delta 0 だったので
上記 4 経路は塞がっており、別の発生源があった。

**主因はもっと下にあった** (並行レビュー指摘)。`CouchAttachmentNode.convert()` が
それ自体で本体を開いていた — しかも SpringContext から connectorPool を引いて
**全リポジトリを順に試す**。そのうえで `AttachmentDaoDelegate.getAttachment` は
`convert()` が開いたストリーム ① を受け取った直後に `client.getAttachment` で ② を開き、
`setInputStream(②)` で**① を閉じずに捨てていた**。つまり:

- 添付読み出し 1 回につき、確実に 1 接続リーク
- しかも添付を**2 回**ダウンロードしていた
- 私が足した `getAttachmentRef` も `convert()` を呼んでいたので、
  「メタデータ専用」と称しながら本体を落としていた (自己矛盾)

対処: `CouchAttachmentNode.convertRef()` (メタデータのみ) を切り出し、
`getAttachmentRef` はそちらへ、`getAttachment` は `convertRef()` + 1 回だけ open に。

**残りのメタデータ専用呼び出しも塞いだ (2026-08-11 午後、Codex 指摘)。**
主因を潰した後もこの形の呼び出しが残っていた:

| 経路 | 何をしていたか |
|---|---|
| `ContentServiceImpl.createAttachmentAtomic` / `copyAttachmentAtomic` | null チェックのためだけに `getAttachment` (= 作成・コピーのたびに 1 本) |
| `RAGIndexingServiceImpl.getMimeType` | MIME type を読むために本体を開く。**索引した文書ごと**に 1 回 |
| `ArchiveServiceDelegate` | archive の mimeType / length を取るために本体を開く |
| `ArchiveDaoDelegate` (archive 作成 / restore) | SDK の `InputStream` を try-with-resources に入れておらず、例外経路と「id が取れなかった」経路で取り残していた |

さらに `createPreviewAtomic` に**別のリーク**があった (これは指摘外、修正中に発見)。
本体を開いてから `checkConvertible` を判定していたので、**レンディションを作らない
MIME type — つまりアップロードの大半 — で、開いたストリームを読まずに捨てていた**。
変換可否は要求側の mime type だけで決まるので、判定を open より前に出した。

**契約を実行時に固定した**: `AttachmentBodyOpenCountTest`。「ref は 1 回も開かない」
「full read はちょうど 1 回開く」を、返り値ではなく**クライアントの呼び出し回数**で
検証する (リークには返り値が無く、1 回開こうが 2 回開こうが使えるストリームは 1 本
返るので、観測できるのはそこだけ)。
なお**このテストは最初、壊れたコードを通した**。`convert()` は注入された pool ではなく
`SpringContext` から pool を引くため、context を入れずにモックすると 2 回目の open が
モックに届かない。意図的に旧実装へ戻して 4/4 通ることを確認してから、モック context を
入れて落ちることを確認した。

**再計測 (2026-08-11、修正版デプロイ + 全スイート 1 周):**

| | 修正前 | 修正後 |
|---|---|---|
| leak 警告 | 約 5,000 | **0** |
| テスト | 4,913 / 0 failures | 4,913 / 0 failures |

CLAUDE.md / RELEASE_NOTES の再索引時の接続数監視の記述は**残す**。本番規模
(数万〜数十万文書) での実測はまだ無く、「開発スタックのスイート 1 周で 0」を

### ✅ A3 (祖先チェーンの二重読み): 実測で見積りを確認し、traversal memo を実装した

台帳 A3 の「1 ノードあたり 2×(1+祖先数) 回の非キャッシュ CouchDB GET」は見積りだった。
**ACL の正しさの中枢をリリース直前に性能目的で触る前に、実際にいくら払っているかを
確定させた** (`tools/acl-probe/acl_propagation_read_cost.py`)。

| 鎖の深さ | ノード数 | 走査の読み取り | 1 ノードあたり |
|---|---|---|---|
| 2 | 22 (folder 2 + doc 20) | 128 | **5.8** |
| 6 | 26 (folder 6 + doc 20) | 324 | **12.5** |

深さ 2 → 6 で 1 ノードあたり 5.8 → 12.5 (2.2 倍)。モデルの予測は
2×(1+3)=8 → 2×(1+7)=16 の 2.0 倍なので、**祖先チェーンの走査が支配的であることが
確認できた**。

**モデルの 8 / 16 は上界**で、実測 (5.8 / 12.5) がそれを下回るのは想定内 — 走査の途中で
打ち切られる経路や、深さがノードごとに違う (鎖の途中の folder は末端の doc より祖先が
少ない) ため。**要点は絶対値の一致ではなく比例**で、そこは一致している。
「見積りが甘い」ではなく「見積りは上界として正しい」と読むこと。設計 §4.6 が許すのは snapshot 側の再利用だけ (revalidation の祖先再読は
fence の正しさの根拠) なので、**削減の上限はこの読み取りの約半分** = 台帳の「約 2 倍」と整合する。

**実装した (2026-08-12)。** 設計 §4.6 が許す範囲 — snapshot 側の祖先再利用だけ — に限定。

| 鎖の深さ | 実装前 | 実装後 |
|---|---|---|
| 2 (22 ノード) | 5.8 | **4.0** |
| 6 (26 ノード) | 12.5 | **7.5** |

アイドル対照は両方 0。深さ 6 で **40% 削減**、計画の目標 (約 7) どおり。

**設計**: `TraversalMemo` は traversal 全体の `id → 生の Document` の LRU。
接頭辞方式は採らない (「子の祖先鎖は親の鎖の接頭辞」は継承ブレークの途中停止と
relationship の 2 鎖で成り立たない)。role はメモせず呼び出し側が作り直す
(`Dependency.role` が `isAncestorOfSameChain` に効く)。不在もメモしない。
SELF read もメモしない。memo ヒットは `read()` を通らないので `authoritativeReads` を
増やさない。`revalidate` は一切触っていない。

**レビューで見つかった 2 件を修正**:

- **memo は O(サブツリー) に育ちうる — 私の主張が誤りだった。** SELF を除外しても、
  **訪問した folder は子を snapshot した瞬間に祖先になる**。root 直下に 5 万フォルダ
  (各 1 文書) なら約 5 万件の生 Document を traversal 中ずっと保持する。10 万ノードの
  伝播で OOM を起こせば、それは `catch (Exception)` に捕まらず伝播を中断する。
  **上限付き LRU に変更** (既定 2,048)。再利用されるのは全員が共有する上位の鎖なので
  hot に残り、増加の原因だった枝ごとの folder は 1 ヒットで evict される。
  退避のコストは再読であって誤答ではない。陰性対照: 上限を外すと 41 件保持で落ちる。
- **私が最初に書いたテストは壊れた実装を通した。** 10 leaf を 1 本の鎖にぶら下げる形
  では上の増加を再現できない。分岐木のテストを追加。`fingerprint` も
  `state` / `kind` / 端点 / **`localAces`** を落としていた (readers は localAces から
  計算されるので、正しい topology と誤った ACL の組が同じ指紋になっていた)。
  revalidation のテストは **memo ヒットを含まない** snapshot を検査していたので、
  兄弟を 2 つ目に snapshot して memo 由来の snapshot を検査するよう修正。

**自分で見つけた 2 件**:

- **PENDING をメモしない。** pending gate は `toDependency` で発火するので、memo への
  put はその前に済んでいた。mid-mutation の祖先をメモすると、CouchDB 側が settle した
  後もその traversal の残り全部が gate に当たり続ける (memo 前は再読して進めた)。
  正しさではなく**収束の後退**。
- **equal-epoch 分岐でも invalidate する。** あの分岐は「authoritative に再計算して
  収束させる」ためにあるので、memo があると同じ祖先から同じ readers が出て
  **再計算が再生になる**。

**invalidate は writer 側でテストされている** (レビュー指摘: 元のテストは
`invalidateAll()` を自分で呼んでいたので、production が呼び忘れても通った)。
`AclEpochIndexWriterIT` で 2 箇所とも陰性対照付きで固定した:

| 経路 | 外すとどうなるか (実測) |
|---|---|
| revalidate 拒否後の restart | **8 回の attempt を使い切って `AclEpochWriteContentionException`** — 予告どおりの非収束ループ |
| equal-epoch の authoritative 再計算 | memo が残るので同じ祖先から同じ readers が出る = 再計算が再生になる |

どちらも memo を primed にしてから祖先を動かすだけで再現でき、hook は要らない。

**残差だったもの → ✅ 2026-08-12 に決着**。上限 2,048 は当初「深さの上限より遥かに大きく、
メモリが有界になる」の 2 条件で決めた値で実測が無かった。カウンタを metrics に露出して測った
結果、**探索すべきチューニング値ではなく境界**と分かった: working set はノード数ではなく
**1 走査が触るフォルダ数**に比例し、深さ 12・フォルダ 84 の木で peak 86 / eviction 0
(上限の 4.2%)。約 2,000 フォルダを超えるまで eviction は起きない。詳細は §7 の A3 節。

観測用に `AclEffectiveEpochService` の authoritativeReads カウンタを追加し、
`GET /api/v1/admin/acl-epoch/quarantine` に出している (JVM ごと)。

**計測手法の失敗も記録しておく**: 最初は CouchDB の `database_reads` を使ったが
**成立しなかった**。サーバ全体のカウンタなのでアイドルの開発スタックでも毎秒 6 件ほど
動く一方、26 ノードの伝播は 300 秒の収束の中に 185 件が散るだけで、**ドリフト推定が
生の差分を上回り 1 ノードあたり −6.9 という値が出た**。「収束した」判定も一度も
成立せず、実際には打ち切りに達していた。呼び出し地点で数える方式に変えて解決した
(アイドル時のカウンタ増加 = 0 を対照として毎回出す)。

### ✅ F4 (view の 20 重 emit): 1 回に collapse した

`joinedDirectGroupsByGroupId` は入れ子グループの辺ごとに**同じ親文書を 20 回 emit**して
いた — キー `[parentGroupId, 0]` から `[parentGroupId, 19]` まで、**バイト単位で同一の行**。
第 2 要素は深さでも何でもなく、情報を持っていない。

**キーの形は変えていない。** scalar キーにするのが一見きれいだが、それは誤り:
consumer 2 箇所 (`checkIndirectGroup` と削除時の逆引き) は
`startkey`/`endkey` = `[id, 0]` で引いており、scalar キーはどちらにも一致せず
**失敗せずに 0 件を返す** — この view の複合キーが過去に起こしたのと同じ壊れ方になる。
index 0 だけ emit すれば既存クエリは全て無変更で正しいままなので、
**view と reader の間に着地順の依存が生まれない** (台帳が「逆順は不可」と書いていた懸念が消える)。
結果として **Java 側の変更はゼロ**。

**実測 (bedroom、文書 5,618)**:

| | 前 | 後 |
|---|---|---|
| view の行数 | 960 | **48** (ちょうど 1/20) |
| `_design/_repo` の index ファイル | 227.8 MB | **183.1 MB** |

**適用コスト**: map 関数を変えると CouchDB は**その design document の全 view**を再構築する。
既に適用済みの `Patch_StandardCmisViews` を編集しても既存環境には届かないので、
別パッチ `Patch_JoinedGroupsSingleEmit` にしてある (`Patch_ChildrenViewReduceCount` と同じ理由)。

**踏んだ落とし穴 — パッチ機構自身が巻き添えになる**: bedroom に適用した直後、
次のリポジトリの**パッチ履歴の照会が 60 秒でタイムアウトした**
(`Error getting patch history by name: JoinedGroupsSingleEmit ... _repo/patch - timeout`)。
履歴 view (`_repo/patch`) が**同じ design document に同居している**ため、
自分が起こした再構築に自分でぶつかっている。今回は続行してどちらのリポジトリにも適用され、
履歴も記録されたが、**再構築が 60 秒で終わらない規模ではこのエラーが常態**になる。
パッチは冪等 (map が既に単一 emit なら何もしない) なので再起動での再適用は安全だが、
**メンテ窓で適用し、適用後に `_design/_repo` の view を 1 本叩いて再構築を完了させてから
通常運用に戻すこと**。

*検証*: 入れ子グループ経由の付与と剥奪 (`rag_revocation_paths.py` の P2) が

### ✅ C8 (folder reindex が epoch fence を外す): batch 経路を fence した

台帳と `acl-epoch-reindex-defect.md` §5 は「epoch scanner / reconciliation キューが
自動で stamp し直すか」を未確認として残していた。「数分では戻らなかった」は
**「まだ戻っていないだけ」とも読める**ので、運用手順を「必須」と書くか「推奨」と
書くかが決まらなかった。

**コードから答えが出る。** `AclEpochScanScheduler` は 300 秒ごとに
`AclEpochFinalizationService.scan` を呼ぶが、その**全パスの選択条件は CouchDB 側の**
`aclEpochState` (PENDING_EPOCH / FINALIZED_NEEDS_RECONCILE) か `aclEpochMutationId` の
存在である。folder reindex が消すのは **Solr の `effective_acl_epoch`** であって
CouchDB 文書は触られない — 状態は settled のまま。**どのパスもその文書を選ばない。**

**実測 (2026-08-12、`tools/acl-probe/epoch_folder_reindex_recovery.py`)**:
子 236 件中 186 件が fenced のフォルダを reindex →

| 経過 | fenced |
|---|---|
| reindex 前 | 186 / 236 |
| reindex 後 5 秒 | **0 / 236** |
| **961 秒後 (スキャナ周期 300 秒 × 3 回超)** | **0 / 236** (期間中のピークも 0) |

**遅いのではなく構造的に戻らない。運用手順は「推奨」ではなく「必須」。**

**根本修正 (2026-08-12)**: `indexDocumentsBatch` を単発経路と同じ機構に通した —
realtime GET → authoritative な incarnation → ACL group は Solr が保持している値を保存
(reindex に新しい ACL 情報は無いので、ACL 軸の値を再主張しない) → 文書ごとの `_version_` CAS。
**別実装を足したのではなく、単発が使っているものをそのまま使っている**。

fence 判定が `SKIP_STALE` / `FAIL_CLOSED` を返した文書は batch から**外す**。
batch 全体が 409 で落ちた場合は既存の「個別索引へのフォールバック」がそのまま効き、
**並行していた fenced write が勝つ**という意図どおりの結果になる。

**当初「`verifyAndReindexMissing` が個別経路で拾う」と書いたが、これは誤りだった**
(レビュー指摘、確認済み)。あの検証パスが再索引するのは **Solr に存在しない文書だけ**で、

- `SKIP_STALE` の文書は Solr に (より新しい版が) **在る** → 触られない。
  もっともこれは**放置が正解**なので実害は無い。
- `FAIL_CLOSED` の文書も通常は Solr に**在る** → 触られない。
  つまり**黙って落ちていた**。

直した内容:

- 戻り値を `BatchOutcome` (written / skippedStale / fenceBlocked) にした。int 1 本では
  「正しく書かなかった」と「失敗した」を区別できず、**呼び出し側が引き算で失敗数を出して
  いたので、正しい no-op が再索引のエラー件数に入っていた**。
- `FAIL_CLOSED` は `enqueueReadersReconcile` で**reconciliation に渡す**
  (`applyContentFence` が ACL group の無い既存文書に対してやっているのと同じ)。
  検証パスが拾わない以上、外すだけでは失うことになるため。

**実測**: 修正前は 186/236 → 0/236 だった同じフォルダが **186/186 のまま**
(reindex は実際に走っている: status `completed`、186/186、開始・終了時刻あり)。
さらに 5,611 文書の**全再帰 reindex** 後も verdict は **`COMPLETE` / 0 unfenced**。

**残差**: `_rev` から generation が取れない文書 (`myGen == 0`) は従来どおり fail-open の
plain add。通常の CouchDB 文書では起きないが、fence の外にいる唯一の形。

先に入れていた緩和 (修正後も維持、ただし**文言は変えた**):

- **応答の `note`**。`OperationResponse` に `note` を足した。根本修正前は
  「このサブツリーは fence の外に出た、自動では戻らない、stamp を打ち直せ」だったが、
  修正後は**その文言が嘘になる**ので「**fence は保たれる、verdict で確認を**」に変更した。
  note 自体を消さないのは、`readers` が成否に関わらず再計算されるため
  **壊れた索引と健全な索引が外から見分けられず、verdict だけが区別する**から。
  `FolderReindexEpochWarningTest` も新しい契約に更新済み。
- **skill の手順のエンドポイントが 404 だった**。`.claude/skills/acl-epoch/SKILL.md` は
  `POST /api/v1/admin/acl-epoch/{repo}/stamp` / `GET .../verdict` と書いていたが、
  実在するのは **`POST` と `GET` の両方が `/api/v1/admin/acl-epoch/migration/{repo}`**
  (実測: 前者 2 つは 404、後者は 200)。SHIP-7 と同じ「手順どおり叩くと 404」。修正済み。

**作業中に踏んだ順序の罠**: 検証で root フォルダを reindex した直後に stamp を打ったら、
`remainingUnfenced` が 336 → 495 → 681 → 919 と**増えていった**。reindex が走りながら
fence を剥がし続けていたため。stamp API の note が言う「再索引の**後**に打て」は
このことで、**逆順の症状は「カウンタが戻っていく」**。reindex 完了を待って打ち直し、
`COMPLETE 0 / 5,619` を確認した。

### ✅ SX1 (2026-08-14): 同時書き込みで Solr クライアントが恒久デッドロックしていた

**これは v3.3.0 のリリース阻害要因だった。** 基準 2 (「アプリ全体の性能を落とさないこと」)
に対する不合格ではなく、**アプリが止まる**。回復手段は JVM 再起動のみ。

#### 症状

RAG 有効なリポジトリへ同時に書き込むと、**CMIS API 全体が返らなくなる**。
最初に気づいたのは「createDocument が 180 秒でタイムアウトする」という形で、
CPU は全コンテナ ≒ 0%、Solr は同等の deleteByQuery を curl から 0.02 秒で返す状態だった。
つまり**忙しいのではなく止まっている**。

#### 実測 (2026-08-14)

`jcmd 1 Thread.dump_to_file -overwrite -format=json` で採取
(**`jstack` は仮想スレッドを表示しないので使えない**)。

| 観測 | 値 |
|---|---|
| `HttpJdkSolrClient-2-thread-*` が `PipedInputStream.awaitSpace` | **4/4 スレッド全部** |
| その上のフレーム | `FastOutputStream.flush` ← `JavaBinCodec.writeFloat` (RAG の埋め込みベクトル) |
| `HttpClientImpl.send` で応答待ち | 42 スレッド |
| `RAGIndexingServiceImpl.indexToSolr` の per-ragId ストライプロック待ち | 25 スレッド |
| 数分空けた 2 つのダンプの差 | **なし** (75 スレッド、出入り 0、フレーム同一) |
| 30 秒のリクエストタイムアウト | **この状態を解かない** |

> タイムアウトについて言えるのは「設定してあるのに解けなかった」という観測だけで、
> **なぜ解けなかったかは特定していない**。当初ここに「応答を待っていないから」と書いたが、
> 同じ表に「42 スレッドが応答待ち」と記録している以上それは自己矛盾で、誤りだった
> (Codex レビュー指摘)。

#### 真因 (SolrJ 10.0.0 の bytecode で確認)

`withExecutor` を渡さないと、SolrJ はコンストラクタで

```
MDCAwareThreadPoolExecutor(core=4, max=256, 60s, LinkedBlockingQueue(1024))
```

を作り、**同じ実体**を `HttpClient.Builder.executor(...)` にも渡す。ここに 2 つの事実が重なる。

1. `ThreadPoolExecutor` は**キューが満杯になるまで core を超えてスレッドを増やさない**。
   キュー 1024 深 × core 4 なので、1000 件溜まるまでは**実質 4 スレッド固定**。
2. 1 リクエストがこのプールを **2 枠**使う。SolrJ がボディを `PipedOutputStream` へ書く側と、
   JDK HttpClient がパイプを読む側の**両方**が同じプールで走る。

したがって同時 4 本でボディがパイプバッファ (既定 1 KiB) を超えると、4 枠が全部書き手になり、
読み手のタスクはキューの中で永久に順番が来ない。**プールも増えないので自力では解けない。**

RAG が最初に踏むのは、block-join 文書が親と全チャンクの float ベクトルを載せるため
**必ず 1 KiB を超える**から。これは確率の差であって種類の差ではないので、
CMIS 側のクライアントも同じ修正を入れてある。

Nemaki 側の executor は CallerRunsPolicy なので、この停止は CMIS リクエストスレッドまで
逆流し、API 全体を巻き込む。

#### 修正

`jp.aegif.nemaki.util.SolrHttpExecutor` を新設し、
**両方**の生成箇所 (`SolrUtil.getSolrClient`、`SolrClientProvider.createSolrClient`) で
`withExecutor(...)` に渡す。中身は
`ThreadPoolExecutor(0, Integer.MAX_VALUE, 60s, SynchronousQueue)`。

- **上限なし**にするのは、互いを待つタスクを載せるプールは有界にできないから。
  N 本で頭打ちなら同時 N リクエストで必ず止まる。

  > **ただし露出がゼロになるわけではなく、形が変わるだけ**。同時 Solr リクエスト数を
  > 上流が固定的に縛ってはいない — Tomcat は無制限の仮想スレッドでリクエストを捌き、
  > `asyncSolrExecutor` は CallerRunsPolicy (拒否ではなく呼び出し元に実行させる
  > バックプレッシャー) で、クエリと `forceSync` 経路はそもそもこのプールを通らない。
  > Solr 自体が停滞すれば in-flight が積み上がり、その分だけプラットフォームスレッドが
  > 増える。**「同時 4 本で確定デッドロック」を「長時間の下流停滞でスレッド枯渇」に
  > 交換した**形で、確実に良くはなっているが無償ではない (Codex レビュー指摘)。
  > そのため `SolrHttpExecutor` は 64 / 128 / 256 … とプールが育つたびに WARN を出し、
  > 障害になる前にログで見えるようにしてある。

- **プラットフォームスレッド**にする理由は「仮想スレッドだとデッドロックするから」ではない。
  Temurin 21.0.10 で確認したところ、`PipedInputStream.receive` は `synchronized` だが
  `awaitSpace` 自体は `synchronized` ではなく、`Object.wait(long)` は
  `jdk.internal.misc.Blocker` を通るので **ForkJoinPool がキャリアを補償**する。
  つまり仮想スレッド 4 本なら**上の停止は再現しない**。
  残る理由は**補償にも上限がある**こと (既定 `max(parallelism, 256)`) で、
  仮想スレッドは崖を 4 から数百に動かすだけ。ここで欲しいのは
  「OS がスレッドを作れなくなるまで読み手が必ず走れる」性質なので、
  プラットフォームスレッドを採る。**当初「JDK 21 では pin するから」と書いたのは誤り**
  (Codex レビュー指摘)。

- executor を渡すと SolrJ は `shutdownExecutor=false` にするので、
  **後始末は呼び出し側の責任**。`SolrUtil.destroy()` と `SolrClientProvider.cleanup()` の
  両方でクライアントを閉じた**後に** shutdown する。
  破棄は**生成と同じロックの下で client と executor を対のまま外し、以後の生成を拒否**する。
  そうしないと破棄と遅延生成が交差し、「破棄側が**新しい方の** executor を落として
  古い方を漏らす」= 生きているクライアントの輸送路が死ぬ (Codex レビュー指摘)。

  生成側も **`build()` が成功してからフィールドに入れる**。先に入れると、失敗した試行の
  executor が閉じ手のないまま残り、次の試行が上書きして漏らす (プールが無上限なので
  漏れも無上限)。**ただしこの経路は実質到達しない** — `HttpJdkSolrClient.Builder.build()`
  は URL を検証しないことを実測した (`null` と空文字を含む 8 通りの不正 URL が全部
  build に成功する)。したがって**テストは無い**。防御として意図的に置いているので、
  「カバーされていないから」で消さないこと。

#### 修正後の実測 (同一スタック、`tools/acl-probe/solr_client_executor_deadlock_probe.py`)

| | 修正前 | 修正後 |
|---|---|---|
| 同時 12 本の createDocument | 1 本も返らない (180s+) | **12/12 が完走** (2 回測って 2.2 秒 / 1.9 秒) |
| `solr-http-cmis` スレッド | — | 6 (**旧上限 4 を超えて増えている**) |
| `solr-http-rag` スレッド | — | 5 (同上) |
| `HttpJdkSolrClient` (SolrJ 既定プール) | 4 (全部 awaitSpace) | **0** |
| `awaitSpace` のスレッド | 4 | **0** |

RAG 側は遅延生成なので、RAG 索引が実際に走ったことを Solr の doc_type 付き文書数が
2,847 → 2,951 に増えたことで確認した上での値。

#### 回帰テスト (2 段構え)

**① 仕組み** — `SolrHttpExecutorStarvationTest` が同じ形の実験を単体で再現する。
**負の対照**として SolrJ の設定そのもの (core=4 / queue=1024) で同一ワークロードが
5 秒待っても完了しないことを assert している。これが無いと、壊れたままでも通ってしまう。

writer を全部投入してから reader を投入する順序は意図的で、実測された状態
(全枠が書き手) を写している。writer/reader を交互に出すと FIFO で対になって
枯渇したプールでも解けてしまい、テストが何も証明しなくなる。

**② 配線** — `SolrClientWiringTest` が**本番の 2 箇所を実際に構築**し、
クライアントが握っている executor を reflection で読み出して
「上限なし + `SynchronousQueue`」であることを assert する。

①だけでは `withExecutor(...)` を消しても全部 green のままで、
**リリース阻害要因が戻っていても気づけない** (Codex レビュー指摘)。
破棄後に再生成されないことも同じファイルで固定している。

②が本当に判別することは**実際に `withExecutor(...)` を外して確認**した
(`expected: <2147483647> but was: <256>` で落ちる)。テストが通ることではなく、
**壊したときに落ちること**を見ている。

#### 落とし穴として残すこと

**新しく `SolrClient` を作るときは必ず `SolrHttpExecutor.create()` を
`withExecutor` に渡すこと。** 渡し忘れても単発の書き込みでは症状が出ず、
同時実行になって初めて**恒久停止**する。

テスト fixture も例外ではない。`AclEpochIndexWriterIT` は SolrJ 既定のまま残っており、
現状は直列なので踏んでいないが、並列化した瞬間に同じ罠に落ちるので揃えた
(Codex レビュー指摘)。

| **調べる順** | ~~② 未コミットのバッチを検索で検証して 1 件ずつに落ちる~~ → **棄却** (事実だが A/B で速くならず) / ~~③ C8 の realtime GET が文書ごとの往復を増やしている~~ → **棄却** (索引フェーズの 9.5% しか無い、2026-08-14) / ~~① 添付の二重往復 (T3)~~ → **除去した** (2026-08-14、CouchDB 読みが 11,360 → 10,045 回)。**残っているのは ④ ehcache の working set 超過 ⑤ CouchDB の b-tree / ディスクキャッシュ**。2026-08-14 の内訳で **約 88% が CouchDB 読み**と分かったので ④⑤ が本命 |

**リリースとの関係**: 製品の正しさには影響しない。ただし**アップグレード手順の所要時間**として
RELEASE_NOTES に明記済み。数十万規模の顧客には分割実行を案内する必要がある。

#### 実測で分かったこと (2026-08-13)

**調べる順の ② (未コミットのバッチを検索クエリで検証 → 全件が 1 件ずつ再索引) は
主因ではなかった。** 同一規模 (5,615) の A/B で **77.2s → 84.0s**。二重索引付けは実在した
(`silentDropCount` 5,614 → 0) が速度は変わらない。**この仮説は棄却**。修正自体は
正しさのために残す (進捗 API が「5,614 件が黙って落ちた」と偽の警告を出していたため)。

**時間の 9 割は索引フェーズにある** (計測を仕込んで実測):

| フェーズ | 時間 | 割合 |
|---|---|---|
| 走査 (フォルダ木) | 779 ms | 1.7% |
| **索引 (文書構築 + CouchDB 読み + Solr 書き)** | **40,610 ms** | **90.7%** |
| 検証 | 160 ms | 0.4% |

**CouchDB 側のベースライン** (5,615 オブジェクト、直接計測):

| 操作 | median | p95 |
|---|---|---|
| content 文書 GET | **7.3 ms** | 34.6 ms |
| 添付メタデータ GET | 5.8 ms | 19.4 ms |
| 添付本体 GET | 42.9 ms | 86.9 ms |

**手がかり**: この規模の索引フェーズは **1 文書あたり 7.2 ms** (40.6s / 5,615) で、
**CouchDB の文書 GET 1 回分とほぼ同じ**。26,416 では 97 ms/文書 (10.3/s) で **13 倍**。
1 文書あたりの往復回数が増えているのでなければ、**1 回の往復が遅くなっている**。

**次にやること**: 規模を上げて同じ 3 つの GET を測り直す。伸びていれば CouchDB / OS の
キャッシュ常駐性 (環境要因)、横ばいなら Solr 側かアプリ側で、そのとき `indexingMs` を
CouchDB 読みと Solr 往復にさらに割る。**status API が内訳 (`enumerationMs` /
`indexingMs` / `verificationMs`) を返す**ので、次の大規模実行は推測せずに済む。

**ばらつきに注意**: 同じ 5,615 で 44.8s / 77.2s / 84.0s と大きく振れる。
**単発の比較で「速くなった」と言わないこと。**

**2 点目を取ったら話が複雑になった**: canopy (165 オブジェクト、うち 152 が添付持ち) は
**1 文書 29.2 ms** で、bedroom (5,615) の 7.2 ms より**遅い**。規模が小さいのに遅いので
「大きいほど遅い」では説明がつかない。効いていそうなのは**添付を持つ文書の割合** —
添付本体 GET は 43〜47 ms と他の 6 倍以上かかり、canopy は全文書が添付持ち、bedroom は
フォルダや添付なし文書を多く含む。

つまり「1 文書あたりのコスト」を規模だけで比較してはいけない。**次の計測では
添付持ちの割合を揃える**こと (`bulk_seed_documents.py` は全件添付付きで作るので、
その fixture で規模だけを変えれば揃う)。

小規模では**未計上が半分を占める** (canopy で 10.1s 中 5.1s)。`clearIndex` /
`forceCommitAndWait` / 健全性チェック / RAG トリガという固定費で、文書数が少ないほど
相対的に大きい。規模の比較は固定費を差し引いてから。

#### 添付割合を揃えた 2 点 (2026-08-13) — 規模だけでは説明がつかない

| | オブジェクト数 | 添付割合 | 1 文書あたりの索引時間 |
|---|---|---|---|
| canopy | 165 | 92% | 29.2 ms |
| canopy | 1,492 | 100% | 28.0 ms |

**9 倍の規模差で 1 文書あたりのコストはほぼ横ばい**。この範囲では「規模そのもの」では
説明がつかず、bedroom 側の落ち込み (5,615 混在 = 7.2 ms/文書 → 3,000 件の全添付文書を
足した 8,646 = 20.0 ms/文書) は**添付割合の変化**で説明できる。

#### 3 点目 (約 4,500) は取れていない — 原因は SX1 だった

投入を 8 並列で走らせたところ 0.07 文書/秒まで落ちて止まった。これが上の
**SX1 (Solr クライアントの恒久デッドロック)** の初回観測で、投入は完了していない。
したがって**この系列は 2 点で止まっている**。

**併せて注意**: SX1 は同時実行数で発火するので、2026-08-14 より前に取った RX1 の数値は
デッドロックの影響を受けていた可能性を否定できない。RX1 の結論を出す前に、
**修正後のビルドで取り直す**こと。

#### 索引フェーズの内訳を割った (2026-08-14、SX1 修正後のビルド)

台帳が「割ってから推測しろ」と書いていた作業。`indexDocumentsBatch` に 4 つの計測点を入れ、
status API と完了ログに出るようにした (`solrRtgMs` / `incarnationMs` / `buildDocMs` /
`solrAddMs`)。**計測だけで制御フローは変えていない。**

bedroom 5,615 オブジェクト、索引フェーズ 40,715ms (全体の 89.5%) の内訳:

| 内訳 | 索引フェーズ比 | 1 文書あたり |
|---|---|---|
| **文書構築 (添付メタデータ + 本体 + Tika)** | **63.6%** | 4.61 ms |
| **content incarnation の解決 (CouchDB)** | **24.3%** | 1.76 ms |
| Solr realtime GET (**文書ごと**) | 9.5% | 0.69 ms |
| Solr add (**バッチごと**) | 2.2% | 0.16 ms |
| 未計上 (ループのオーバーヘッド) | 0.4% | — |

**分かったこと 3 つ**

1. **「調べる順 ③」は主因ではない。** C8 で自分たちが入れた文書ごとの realtime GET は
   **9.5% / 0.69ms** しかない。実在はするが支配項ではないので、**自分たちで入れた退行という
   線は消える**。
2. **Solr 側は主因ではない。** realtime GET と batch add を足しても 11.7%。
   規模依存の劣化が Solr の書き込みで説明できる余地はほとんど無い。
3. **約 88% が CouchDB 読み** (文書構築 63.6% + incarnation 24.3%)。
   **RX1 の規模依存性がどこかにあるとすれば、ほぼ確実にここ**。Codex の第 1 候補
   (CouchDB / OS のページキャッシュ常駐性) と整合し、他の候補より優先度が高い。

#### 新しい手がかり: incarnation の解決が文書ごとの丸ごと GET になっている

`ContentIncarnation.resolve` は**キャッシュ無しで毎回 `store.read()`** を呼ぶ
(`ContentIncarnation.java:89`)。既に値が入っていれば即返すが、**読みは既に発生している**。
これが索引フェーズの **24.3%**。

しかも**呼び出し側は既に `Content` を持っている**。`Content` は `contentIncarnation` を
verbatim で保持する (`Content.java:76`、「assign-once の唯一の例外」)。

**ただし安全に外せるとは断定できない。** `resolve` の再読みは**権威的な現在値**を取るためで、
列挙時点のスナップショットを使うと、列挙と索引の間に削除・再作成が起きた場合に
**フェンスが検出すべき差異を見逃す**。ここはフェンスの正しさの入力なので、
性能だけを理由に触る話ではない。**設計判断が要る。**

#### 訂正: 規模別の CouchDB レイテンシは今も未測定

上の表の「5.8 / 19.4」「42.9 / 86.9」を規模別の 2 点と読んだが、**median と p95 の 2 列**で、
規模は 5,615 の 1 点だけ。台詞どおり「次にやること」のまま残っている。
**規模を変えて同じ 3 つの GET を測るのは、依然として未実施。**

#### 過去の数値と直接比べないこと

同じ 5,615 で、記録された content 文書 GET は 7.3ms、2026-08-14 の再測定は **3.81ms**。
レートも 123.5 文書/秒 (履歴の 70〜125 の上端)。**機械の負荷が違うだけ**で、
コードの改善ではない。レビュー指摘のとおり、**公表する所要時間を確定したいときだけ
測り直す**のが正しく、過去の値との差分を改善として読んではいけない。

#### 未消化の手がかり: 抽出のたびにスレッドプールを作っている

`TextExtractionServiceImpl` は Tika の parse にタイムアウトを掛けるため、
**1 回の抽出ごとに `Executors.newSingleThreadExecutor()` を新規に作っている**
(`TextExtractionServiceImpl.java` の parse 呼び出し直前)。
全再索引は全文書で 1 回ずつここを通るので、文書数ぶんのスレッド生成・破棄が乗る。

規模とともに**単調に悪化する**形ではないので RX1 の主因の候補としては弱いが、
1 文書あたりの固定費としては実在する。上の 2 点系列 (28〜29 ms/文書) の内訳を割るときに
最初に外して測るべき候補。**未測定**。

### ✅ V1 (2026-08-12): keyed view クエリが view 全体を取っていた — 書き込みが O(リポジトリ)

F3 の規模を上げようとして「createDocument が並列化しない」ことに気づき、追ったら
**台帳に無かった別の欠陥**が出た。実装済み、実測済み。

#### 症状から原因まで

まず**症状**: 16 並列でも **約 1.2 文書/秒**、単発 createDocument は 1.05〜1.35 秒。
RAG を止めても、親フォルダを 16 個に分散させても変わらない。つまり親フォルダの
書き込みロックでも TEI でもない。

推測を捨てて**負荷中のスレッドダンプ**を取った (`create_throughput_probe.py`)。
ここで最初に**道具が嘘をついた**: `jstack` は仮想スレッドを表示しないので、16 件の
create が進行中なのに「リクエストスレッド 2 本」と出る。**「何も起きていない」ではなく
「見えていない」**。`jcmd Thread.dump_to_file -format=json` に変えたら答えが出た:

```
34 スレッド中 32 が CloudantClientWrapper.queryView で park
  ObjectServiceImpl.createDocument
    → ExceptionServiceImpl.nameConstraintViolation      (CMIS の名前一意性)
      → ContentDaoServiceImpl.getChildrenNames
        → view childrenNames
```

次の仮説「CouchDB の view インデックス更新待ち」も**外した**。`update=false` との対比
(`view_index_wait_probe.py`) で、負荷中も 10〜20ms・`updates_pending=0`。比 1 倍。

正解は `CloudantClientWrapper.queryView(designDoc, viewName, key[, forceUpdate])` が
**key を CouchDB に送っていなかった**こと。view 全体を `include_docs=true` で取得し、
**Java 側で key を突き合わせて**いた。答えは正しいので、症状は**コストだけ**。しかも
そのコストは**答えの大きさではなくリポジトリの大きさに比例**する。

| | 行数 | バイト | 時間 |
|---|---|---|---|
| 実際に取っていたもの (view 全体) | 2,722 | 2.6 MB | 0.90s |
| 必要だったもの (key 付き) | 271 | 0.28 MB | 0.095s |

**同じ欠陥は typed overload では既に直っていた** (`queryView(..., Class<T>)` に
"CRITICAL FIX: Add key to the server-side query instead of client-side filtering" が在る)。
untyped の方に適用し忘れていただけ。

#### 効果 (実測)

| | 16 並列の 1 件あたり | スループット | TCK AllTest |
|---|---|---|---|
| 修正前 | median **11.85s** | **1.2〜1.4/s** | 573.0s |
| 修正後 | median **0.44s** | **6.5/s** (2,000 件 309.5s) | 310.3s |

スループットは同じ道具 (`bulk_seed_documents.py`) の同じ条件で **5.4 倍**。
TCK 自体も**ほぼ半分の時間**になった。

#### 併せて直した 2 点目: reduce view に include_docs を付けていた

この overload は `include_docs=true` を**無条件**で付けていたが、**呼び出し側 5 箇所は
全て `row.getValue()` しか読まない** (view 側が doc を value に emit している)。
取得して捨てていた。

さらに **CouchDB は reduce view への `include_docs` を拒否する**:

```
query_parse_error: `include_docs` is invalid for reduce
```

`countByObjectType` は reduce 付き。したがって `existContent` は**毎回例外**を投げ、
catch が **false** を返していた。include_docs を送らないことでこれも直る。

**ただし波及範囲はここで止まる (実機で確認した)。** `existContent` の唯一の消費者
`constraintObjectsStillExist` は**どこからも呼ばれていない**。実際の `deleteType` は
`TypeManagerImpl.checkTypeDependencies` を通り、その `checkTypeHasInstances` は
**未実装のスタブで常に false**。よって **「インスタンスが在るタイプの削除が通る」
という CMIS 適合ギャップは残っている** — 修正をデプロイした状態で
`type_delete_constraint_probe.py` を走らせ、200 が返ることを確認済み。
塞ぐにはスタブを `existContent` に配線する必要があり、それは別の挙動変更なので
**本修正には含めない** (下記 V2)。

#### 影響を受けていた呼び出し (untyped overload、key 付き)

| 呼び出し | view | 行数 (bedroom) | 経路 |
|---|---|---|---|
| `getChildrenNames` | `childrenNames` | 2,527 | **createDocument の名前一意性 (ホットパス)** |
| `getUserItemById` | `userItemsById` | 112 | 認証 (`AuthResource` / `ApiKeyResource`) |
| `existContent` | `countByObjectType` | reduce | 上記のとおり常に失敗していた |
| `getWebAuthnCredentialsBy{UserId,CredentialId}` | 同名 | 0 | WebAuthn 登録・検証 |

`userItemsById` は bedroom では 112 行だが、**ユーザ数に比例**する。数万ユーザの
環境では**ログインのたびに全ユーザ文書を転送**していたことになる。

#### 落とし穴として残すこと

- **`jstack` は仮想スレッドを見せない。** Tomcat のリクエストは VT で走るので、
  `jstack` は「リクエストスレッドがほぼ居ない」と出す。`jcmd Thread.dump_to_file
  -format=json` を使うこと。
- **答えが正しい性能欠陥はテストで捕まらない。** client-side filtering は正しい行を
  返すので、戻り値へのアサーションでは絶対に落ちない。回帰テスト
  (`CloudantClientWrapperViewKeyTest`) は **CouchDB に送った `PostViewOptions` の側**を
  検証している。`builder.key(key)` を消すと 2 件落ちることを確認済み。

### ✅ V2: インスタンスが在るタイプの削除が通っていた (2026-08-12 に修正)

上記の調査で判明。`deleteType` は CMIS 上、当該タイプのインスタンスが残っていれば
`CmisConstraintException` を投げなければならないが、**通ってしまう**。

- `TypeManagerImpl.checkTypeHasInstances` が未実装のスタブ (常に false)
- 本来の番人 `ExceptionServiceImpl.constraintObjectsStillExist` は呼び出し元が無い
- 依存する `existContent` は V1 で直し、さらに **null 分岐も入れた** (下記) ので、
  **配線するだけで塞げる状態になった**

**配線前に必要だった修正 (レビュー指摘、2026-08-12 に対応済み)**: V1 後、キーが
一致しない `queryView` は契約どおり `null` を返す。`existContent` はそれを直に
参照していたため、**インスタンス 0 件という最も普通の入力で NPE → catch → false**
という経路を通っていた。答えは偶然正しいが毎回 ERROR ログが出るうえ、
「配線するだけ」で塞ごうとすると **null 分岐が無いまま**本番経路に載ることになる。
`getChildrenNames` と同じ形の null ガードを入れ、回帰テストは
**ERROR ログが 0 件であること**を検証している (戻り値はどちらでも false なので
戻り値へのアサーションでは落ちない)。

**修正 (2026-08-12)**。配線は `ContentService` ではなく **`ContentDaoService`** に対して行った
— `contentService` は既に `TypeManager` を参照しており、逆向きに注入すると
`lazy-init="false"` + `init-method` の bean を巻き込む Spring の循環になる。
`existContent` は DAO のインタフェースにある。

**未配線なら「拒否」にした (fail-closed)**。DAO が無いときに false を返すと、V2 が塞いだ
穴が静かに戻る。タイプ削除は稀な管理操作なので、設定不良で目立って失敗する方が安い。

**`tck:` 接頭辞の免除は入れていない**。`constraintObjectsStillExist` (呼び出し元無し) には
在るが、これを持ち込むと **タイプ名を `tck:...` にした実運用リポジトリが黙って保護を
失う**。クライアントが名前の付け方で回避できる規則は制約ではない。

**免除無しで CMIS TCK 38 テストは green**。つまりあの免除は**そもそも要らなかった** —
TCK は自分が作ったオブジェクトを削除してからタイプを消している。「TCK を通すために
入れた例外」に見えるものが、実は不要だったという確認になる。順序として、
免除を入れずに配線して TCK を回す、を先にやったから分かったこと。

#### 併せて出た欠陥: CMIS の拒否が 500 になっていた

配線した直後、ガードは正しく発火したのに応答は **500 runtime** だった。
`RepositoryServiceImpl.deleteType` の `catch (Exception)` が **CMIS 例外まで**
`CmisRuntimeException` で包み直しており、バインディングが状態コードを決める根拠を
壊していた。`TypeManagerImpl` 側は `CmisConstraintException` を包まず再送出するよう
既に配慮していたが、**その 1 段上で台無しになっていた** — 1 箇所で気を付けても足りない
形。`CmisBaseException` を素通しにして解決。

回帰テスト `DeleteTypeConstraintPropagationTest` は**同一インスタンスが出てくること**を
検証する。新しい `CmisConstraintException` で包み直しても状態コードは保たれるが、
ガードが組み立てたメッセージ (タイプ名と理由) は失われ、クラスだけの検証では気づけない。
陰性対照も確認済み。

**実測 (デプロイ後)**: 空のタイプ削除は 200、インスタンスが在るタイプは **409**。
`tools/acl-probe/type_delete_constraint_probe.py` が exit 0 になった。

**利用者への影響**: 今まで通っていた削除が 409 になる **挙動変更**。RELEASE_NOTES に記載。

### ✅ F2 (グループ / ユーザ削除の全件列挙): 逆引き view に切替

`removeGroupFromAllNestedGroups` は「このグループを入れ子に持つのは誰か」を知るために
**全グループを include_docs 付きで取得して 1 件ずつ走査**していた。逆引き view
`joinedDirectGroupsByGroupId` は**既に存在し、読み取り経路は既に使っている**のに、
書き込み側だけが使っていなかった。

**ユーザ削除も同型だった** (`removeUserFromAllGroups`、view は `joinedDirectGroupsByUserId`)。
F2 の台帳項目はグループ削除しか挙げていないが、修正中に見つけたので同時に直した
— 片方だけ直すのは今回のレビューで繰り返し指摘されている形なので。

### ✅ R1 (RAG 経路の剥奪整合): 実測して基準 4 に数値を入れた

台帳は「基準 4 の判定はこの領域を未評価のまま含む」としており、測定資産も無かった。
`tools/acl-probe/rag_revocation_seed.py` を作って実測した (RAG 有効環境:
nb33 + TEI ARM64、bedroom、非 admin ユーザ)。

**⚠️ 初版 (2026-08-11 午前) の数値は破棄した。** レビューで指摘され、確認した:
`/rag/search` は **ユーザ単位 2 req/s・burst 5** のレート制限下にある
(`RAGSearchResource.checkRateLimit` / `RAGConfig` 既定値) のに、初版プローブは
250 ms 間隔で叩き、かつ **200 以外をすべて「0 件」に潰していた**。つまり
**429 が「剥奪済み」と読めていた**。しかも陽性対照のループでバーストを使い切った
直後に剥奪を測る作りなので、これは理論上の懸念ではない — 初版の検索側の値
(0.077 s / 0.066 s) はレート制限を測っていた可能性が高い。**seed 側 (`/rag/similar`)
はレート制限対象外なので、その 2 値だけは汚染されていない**が、同じ表に並べる意味が
無いので全面的に測り直した。

現行プローブは allowed / denied / **unknown** の 3 値で、429・5xx・通信失敗を
unknown として扱い、判定せず backoff して同じ質問をやり直す。429 の遭遇回数を
要約に出すので、値がレート制限律速かどうかを読者が判断できる。

**実測 (2026-08-11 午後、修正版 WAR をデプロイして 2 回、文書 3 件、対照付き):**

| 測定 | 値 (2 回) |
|---|---|
| T1 ACE 剥奪 → seed (`/rag/similar`) 拒否 | **0.183 / 0.191 s** |
| T1 ACE 剥奪 → 検索 (`/rag/search`) から消失 | **0.308 / 0.261 s** |
| T2 グループ membership 剥奪 → seed 拒否 | **0.090 / 0.081 s** |
| T2 グループ membership 剥奪 → 検索から消失 | **0.168 / 0.150 s** |
| T4 folder reindex 後も剥奪維持 (60 秒観察) | **維持 (2 回とも)** |
| 参考: ACL 書き込み自体 | 0.118 / 0.124 s |
| 参考: RAG 索引完了まで | 0.332 / 0.177 s |
| 参考: 再付与 → seed 可 | 0.096 s |
| レート制限に当たった回数 | **0 回** (= 上の値はレート制限律速ではない) |

初版より値が大きいのは劣化ではなく計測の是正で、理由は 2 つ:
**(a) 計時を ACL 書き込みリクエストの発行「前」から始めた** (利用者が待つ時間には
書き込み自体が含まれる。初版は書き込み後から測っており、その分を黙って落としていた)、
**(b) 検索のポーリング間隔をレート制限に合わせて 0.55 s にした** ので検索側の
分解能がその値で下限を持つ。したがって検索の 2 値は**上限**として読むこと。

対照 (これが取れない回は全数値無効。**現行プローブは print ではなく raise する**):

- 陽性: 剥奪前に UIN が seed 可 = allowed、検索で 3/3 可視 = 2.1 / 3.2 s
- 陰性: 無関係ユーザ UOUT は seed denied / 検索 0 件 (最初から最後まで)
- 観測用 admin ACE は最後まで seed allowed (= fixture が消えたのではないことの証明)
- T4 の reindex は status の `startTime` が**変化**し、かつ `indexedCount == 3` を要求
  (status は「最後の reindex」を返すので、"completed" だけでは前回の結果を
  自分の成果と読み違える)

**読み: 剥奪は索引の追従を待たない。** 数値が 0.1 秒未満なのは、seed も検索結果も
`VectorSearchServiceImpl` の live-ACL ゲート (`buildReaderTokenSet` +
`isReadableByTokens` / `filterByLiveAcl`) で落ちるためで、索引の `readers` fq は
最適化に過ぎない。**上限は「索引伝播の時間」ではなく「1 リクエストの処理時間」**。
group membership 経由 (T2) でも同じで、principal 世代とキャッシュを挟んでも
0.1 秒台に収まっている。

**R1 が残していた懸念は全て解消。**

| R1 の懸念 | 現在 |
|---|---|
| seed の live-ACL ゲートは実在するが数値が無い | ✅ 実測 (上表) |
| RAG folder reindex 経路は未確認 | ✅ T4 で確認 (reindex 後も剥奪維持) |
| 経路がグループ ACE の 1 本しか測れていない | ✅ anyone / ネストグループ / move / admin 降格 / PWC / cross-replica を追加確認 |
| 判定が PermissionServiceImpl ではなくトークン交差で、ownership / PWC の意味論差が残る | ✅ ownership が効くのは PWC のみと特定し、除外を実測 (E1–E4、陰性対照付き) |
| (当初「単一レプリカでは測れない」としていた) cross-replica | ✅ 2 レプリカを立てて実測 (X1–X3)。ACE 剥奪 0.25–1.33 s / グループ剥奪 5.4–8.4 s |

**測定中に見つけた別件 (✅ 修正済み。ただし直すのに 2 回間違えた)**:
`/rag/search` の `folderId` が**スコープとして機能していなかった**。

加重検索は 2 本の KNN を走らせる。**content 側は chunk** (`doc_type:chunk`)、
**property 側は親文書** (`doc_type:document`) で、索引しているフィールドが違う:

```
親文書  : id="rag:<objectId>"  object_id="<objectId>"  parent_id="<folderId>"
チャンク: id="<objectId>_chunk_N"  parent_document_id="<objectId>"   ← フォルダ情報なし
```

**1 本のフィルタを両方に載せると必ずどちらかが間違う。しかも Solr はどちらの間違いも
200 で答える。**

| 版 | 何が起きたか | 実測 |
|---|---|---|
| 元 | `{!parent which='doc_type:document'}parent_id:X` (to-parent Block Join)。内側クエリは**子**に当たるので、チャンクを親のフィールドで探していた | 2 件のフォルダで 1 件しか返らず、API 経由では**他フォルダの文書**が返った |
| 1 回目の修正 | 素の `parent_id:X` を両方に。property 側は正しくなったが chunk 側が全滅 | フォルダ内 2 文書 = 1,144 チャンクのうち、素のフィルタが当たったのは **0 件**。join なら 1,144 件 |
| 現行 | property 側は `parent_id:X`、chunk 側は `{!join from=object_id to=parent_document_id}(doc_type:document AND parent_id:X)` | 下記 |

join を `id` ではなく `object_id` から張るのは、親の `id` に `rag:` 接頭辞が付く一方で
チャンクの `parent_document_id` は素の objectId だから。`id` で張ると 0 件になる。

**join の内側クエリにも `repository_id` を入れる**。外側のフィルタ
(`doc_type:chunk` / `repository_id` / ACL) が縛るのは**返ってくるチャンク**であって、
join が `object_id` を**拾ってくる親文書**ではない。入れないと、同じ folder id を持つ
別リポジトリの親文書の object_id が join 集合に混ざる。object id は CouchDB の uuid
なので自然衝突は考えにくいが、**import/export はリポジトリ間で id を持ち回れる**ので、
「衝突しないはず」が根拠にならない場面が実在する。実測: 内側を `repository_id:"bedroom"`
にすると 1,144 件、`"canopy"` にすると 0 件。

#### join のコストはフォルダ内文書数に対して増えない (`rag_folder_join_scale.py`)

レビューが「10 万文書のフォルダでは folder cardinality 依存の高価な join になる。
正しさの欠陥は無いが、その規模の許容性を示すものが無い」と残した点を埋めた。

開発索引は親 1,300・チャンク 3,508 で最大フォルダも 232 文書しかないので、
**Solr に合成の親とチャンクを直接投入**して内側クエリの一致件数だけを増やした
(join のコストは内側クエリの一致件数で決まり、ベクトルの有無に依らない)。
`cache=false` で filterCache を迂回し、25 回の中央値。

| フォルダ内文書数 | フィルタ無し (床) | join | join − 床 | チャンク数 |
|---|---|---|---|---|
| 100 | 1.9 ms | 1.8 ms | −0.1 ms | 200 |
| 1,000 | 1.3 ms | 1.3 ms | 0.0 ms | 2,000 |
| 10,000 | 3.3 ms | 1.9 ms | −1.4 ms | 20,000 |
| **100,000** | 1.8 ms | 1.8 ms | **0.0 ms** | **200,000** |

**読み: フォルダを 1,000 倍にしても join のコストは増えない。** 差分列のばらつきは
約 1.4 ms あり負の値も出るので、**特定の ms 値は主張できない** — 主張できるのは
「フォルダサイズに対して増えない」ことだけ。合成親にはベクトルが無いので、これは
**join フィルタの上乗せ分**であってクエリ全体の応答時間ではない (KNN 自体は
フォルダサイズに依存しない)。

このプローブは 2 回、自分で無意味な数字を出してから直した:
**(1)** 親だけを投入してチャンクを作らなかったので join が 0 件に当たり、全サイズで
0 ms が出た — 走っていない実験に対する自信のある数字。
**(2)** 比較対象の素フィルタを**チャンクに対して**測っていたので 0 件で、
これも空を測っていた (副産物として「素の `parent_id` はチャンクに当たらない」の
3 度目の確認にはなった)。現在は「フィルタ無しの床」を毎回測り、素フィルタは
親文書側で測っている。

**実測 (`tools/acl-probe/rag_folder_scope.py`)**: フォルダ内 2 件・フォルダ外 1 件を
同一本文で作り、3 通りの重み配分で id 集合を突き合わせた。全て `in=2/2, out_leaked=False`。
陰性対照として `rag.search.property.enabled=false` で **content 経路だけを残し**、
壊れた 1 本フィルタ版を clean ビルドしてデプロイすると **`in=0/2`** になる
(= 「フォルダ検索から本文ヒットが消える」が実機で再現)。修正版は同条件で `in=2/2`。

> 陰性対照が最初 2 回「壊した版でも通る」と出たが、これは**両方とも計測の失敗**だった。
> 1 回目は property 側が結果を埋めて chunk 側の全滅を隠していたため
> (`propertyBoost=0` を渡しても効かない。下記)。2 回目は WAR ビルドが JDT LS の
> `target/classes` 競合で落ちていたのにパイプで終了ステータスが潰れ、**古い WAR を
> 測っていた**ため。どちらも「壊れているのに緑」なので、対照が通ったときこそ疑うこと。

**同時に見つかった契約違反も直した (✅)**: `folderId` を指定すると
`RAGSearchResource` は `searchInFolder(...)` を呼ぶが、この経路は
**`propertyBoost` / `contentBoost` / `minScore` を一切見ていなかった** (設定値で検索して
200 を返す)。API はこれらを受け付けると documented しているのに、`folderId` と併用した
瞬間にエラーも警告もなく捨てられていた。`folderId` 自体の欠陥と同じ
「黙って効かないパラメータ」。

`searchInFolder` に 3 つを取るオーバーロードを足し (5 引数版は設定値へ委譲)、
resource から渡すようにした。`RagFolderFilterTest` が転送をピン留めしている。

**この修正が入るまで、上の陰性対照は成立していなかった。** プローブが
`propertyBoost=0&contentBoost=1` を送っても捨てられていたので、3 ケースは同じ呼び出しに
潰れており、property 側がフォルダ内 2 件を埋める限り chunk 側が 0 件でも「OK」と出た。
最初の陰性対照が空振りしたのはこれが原因で、当時は `rag.search.property.enabled=false`
を**プローブの外から**与えて凌いでいた。現在は既定設定のまま、chunk フィルタを壊すと
`content 100%` が `in=0/2` で落ち、`property 100%` は 2/2 のまま、**既定加重も 2/2 のまま**
になる — 最後の 1 行が「なぜ content 100% のケースが要るのか」の実測的な答え。

ついでに 2 点:

- **folder 経路にも「boost が両方 0 なら拒否」ガードを入れた** (`searchWithBoost` には
  あった)。無いと両半とも無効のまま空の 200 が返る — 何も走らなかった検索が
  「見つからなかった検索」として報告される。効いた値 (null なら設定値) で判定する。
- **`minScore` の既定をリテラル 0.7 から設定値に変えた**。resource が持っていた
  `0.7f` は `RAGConfig` の既定を二重化しており、`rag.search.similarity.threshold` を
  変えた運用では **folder 経路 (設定値を読む) と他の 2 経路 (0.7 固定) で閾値が違う**
  という状態だった。

#### 経路別の確認 (`tools/acl-probe/rag_revocation_paths.py`、2026-08-11)

seed プローブが測ったのは**グループ ACE 経由の read 剥奪 1 経路**だけ。判定が
PermissionServiceImpl ではなく**トークン交差**である以上、トークン集合の作られ方が
違う経路はそれぞれ別の検査が要る。4 経路を追加で確認した (3 回連続で同結果)。

| 経路 | 結果 |
|---|---|
| P1 `anyone` / GROUP_EVERYONE 経由の read 剥奪 (公開フォルダを閉じる) | ✅ seed 0.061–0.072 s / 検索 0.104–0.118 s |
| P2 ネストグループ (outer ⊃ inner ∋ user、ACE は outer のみ)。inner を outer から外す | ✅ seed 0.063–0.067 s / 検索 0.094–0.120 s |
| P3 admin 降格 | ✅ ただし**測るものが無かった** (下記) |
| P4 読めないフォルダへの move (ACL は 1 バイトも変えない) | ✅ seed 0.105–0.121 s / 検索 0.127–0.138 s |

いずれも剥奪後 20 秒の再観測でも戻らず、観測用 admin ACE は最後まで通っている。

**P3 で分かったこと (別件の不整合)**: admin 権限は **RAG に及ばない**。ACE を持たない
管理者は、同じ文書を **CMIS の getObject では 200 で読め、RAG の seed では 404** になる。
つまり降格しても RAG 側に剥奪すべきものが無い。差の向きは安全側なので漏れではないが、
**「管理者にだけ意味検索が効かない」**という機能上の不整合ではある。プローブはこれを
性質として固定してあるので、RAG に admin bypass を足すと**この検査が落ちて**、降格
シナリオが実在に変わったことが分かる。

#### ownership 残差 = PWC だけだった (`tools/acl-probe/rag_pwc_exclusion.py`)

R1 が言う「ownership の意味論差」の実体を追うと、`PermissionServiceImpl` で
ownership が効くのは **PWC 1 箇所だけ**だった (`checkPermissionInternal`:
PWC は `VersionSeries.getVersionSeriesCheckedOutBy()` と一致する本人のみ許可し、
**通常の継承 ACL を見ない**)。RAG は継承 ACL 由来のトークン交差なのでこの規則を知らず、
**PWC が索引されていれば同一グループの非オーナーが作業中の草稿を seed に使える**
(存在 + 意味的近傍の oracle)。

実測 4 点、全て OK:

| | 内容 | 結果 |
|---|---|---|
| E1 | PWC はオーナー自身にも seed できない | denied |
| E2 | **PWC は同一グループの非オーナーにも seed できない** (漏れの本体) | denied |
| E3 | チェックアウト中も**元の文書**は seed できる (陽性対照) | allowed |
| E4 | チェックイン後は新版が索引に戻る | 0.99–1.14 s |

E3 が要。除外を「全部消す」で実装しても E1/E2 は通ってしまうので、
何が残っているべきかを同時に主張しないと劣化を検出できない。

**陰性対照で分かったこと: 除外は 2 段ある。** `RAGIndexingServiceImpl.indexDocument`
の入口だけを潰しても **PWC は索引されなかった** — 通常の書込み経路では
`SolrUtil.triggerRAGIndexing` (627 行) が先に弾いて `triggerRAGDeletion` まで走らせる。
**両方**を潰して初めて E1/E2 が `allowed` に転び、seed-oracle が再現した
(E3/E4 は OK のままなので、検査は狙った差だけを見ている)。
片方だけ「冗長だから」と外してもテストは緑のままなので、
**この 2 段が冗長であること自体を記録しておく**。

#### cross-replica も測った (`tools/acl-probe/rag_revocation_cross_replica.py`)

「単一レプリカ環境では測れない」と書いていたが、`core2` を 8090 に立てて
**同一 CouchDB / Solr を見る 2 レプリカ**にすれば測れる。live-ACL ゲートは
**その JVM のキャッシュに載った ACL** を見るので、ACL 変更を行っていないレプリカが
自前の memoise を持ち続けないか、が問われる点だった。

**A (8080) で剥奪し、B (8090) で確認する。**確認系のセッションは必ず B 側のみ。

| 測定 | 3 回の実測 |
|---|---|
| X1 ACE 剥奪 → B の seed 拒否 | **0.25 / 1.12 / 1.33 s** |
| X1 ACE 剥奪 → B の検索から消失 | **1.29 / 1.30 / 1.45 s** |
| X2 グループ membership 剥奪 → B の seed 拒否 | **5.38 / 7.06 / 8.43 s** |
| X2 グループ membership 剥奪 → B の検索から消失 | **6.31 / 7.89 / 9.45 s** |
| X3 剥奪後 30 秒、B 側で復活しない | 3 回とも維持 |

陽性対照 (剥奪前に **B 側で** seed / 検索できること) が取れない回は無効。3 回とも取れている。

**読み: 経路によって桁が違う。**

- **ACE 剥奪は約 1 秒**。B は ACL 自体を読み直すので、自分が変更していなくても追随する。
- **グループ membership 剥奪は 5〜9 秒**。こちらはトークン集合が principal 世代の
  キャッシュに載っており、`CrossReplicaCacheInvalidator` の**ポーリング (既定 5 秒、
  `scheduleWithFixedDelay`)** でしか他レプリカに伝わらない。書いた側の publish と
  読む側の検知でポーリングを 2 回跨ぐので、**正常時の目安は 5〜10 秒**。

  **ただしこれは上限ではない** (レビュー指摘、確認済み)。`scheduleWithFixedDelay` は
  各回の実行時間を間隔に上乗せするし、`pollOnce` の失敗もリポジトリ単位の失敗も
  catch されて次周回に回るだけ、世代の publish は 2 回とも失敗しても警告ログだけ残る。
  CouchDB 不達・ポーラ停止・publish 競合の継続では**無期限に遅れうる**。
  プローブが測ったのは**正常系の観測値**であって SLA ではない。
  剥奪の反映時間を保証する要件があるなら、この機構だけに依存させないこと。

単一レプリカでの同じ操作は 0.08〜0.12 秒なので、**multi-replica ではグループ剥奪だけが
2 桁遅い**。運用上「グループから外した直後に別レプリカで検索されると最大 10 秒見える」
ことを意味するので、SLA を書くならこの数字を使うこと
(`CrossReplicaCacheInvalidator.setPollSeconds` で短縮可、CouchDB への読み出しは増える)。

**残差**: なし。ownership (= PWC) と cross-replica はどちらも上記で閉じた。

#### プローブ自身の落とし穴 (2 つ踏んで直した)

- **陽性対照がランキング運に依存していた。** 検索の照会語にランダムなマーカー文字列を
  使っていたが、意味検索の順位はコサイン類似度で決まるので、約 1,300 文書の索引に対して
  「fixture が topK に入るか」は運になる。負けた回は**権限の失敗として報告された**
  (P1 が 1 回 INCONCLUSIVE)。照会語を**文書自身の文**に変え (fixture のコサインが ≈1 に
  なるので必ず上位)、topK も 100 に上げた。
- **観測用 admin の対照が 1 サンプルだった。** 5xx や接続断が 1 回混じるだけで
  「fixture が消えた」と判定され、完走した計測ごと捨てていた。対照は*生存確認*なので
  有界待ち (30 秒) に変更。**確定した拒否は retry で消せない**ようになっている
  (ALLOWED を待って諦める形なので、本当に消えていれば依然 INCONCLUSIVE)。

### 🟡 A6: ロック順の逆転によるリポジトリ全停止 (計測して大半を除去、残りは可視化)

**2026-08-10 に実機で発生。リポジトリが復旧不能に固まった。** 今回の変更とは無関係の
既存欠陥だが、**基準 2 の最も重い違反**なので v3.3 のブロッカーに上げた。

観測できたのは「どのスレッドがどの行で park したか」までで、**ロックの identity は
採れていなかった**。当初はここから `deleteTree` (親 write → 子 write) と
`getFolderParent` (子 read → 親 read) のペアだと推定したが、**この推定は外れていた**
(レビュー指摘。後述の実測にそのペアは 1 件も出ていない)。推定で直していたら、
直った気になって別の環が残っていた。

#### なぜ推定が危険だったか

ロックは **striped** で、`ReentrantReadWriteLock` が 4096 本しかない。
リポジトリには 6 万件超のオブジェクトがあるので、**無関係な 2 オブジェクトが同じ
ロックを共有する**。「常に祖先を先に取る」のような**階層で表現した順序規則は、
そもそも問題に届かない** — 環の両端は親子とは限らないため。

#### 計測 (推定をやめて事実を採った)

`LockOrderMonitor` を入れて実機に投入し、全テストスイートを 1 周させた。
検出するのは 2 つ:

- **upgrade**: 同一スレッドが read 保持のまま write を要求。
  `ReentrantReadWriteLock` は昇格できないので**確実・即時・恒久の自己デッドロック**。
  取得の**前**に報告する (取得は戻ってこないので、後で報告する実装では何も残らない)。
- **inversion**: あるスレッドが A→B、別のスレッドが B→A。
  まだ刺さっていなくても報告する。刺さるのを待つのは、障害で学ぶのと同じ。

| | 修正前 | 修正後 |
|---|---|---|
| upgrade | 0 | 0 |
| inversion (件数) | **217** | 23 |
| inversion (相異なるペア) | **60** | 6 |

検出されたペアには**ルートフォルダが含まれていた**。例外的な相互作用ではなく、
日常のトラフィックで起きていた。

#### 原因は 1 つの形だった

スタックを集計すると発生元は 4 箇所で、**すべて同じ形**だった:
**順序付きセットの「外側」で取ったロックを、そのセットの間ずっと保持している**。
セット内をソートしても、セットの外で取ったロックはそのセットに対して順序を持たない。

| 発生元 | 件数 |
|---|---|
| `NavigationServiceImpl.getChildrenInternal` (子の bulkLock) | 51 |
| `NavigationServiceImpl.getObjectParents` | 6 |
| `NavigationServiceImpl.getFolderParent` | 2 |
| `SolrQueryProcessor` の検索結果 bulkLock (`DiscoveryServiceImpl.query` 経由) | 1 |

#### 対処

1. **`readLocks` / 新 `orderedLocks` がストライプ順に揃える**。以前は呼び出し側の
   リスト順 (= Solr が返した順) のままで、Guava が `bulkGet` で明示的に警告している
   まさにその使い方だった。同一ストライプに落ちる id は 1 つに畳む
   (二重取得すると `bulkUnlock` が 1 回しか返さず、スレッド寿命ぶん保持が漏れる)。
2. **`getFolderParent` / `getObjectParents`**: 親をロック前に解決し、
   子と親を**1 つの順序付きセット**として取る。親はロック下で読み直し、
   **一致しなければ解放して再プレビューからやり直す** (有界リトライ、尽きたら 409)。
   初版は不一致を即 409 にしていたが、それは「move をロック待ちで見送った読み取り」——
   旧コードなら正しい新親を返せていたケース——を決定的に失敗させる劣化だった
   (レビュー指摘 NAV-002)。リトライで通常ケースは正しい新親に収束し、
   409 が出るのは move が続いている間だけになる。
3. **`getChildren`**: フォルダのロックを**フォルダ自身の compile までに狭め**、
   `getChildrenInternal` が **{フォルダ}∪{子}** を 1 セットで取る (両分岐)。
   空フォルダの早期 return 分岐にも存在確認を追加 (レビュー指摘 NAV-001/TQ-4)。
   deleteTree は子を先に消すので「窓の間に削除されたフォルダ」は子 0 件として
   まさにこの分岐に入り、ガード無しでは 404 のはずが空の 200 になっていた。
4. **`bulkLock` を有界化**: セット 1 試行 30 秒・総 300 秒 (試行の締切は総締切で
   打ち切られるので 300 秒は**厳密な**上限)、**試行の間で全解放**、最終的に
   `LockAcquisitionTimeoutException`。これが**恒久停止そのものを塞ぐ**。
   セット内をいくら揃えても、外側の保持を通って閉じる環はセットの中からは見えない。
   見えないものを順序で直すことはできないが、**待ち続けないことはできる**。
   タイムアウトした側がセットを手放せば、相手は前に進める。

#### 検出器自体の欠陥を直した (レビュー指摘)

初版は**保持スタックの先頭としか比較していなかった**。A→B→C を保持している状態で
A→C を記録しないので、「外側のロックを内側のセットの間ずっと保持する」という
**まさにこの問題の形が見えない**。「発生元は 4 箇所」は「この不完全なモデルで見えた
4 箇所」であって、それ以上の主張ではなかった。**最古 16 本** (= 外側スコープ) と
比較するよう修正。16 本で打ち切るのは意図的で、コストを抑えつつ「外側保持 vs 内側
セット」という今回の障害の形は必ず比較対象に入る。打ち切りが起きた回数は
`depthLimitedAcquisitions` として `/lock-order` に出るので、「inversion 0」は
「どれだけ見た上での 0 か」と併読できる。

第 3 ラウンドのレビューでさらに 3 つ直した:

- **upgrade 判定が mode を見ていなかった**。W→R→W (合法な降格 + 再入 write) を
  「確実な自己デッドロック」と誤報する。同一ストライプの保持に **write が 1 つも
  無い**ときだけ upgrade とするよう修正。
- **確定した upgrade に 300 秒払っていた**。判定した瞬間に失敗が確定しているのに
  単独 lock() は上限まで待ち、その間キュー先頭の writer が後続 reader を全部止める。
  `beforeAcquire` が verdict を返し、**即時に拒否**するようにした (誤検出を先に
  直したから安全にできる — 逆順だと合法な取得を即時 503 にしていた)。
- **findings がオブジェクトペアでキーされ基数無限**だった。ホットな 1 箇所が
  組み合わせごとに finding を鋳造し、上限 500 を埋めた後は新規 (将来の upgrade 含む)
  が**ログにも出ない**。**ストライプペア**でキーし直し、上限到達は一度だけ ERROR +
  `findingsCapReached` で可視化。加えて `released(stripe, mode)` (mode 無視の解放は
  降格パターンで幻の write を残す)、`unlocksWithoutHold` カウンタ (別ラッパ経由の
  unlock は旧実装と違い**解放されずリークする**ようになったので、その唯一の症状)。

そのため**修正前後の件数は直接比較できない** (計測器が変わっている)。
比較できるのは発生元の数と形:

| | 修正前 | 修正後 |
|---|---|---|
| 発生元 | 4 箇所 | 3 箇所 |
| 形 | 外側の単独ロック + 内側のセット | **同型が残存** (getDescendants が各階層のセットを保持したまま次の階層のセットを取る) + セット同士 |
| upgrade | 0 | 0 |
| **リクエストの恒久停止** | **しうる** | **しない** (有界化) |

(旧版のこの表は残存形を「入れ子のセット同士」とだけ書いていたが、実測ログの
残存 3 箇所には外側保持の形も含まれる。除去したのは Navigation 系 4 箇所の
「単独ロック + セット」であって、形そのものが絶滅したわけではない。)

#### 上限は 2 つに分けた (自分の誤りを 2 回踏んで確定した)

最初、単独ロックも 30 秒で切った。結果、MultiThreadTest の**正当な輻輳**
(同一フォルダへの並行 create) が失敗した。デッドロックではなく、混んでいただけ。
次に、セットの上限を「3 回試行」に固定したままにしたら、今度は
`getFolderParent` の 2 ロックが 30 秒×3 で足りず、通常の読み取りが 63 件失敗した。

**リトライは環を壊すためのもの、総時間は輻輳のためのもの**で、混ぜると
「混んでいる」が「壊れている」に見える。分離した:

| | 値 | 役割 |
|---|---|---|
| セットの 1 試行 | 30 秒 | この周期で**全解放**する。解放が環を壊す |
| セットの総時間 | 300 秒 | 輻輳をどこまで待つか |
| 単独ロック | 300 秒 | デッドロック破りのみ。15 秒で WARN (失敗ではない) |

**300 秒は 1 回の取得の上限であって、リクエストの上限ではない** (レビュー指摘
A6-DOC-2)。1 リクエストが複数の取得を順に行えば合計はその倍数になる
(例: 親ヘルパーは最大 3 試行、`deleteTree` はノードごとに取得する)。
「リクエストが恒久停止しない」ことは保証するが、「300 秒で必ず返る」は保証しない。

実測: 全スイート 1 周で「30 秒で取れず再試行」の WARN が 62 件、
**例外は 0 件**、テスト全緑 (当時 4,890 件、最終 4,904 件)。つまり輻輳は
待ち切れており、上限は本当にデッドロック用の網になっている。
なお上限系は**実測だけに頼らず単体で失敗経路を実行する**ようにした
(注入可能な上限で: 単独タイムアウトの throw と 503 契約、bulk タイムアウト後の
全解放、試行が総締切で打ち切られること — `ThreadLockServiceImplTest`)。
「例外 0 件」は網が誤爆しない証拠ではあっても、網が受け止められる証拠では
なかったため (レビュー指摘 TQ-1)。

#### 残っているもの (可視化済み・恒久停止はしない)

**修正済み検出器での再計測** (2026-08-11、新 WAR + 全スイート 1 周):

| | cf4272a19 時点 | ae2c70705 時点 (現在) |
|---|---|---|
| inversion (発生回数) | 1,815 | **0** |
| inversion (相異なるストライプペア) | 162 | **0** |
| upgrade | 0 | 0 |
| depth 打ち切り (`depthLimitedAcquisitions`) | 12,798 | 12,791 |
| `unlocksWithoutHold` | 0 | 0 |
| findings 上限到達 | false | false |
| 例外 (LockAcquisitionTimeout) | 0 | 0 |
| テスト | 4,904 / 0 failures | 4,909 / 0 failures |

旧検出器の「23 件 / 6 ペア / 3 箇所」は**大幅な過小計上だった** — 盲点 (先頭比較・
深さ 16 で照合ごとスキップ) が数字を作っていた。修正した検出器で 1,815 件が見え、
その 161/162 が `getDescendants` の外側保持だと分かり、そこを直して **0** になった。
「3 箇所という主張はこのモデルの範囲でしか言えない」という指摘は正しく、
検出器を直さなければこの本体には到達できなかった。

**この 0 の読み方** (過大解釈しないこと):

- **`depthLimitedAcquisitions` が 12,791 ある。** 保持 16 本超の状態での取得は
  inversion 照合が部分的になる。検出器は新規取得を**最古 16 本** (= 外側スコープ、
  今回の障害の形) と比較するので、落ちるのは内側セット同士のペアだが、
  「0」は「この窓で見た限り 0」である。
- テストスイートの並行度・データ量での 0 であり、本番規模での 0 ではない。
- 逆順が無いことと、恒久停止しないことは別の主張。後者は有界化が保証する。

**多重ロック点の変換状況** (レビュー指摘を受けて追加対応):

| 箇所 | 状態 |
|---|---|
| `PolicyServiceImpl` (object + policy) | ✅ 1 つの順序付きセットに変換 |
| `ObjectServiceImpl.moveObject` | ✅ id 順 → **ストライプ順**に変換。id 順はストライプの順序を何も保証しない |
| `NavigationServiceImpl.getDescendants` | ✅ 外側の単独ロックを狭めた。**残存 inversion の本体** (161/162) で、これで実測 0 に |
| `AclServiceImpl.applyAcl` | ✅ READ → WRITE。read-modify-write を共有ロックで守っており、同時 applyAcl が権限を取りこぼしていた |
| `ObjectServiceImpl.moveObject` の hierarchy lock | ✅ enum 経由のみに変更 (objectId から到達不能) + サブツリー refresh をロック外へ |
| `VersioningServiceImpl` の内側 `latestLock` | ✅ 対処済み (別問題として)。checkIn / cancelCheckOut の内側 latestLock は**ミューテーション確定後**にあり、そこで 503 を出すと「safe to retry」が偽になる (再試行は PWC 消滅で失敗し、成功した事実をクライアントが知れない) 上にキャッシュ退避も飛ぶ — レビュー 3 者が一致して指摘。タイムアウト時は**ロック無しで退避して成功を報告**するよう変更 (退避は冪等で、ロック下でも再取込レースは防げていなかった) |
| `ObjectServiceInternalImpl.deleteObjectInternal` の再帰 | ⚠️ 未変換。**構造上バッチにできない** (親を保持したまま子へ降りる)。有界化で恒久停止はしない |

**単独 `lock()` も有界**になったので、単独ロックだけで構成される環も恒久停止しない。

#### 出荷判断

達成: 観測された停止の**再現と原因特定** (推定ではなく実測)、主要因の除去、
そして**恒久停止という故障モードそのものの除去** — すべての取得が有界になったので、
環ができても片方がタイムアウトして解放し、リクエスト 1 本が retryable な
`CmisServiceUnavailableException` (503) になる。リポジトリは止まらない。
(「すべて」は第 3 ラウンドで文字どおりになった: 呼び出し元ゼロのまま無防備だった
`lockInterruptibly` も同じ上限に入れた。)

**503 が 503 のまま届くかを全経路で確認し、主要経路を修正した** (レビュー指摘 A6-EX 系)。
「全経路で修正」ではない — 下の残余表に挙げた 29 箇所は 500 のまま。
Browser binding のコンテンツ取得だけ catch (Exception) → 500 で信号を失っていた。
/api/v1 は `CmisServiceUnavailableException` の getCode()==0 を「クライアントエラーに
非ず」= 500 と写像していた上、リソース層の catch (Exception) → internalError 包みでも
消えていた — マッパに型分岐と cause 連鎖の復元を入れた (cause を渡さない一部の
wrap 箇所 (136 中 29) は救えない。残余として記録)。bulkUpdateProperties は
例外を**無言で**畳んでいた (対象がログ 0 行で結果から消える) → WARN + retryable の
明示。deleteTree はロックタイムアウトを「orphan、CouchDB 直接掃除」と誤誘導する
ログにしていた → transient と分類し「再実行せよ」に変更。

残るのは「輻輳下で読み取りが 503 で失敗しうる」こと (300 秒待っても取れない場合)。
実測ではスイート 1 周で 0 件 (最終スイート 4,909 件全緑)。**恒久停止 → 一過性の失敗**
という格下げが A6 の到達点であり、それに加えて**観測された逆順は現在 0** である
(上の再計測表と、その読み方の注記を参照)。

第 5 ラウンド (最終検証) で見つかった退行・新規 6 件も修正済み:
親リトライの例外経路でロックが恒久リーク (**A6 の主張を直接壊す退行**。回帰テストで
固定)、`__…__` パターン一致による named lock がリクエスト由来 id で無制限に増える
(許可リスト方式に変更 — named 扱いは閉じた列挙で、クライアント id は従来どおり
ストライプへ)、割込み済みスレッドの upgrade 拒否が InterruptedException に先行する、
バックオフ睡眠が総締切を突き抜ける (これで 300 秒は本当に厳密)、cause 循環でマッパが
回り続ける (深さ 16 で打ち切り)、named lock の WARN が律速されない。

**受容済みの残余** (いずれも有界):
- checkIn / cancelCheckOut のロック無し退避は、変更前に読んだ読者の stale 再取込に
  先行され得る。5 秒後の二次退避 (専用 daemon scheduler。共有 ForkJoinPool は
  undeploy 時にアプリの制御外へ出るので使わない) で窓を狭め、**ehcache の
  `timeToLiveSeconds: 3600` = 1 時間**が最終防波堤
  (「503 で成功を隠す」よりは stale 数秒〜最悪 1 時間の方を取った)。
- /api/v1 の `internalError(...)` 呼び出し 136 箇所のうち **cause を渡さない 29 箇所**
  では、マッパの cause 連鎖復元が効かず 503 が 500 に落ちる (107 箇所は復元される)。
- 検出器の打ち切りは 2 つ: 深さ 16 (`depthLimitedAcquisitions` で可視) と、
  EDGES 20 万件の上限 (**カウンタもログも無い**。到達すると新しいエッジが記録されず
  以後の inversion 検出が静かに劣化する — レビュー指摘 A6-DOC-3)。

出荷するなら、オーナーが受容するのは
「リポジトリ全停止は無くなった。代わりに極端な輻輳下で個別リクエストが 503 になる」。

### P1 — 隔離 (基準 2 の合格ライン)

**P1-1 (A1/A5): 実行面の隔離。実装済み — ただし手段を差し替えた。**

*当初案 (協調的譲歩) を採らなかった理由*。
オーナー決定は「第一段 = 協調的譲歩のみ」だった。実装に入って設計条件を詰めた
結果、**この手段は肝心のケースで効かない**ことが確定したので、同じ制約の中で
別の手段に差し替えている。判断の根拠は次のとおり。

譲歩とは「N ノードごとに区切り、残りを継続タスクとして re-submit して返る」こと。
re-submit 先は同じ `ragAclExecutor` である。**キューが満杯だから CallerRuns が
発火している**のだから、その継続 re-submit もまた CallerRuns で同じスレッドに
即座に返される。つまり基準 2 が壊れる唯一の局面 (リクエストスレッドがサブツリー
全走査を負う) では、譲歩は 1 ノードも仕事を減らさない。当初案自身が
「キュー満杯が続く間は現状同等」と正直に書いていたが、**それは効果の限界ではなく
効果の不在**だった。

*実装した手段: inline 流出の耐久キューへの委譲*。
タスク本体で `Thread.currentThread() == submittingThread` を見て CallerRuns で
リクエストスレッドに落ちたことを検出したら、走査を **一切せず** に root を
reconcile キューへ `TRAVERSAL_FAILURE` + epoch 付きで積んで返る。

- executor の構造 (core=0 / max=1 / queue 256 / CallerRunsPolicy) は**一切変更
  していない**。CLAUDE.md の凍結制約も、オーナーが除外した repo 単位ワーカー
  分離・並列化 (第二段) も、そのまま。
- **仕事は失われない**。reconcile の re-drive が root から引き受ける。
  代償は「root からの再走査」であり、リクエストを人質に取るより明確に良い。
- **epoch 義務はここで settle しない**。settle するのは re-drive の終端のみ。
  (当初案が継続タスクに課していた「最終セグメントのみ settle」条件は、
  セグメントが存在しなくなったので自動的に満たされる。)
- reconcile service が未配線の構成では委譲せず inline 走査する。
  黙って落とすより遅いリクエストの方がまし、という判断を WARN で明示する。

*キュー書込みが失敗したら委譲しない*。`enqueueOrThrow` を使い、例外なら `false` を
返してその場で走査する。fail-soft な `enqueue` は CouchDB 障害をメトリクスに
飲み込むので、「委譲した」と偽って早期 return すると**遅いリクエストが失われた
リフレッシュに化ける**。

*観測*。`/v1/admin/search-index/metrics` に `deferredToReconciliation` を追加。
既存の `inlineRunsOnRequestThreads` と**並べて読む**のが正しい読み方で、
両方が揃って増えるのが健全 (溢れた分はすべて耐久キューへ移った)。caller-runs だけが
増えて deferrals が平坦なら、reconcile 未配線で実際にリクエストが走査している。

*効果の正確な言明*。基準 2 で問題になる「リクエストスレッドが他人のサブツリーを
走る」ことは、**reconcile が配線されており、かつキューへの書込みが成功する限り**
起きなくなる。CouchDB が落ちている等で `enqueueOrThrow` が失敗した場合は
意図的に inline 走査へ落ちる (捨てるよりまし)。つまり保証の前提は「配線」だけでなく
**キューが書ける**ことまで含む。一方、伝播そのものが
速くなるわけではなく、キュー満杯が続けば耐久キューのバックログが伸びる。
バックログは可視 (metrics / reconcile 状態) で、リクエスト遅延には変換されない。
これはオーナーの受入条件 (遅くてよい / アプリ全体を落とすのは不可) に一致する。

**A5 (剥奪系タスクの HOL): 実装済み — レーン分離。**
上の委譲で ACL_REINDEX のバックログが増えるため、**A5 は委譲の前提条件**だった。

最初はバッチの 1/4 を purge に予約するクォータで実装したが、**それでは効かない**ことが
レビューで判明した。理由は**ブロックの単位**にある。scheduler は claim したバッチを
**直列に**処理し、その 1 件が数分〜数時間かかるサブツリー走査でありうる。バッチを
claim した 1 秒後に届いた purge は、その走査が終わるまで **claim すらされない** —
バッチの何割を予約していようと関係ない。予約は claim を守るが、待たされている場所は
claim ではない。

そこで **専用ポーリングスレッド** (`SearchIndexReconcile-purge`) を追加した。
purge は有界かつ冪等な delete なので、このレーンが長時間ブロックすることはない。
- `claimDuePurges` は `operation=RAG_PURGE` で**クエリ側**を絞る (後段フィルタでは
  CouchDB が due 全域を走査してしまうため)。期限切れリースの purge も回収する。
- **共有レーンは operation で絞らない**。purge レーンが未配線・停止しても孤児に
  しないため。分離の目的は「purge を待たせない」ことであって、共有レーンが purge を
  実行できないからではない。
- ただし絞らない以上、共有レーンが `[長い ACL_REINDEX, RAG_PURGE]` という混在バッチを
  掴むことがある。claim した時点で両方 LEASED になるので purge レーンはもう手を出せず、
  直列ループが再駆動を先に回せば purge は結局数時間待つ — 分離した意味が消える。
  そこで **`processClaimed` はバッチ内で purge を先に回す**。混在バッチに入っても
  purge に対して最初に行うのはその処理、という状態を保つ。
- `claimDuePurges` は **期限切れリースを先に**引く。PENDING を先に満たすと、
  新規 purge が毎 poll バッチを埋める状況で、クラッシュしたワーカーが放棄した purge が
  永久に見られない (新しいものに押し出され続ける)。
- 両レーンは同じ `_rev` CAS で claim するので、同じ文書を掴んでも二重実行しない。
- **Mango index を追加** (`type/status/operation/nextAttemptAt` と同 `leaseExpiresAt`)。
  無いと CouchDB が status index で答えて operation を後段フィルタし、
  大きな再駆動バックログに紛れた稀な purge を探して due 全域を走査する —
  アプリのリクエストを捌いている同じ CouchDB に負荷をかけることになり、本末転倒。
  patch 名の suffix も `-20260810d` に上げたが、**この patch に関しては効果は無い** —
  `AbstractNemakiPatch.apply()` は `isApplied()` 判定より前に `applySystemPatch()` を
  呼び、`PatchService` 側も名前で門を作っていないので、system 側の index 登録は
  毎起動走る (`postIndex` は冪等)。suffix は per-repository 側の慣習に合わせただけ。

**レーン分離で顕在化した既存欠陥 (修正済み)**。2 レーンにしたことで purge と ACL
再構築が**同時に走り得る**ようになったため確認したところ、`purgeDocumentBlocks` が
per-ragId ストライプ (`ragBlockLocks`) を**取っていなかった**。`updateDocumentACL` は
Block Join の制約から read-rebuild-write (親と全チャンクを読み、readers を差し替えて
ブロックごと再 add) なので、その read と write の間に delete が入ると**再構築が
delete を打ち消す** — purge は「消えた」と検証済みで成功を報告しているのに、
剥奪されたリーダーのブロックが索引に戻る。purge が消したかったオラクルそのものが
黙って復活する。

**multi-replica も閉じた** (realtime GET による版フェンス)。
ストライプはプロセスローカルなので、それだけでは別レプリカの purge を止められない。
コード上のコメントが既に正解を指していた: 「`_version_` CAS は一度試して revert した。
親を **searcher クエリ**で読んでいるので soft commit 遅延で版が古く、偽の 409 が出た。
正しい CAS には **realtime GET** が要る」。そのとおりに実装した。

- ブロック再 add の直前に `getById` (realtime GET = update log を読むので soft commit
  遅延の影響を受けない) で親の権威ある `_version_` を取り、それを CAS トークンとして
  add に載せる。
- **realtime GET が「無い」と答えたら add しない**。再構築中に purge が勝った証拠で、
  ここで add することが復活そのものだから。
- 正の `_version_` は「この版でちょうど存在すること」を意味するので、
  別レプリカの同時ブロック書込み (版が上がる) でも purge (消える) でも add は棄却される。

*検証 (単体)*: `RagPurgeVsAclRebuildRaceTest` は 2 ケース。同一インスタンス
(ストライプが効く) と、**別インスタンス = ストライプを共有しない multi-replica 相当**。
後者はフェンスを外すと `[delete, add]` で落ちることを実測確認済み
(フェンス有効時は `[delete]`)。

*検証 (実機 Solr、2026-08-10)*。「Solr が Block Join の親に対して楽観ロックを
本当に効かせるのか」はモックでは確かめられないので、nb33 の Solr に直接当てた。

| 確認 | 結果 |
|---|---|
| 親 (子付き) の realtime GET で `_version_` が取れる | ✅ `1873119855048130560` |
| `_root_` 削除の**直後**に realtime GET | ✅ `{"doc":null}` (searcher の遅延を受けない) |
| 旧版を載せたブロック再 add | ✅ **409** `expected=1873119855048130560 actual=-1` |
| 正しい版での連続更新 3 回 | ✅ 3 回とも status 0 (**偽 409 なし**) |
| CAS 付き置換後もチャンクが残る | ✅ ブロック内 2 docs |

つまり復活は**二重に**塞がれている: realtime GET の null 判定と、Solr 側の版 CAS。

**P2 の兄弟欠陥も塞いだ** (レビュー指摘 A6-INT-2)。同じ soft-commit 遅延 (既定 10 秒) で
**searcher が「無い」と答える枝**は、これまで「未索引 — 次の索引で反映」として正常 return
していた。しかしブロックが update log には存在する (= 直前に書かれた) 場合、これは
**GRANT を無音で落とす**: 新規許可ユーザは次のコンテンツ再索引まで RAG 検索から欠落し、
reconcile タスクも積まれないので収束機構が無い (REVOKE 側は live-ACL ゲートが実害を
止めるため機密漏れは無い)。修正: 空 searcher でも realtime GET を照会し、update log に
在れば P2 と同じく throw して再駆動に委ねる。realtime も null なら従来どおり skip
(purge 勝ち / 本当に未索引)。

**さらに: CAS トークンと データ が同じ版であることを要求する** (レビュー指摘)。
realtime GET で取った「現在の版」を、**前に読んだ snapshot** に貼って書くと、
CAS は「直前の数マイクロ秒に変化が無かった」ことしか証明しない。読取り後・GET 前に
別レプリカが新しいブロックを書いていた場合、こちらが提示する版は本当に現在の版なので
**Solr は受理し、新しい readers とチャンクが古いもので置き換わる** — 剥奪したはずの
アクセスが戻る。そこで searcher から読んだ親の `_version_` を snapshot 版として保持し、
realtime 版と**一致しなければ書かずに例外**にする。呼び出し側がノード単位の失敗として
記録し、reconcile が競合相手の書込みが落ち着いた後に再駆動する。
静かに `return` すると「更新した」と報告してしまうので、ここは必ず throw。

**この欠陥はレーン分離以前から存在していた** (async applyAcl の refresh は
`ragAclExecutor` 上、`handlePwcPurge` はリクエストスレッド上で、既に別スレッド)。
分離は発生確率を上げるだけだが、修正は必須。`purgeDocumentBlocks` で同じストライプを
取るようにした。`RagPurgeVsAclRebuildRaceTest` が read/write 窓を実スレッドでこじ開けて
順序を固定する (**ロックを外すと `[delete, add]` で落ちることを実測確認済み**)。

**残る性質 (意図的)**: 共有レーンは古い順で公平なので、purge が大量に来続ければ
再駆動はその分後ろになる。purge レーンが並行して捌くため滞留は縮むが、
再駆動の下限保証は置いていない。剥奪の洪水が続く状況で再駆動を優先する理由が無い。

*検証*: `ReconcilePurgeLaneTest` (5) が「purge レーンは purge しか取らない」
「期限切れ purge も回収する」「共有レーンは絞らない」「期限切れ優先」
「重複してもバッチが埋まり切る」を固定。`InlineRefreshDeferralTest` (6) が
委譲時の enqueue・epoch 引継ぎ (null 含む)・未配線時に落とさないこと・
**キュー書込み失敗を成功と報告しないこと**・settle しないことを固定。

**P1-2 (A2/A3/A4): 構造を変えずスループットを上げる。見積りは約 2 倍 + α。**
1. **祖先チェーン再利用** (A3): §4.6 が許可するのは **snapshot 側のみ**。
   revalidation の祖先再読は fence の正しさの根拠なので**削減対象外**。
   削減効果は 2×(1+D) → (1+D)+1、つまり**約 2 倍が上限** (初版の 6 倍は誤り)。
   実装条件: step 4 不一致で restart する際は共有チェーンを破棄してフレッシュな
   walk からやり直す。
2. **principal lookup の短 TTL キャッシュ** (A4): **実装済み**。ただし当初案の
   「成功のみ・30 秒」から変更した。principal の by-id 参照がキャッシュを迂回していた
   理由は「served できなかった (UNAVAILABLE) を『不在』と取り違えると reader 集合が
   静かに縮む」ことなので、そこを壊さない形にした:
   - **UNAVAILABLE は絶対に保存しない**。FOUND / NOT_FOUND だけを記憶する。
     障害を答えとして再生しない。
   - **principal 世代をキーに含める** (P3-1-3 のカウンタ)。ユーザ・グループの
     create / update / **delete** が世代を上げるので、剥奪は TTL を待たずに
     全エントリが一斉に到達不能になる。
   - TTL 10 秒は、他レプリカでの principal 変更が世代ポーラ経由で届くまでの
     バックストップ。既存キャッシュの 1 時間より桁違いに短い。
   記憶するのは principal の**種別 (user か group か)** だけで、所属や権限は含まない。
3. **Solr バッチ** (A2): fenced write の 1 件ずつ `_version_` CAS が正しさの根拠
   なので、バッチ化は epoch 設計の精査が先。1+2 で足りるなら捨てる。
*検証*: 伝播スループット (docs/s、可視化ラグ控除) を before/after で。
正しさは epoch verdict + GRANT/REVOKE の陰性対照付き統合テスト。

**P1-3 (B1): 実施しない (§0 の決定)。**
応答前 BFS を「最大 M ノード」に制限する案は、M+1 件目以降の aclCache に
stale-permissive な実効 ACL が残る = **REVOKE 済みユーザが読める窓**を作る。
オーナー判断により、大規模フォルダの applyACL 応答が子孫数に比例して伸びること
(実測 +0.3ms/子孫、10 万件で約 +30 秒) を受け入れ、**認可の即時性と REVOKE の
即時性を一切緩めない**方針とした。B1 は「既知の特性」として文書化し、実装しない。
将来やるなら pending-aware キャッシュバイパス (設計 §7(a)) が有界化と両立する唯一の
形だが、伝播中の読みが全て cold になるコストを伴う。

**P1-4 (C7): pending gate を非カウントに — 可観測性要件とセットで。**
`retryLaterWithoutCountingAnAttempt` を AclEpochPendingException 由来にも広げる。
ただし非カウント化は「永遠に terminal FAILED に到達しない」を意味するので、
quarantine の前例 (§5.1: quarantineBlockedTasks メトリクス + blocker id) と同型の
**pendingBlockedTasks メトリクス + ブロック元 objectId** を必須とする。
実装注記: 現在 AclEpochPendingException は scheduler の汎用 catch(Exception) で
clean=false に潰されるため、例外型の伝播経路の整備が要る。pending の解消は
scanner (既定 300s) に依存する liveness であることを明記。
**配線 (ここが抜けると偽修正になる)**: 型を投げるだけでは scheduler が
`catch (Exception)` で拾って `retryLater` に落とすため attempts が増え続ける。
`SearchIndexRefreshPendingException` 専用の catch を **generic catch より前**に置き、
`retryLaterWithoutCountingAnAttempt` を呼ぶところまでが 1 セット。

*検証*: RefreshCountersTest — pending のみ / 本物の失敗が混在 / 失敗ゼロ の 3 分岐、
JVM 単位カウンタ、**scheduler が専用 catch を generic より前に持ち
`retryLaterWithoutCountingAnAttempt` を呼び `markFailed` を呼ばないこと**、
**re-drive から型のまま外へ出ること**を検査する。

### P2 — 可観測性 (基準 3 の合格ライン)

**計画からの変更**: queueDepth / activeCount の直接公開はやめた。executor は所有

### P3 — multi-replica の正しさ (§0 の決定により 3.3 のサポート対象。全項目を実装する)

**P3-1**: 実装済み。**値だけ共有し、機構は分ける**方針を採った (レビュー承認済み)。

1. **TTI 停止** (実装済み): ehcache の default から `timeToIdleSeconds` を除去。
   stale 上限が「無期限」→ 最大 3600 秒になった。
2. **P3-1-2 レプリカ間無効化** (実装済み): 各レプリカが自分の世代を CouchDB の
   `cache-generation` 文書に publish し、**他レプリカのエントリだけ**を読む。
   いずれかのノードの値が前回見た値と**変わっていたら**キャッシュを落とす。

   **初版は誤りだった (レビュー指摘で判明)**。当初は「全レプリカの最大値 vs 自分の
   カウンタ」で比較し、自分の書き込みに反応しないようにしていた。しかしこの 2 つの
   カウンタは**各プロセスのローカル書き込み回数**であって共有時計ではないので、
   値どうしの比較に意味がない。結果として**書き込みの多いレプリカは自分のカウンタが
   常に先行し、他レプリカの変更に恒久的に反応しなくなる** — 例外的な条件ではなく、
   忙しいレプリカほど確実に壊れる。しかも当時のテスト (`ownWritesDoNotTriggerAClear`)
   がその誤った同値関係を固定していた。

   直し方は「自分を除外する場所」を変えること。除外を**ストア側**で行い、
   invalidator は他ノードの値の変化だけを見る。これで「自分の書き込みでは落とさない」
   と「他レプリカは必ず見る」が同時に成立する。増加ではなく**変化**を見るのは、
   他レプリカ再起動でカウンタが 0 に戻っても取りこぼさないため (減少も変化として
   1 回だけ落とす)。初めて見るノードも変化として扱う — そのノードが自分の起動前に
   何をしたかは知りようがないので、「不明」は「変わった」に倒す。

   publish は CAS せず best-effort — 取りこぼしても次の周期で republish されるので、
   リトライ嵐のほうが高くつく。読み取り側は逆に厳格で、整数として読めない値は 0 に
   丸めず警告して無視する (丸めると「変化なし」に化けて静かな未無効化になる)。

   落とす対象は `aclCache` / `contentCache` に加えて **`objectDataCache`** も含む。
   ローカルの `removeCmisAndContentCache` がこの 3 つを消すので、2 つだけでは非対称に
   なり、compile 済み CMIS オブジェクト (ACL を含む) が残る。
3. **P3-1-3 principal 世代** (実装済み): ACL epoch は ACL 確定でしか進まない
   (allocate の呼び出し元は 1 箇所) ため、パスワード変更・admin フラグ・グループ
   除名は**一切カバーしない**。別カウンタを立て、DAO 層のユーザ/グループの
   create・update・**delete** で進める (削除は剥奪そのものなので落とせない)。
   落とす先も分ける: ACL 世代 → aclCache/contentCache、principal 世代 →
   userItem/groupItem/joinedGroup。

**Codex レビュー (2026-08-10) で追加修正した 7 点**:

- **acknowledge-before-clear の回帰 (自分で入れた)**: 変化を記録してから clear して
  いたため、clear が失敗すると次の poll で「変化なし」と判定され、退避が二度と
  再試行されない。収束機構が犯してはいけない唯一の誤り (やっていない仕事を
  完了扱いする) だった。clear 成功後にだけ記録するよう分離した。
- **importer の ACL 書き込みが世代を上げない**: `AclCacheGeneration.advance` は
  `clearCachesRecursively` にしか無く、applyAcl を迂回する 3 系統 (Zip /
  Filesystem / canonical ingest) の ACL 変更は他レプリカに一切届かなかった。
  DAO 層で一律に上げると通常の更新でも全レプリカが cold になるので、
  **ACL を書く 5 箇所に限って**上げる。
- **publish の永久喪失**: `update(Map)` は例外を握りつぶして null を返すため、
  失敗を検知できていなかった。加えて fixed-delay では同じレプリカが毎回 revision
  race に負け続けうるので「1 poll 分の遅れ」は成立しない。失敗を検知して
  fresh revision で 1 回再試行し、それでも駄目なら WARN を出す。
- **principal 変更で content/objectData が残る**: UserItem/GroupItem も Content
  なので、ローカル更新は contentCache を更新し objectDataCache を消す。
  レプリカ間でも同じ 3 つを落とす。principal 変更は稀なのでコストは無視できる。
- **ノードエントリの永久増加**: nodeId はプロセスごとの UUID なので再起動のたびに
  増え、poll のたびに読み書きする文書が膨らみ、いずれ書き込みがサイズ上限で
  失敗して無効化が止まる。heartbeat を持たせて 1 時間で刈る。
- **poller の静かな死**: `store.repositoryIds()` の例外は per-repository の try の
  外だったため、`scheduleWithFixedDelay` がタスクを永久に止める。全体を包み、
  連続失敗回数を公開する。
- **壊れた値の 0 丸め**: 「無視する」と書きながら 0 に丸めており、前回値が 0 なら
  無効化が起きなかった。ノードごと落として「離脱」扱いにし、次の正常な publish を
  新規ノードとして clear させる (余分な clear 側に倒す)。

自分の検証で見つけた追加 1 点: prune を publish の**後**に呼んでいたため、刈った
結果が書き込まれず永久に効いていなかった。publish の前に移した。

**有界性の言明**: 他レプリカの権限変更がこのレプリカに届く上限は
「ポーリング間隔 (既定 5 秒) + 書き手の publish が届くまで」。従来は「エントリが
期限切れになるまで」で、TTI のため実質無期限だった。

*検証*: CrossReplicaCacheInvalidatorTest — ACL/principal の独立性、自分の書き込みで
落とさない、**自分が 100 回書き込んで先行していても他レプリカの 1 回を検知する**
(旧ロジックを一時的に戻すとこのテストは実際に落ちることを確認済み)、他レプリカ
再起動によるカウンタ後退も変化として検知する、同一世代で二度落とさない、ストア障害
でポーラが死なない。実機では本レプリカで ACL 変更を 5 回行って世代を先行させた上で、
他レプリカが**より小さい**世代 1 を publish しても検知することを確認した。

**P3-2 (D5)**: 管理者用のキャッシュ全消去を配線 (実装は既存)。

### ビルド由来の偽陽性に注意 (2026-08-10 に 1 日で 2 回踏んだ)

台帳の課題とは別に、**検証を誤らせる 2 つの罠**を記録しておく。どちらも
「コードは正しいのにテストが落ちる」形で現れるので、回帰と誤診しやすい。

0. **TCK と同時にライブサーバへ負荷をかけない (再デプロイに限らない)。**
   F3 の規模を上げるための一括投入を走らせたまま全スイートを回したら、TCK の
   `rootFolderTest` が「root の子の数と getDescendants が一致しない」で落ちた
   (しかも 608 秒かかった上で)。投入がテスト中に root 直下へフォルダを作っていたため
   — テストが数えている木がテスト中に変わっていた。**製品の回帰と区別がつかない**。
   投入ツールは run 専用コンテナ配下に作るよう直したが、負荷そのものは避けられないので
   同時実行しないこと。

0.5. **`jstack` は仮想スレッドを見せない。** Tomcat のリクエストは仮想スレッドで走るので、
   負荷の最中に `jstack` を取ると「リクエストスレッドが 2 本」のように出る。**居ないのでは
   なく見えていない**。V1 の調査はこれで一度誤読しかけた。`jcmd <pid> Thread.dump_to_file
   -overwrite -format=json <path>` を使うこと。

1. **テスト実行中に再デプロイしない。** TCK はライブサーバを叩くので、実行中に
   `--build --force-recreate` すると全 TCK が `Connection reset` で落ちる。
   製品の回帰と区別がつかない。
2. **WAR は IDE が監視していない場所でビルドする。** (当初「clean すればよい」と
   書いたが不十分だった — 下記) Cursor の JDT LS が `core/target/classes` を
   Maven と共有しており、**javac は通るが JDT はエラーにする**コードを
   「`Unresolved compilation problem` を throw するクラス」として書き出す。
   `mvn package -DskipTests` は増分なのでそれを再コンパイルせず WAR に混入させる。
   実例: `DataUtil.clonePropertyDefinition` の
   `Cannot cast from List<Choice<capture#N>> to List<Choice<?>>`。
   症状は**空メッセージの CmisRuntimeException** で、アプリログには何も出ない
   (`docker logs <core> | grep -A 3 "Unresolved compilation problem"` で初めて見える)。
   個別の型定義 API は 200 なのに `typeDescendants` だけ 500、という出方をした。
   **前のコミットに戻しても直らない**ので、コード側を疑い続けると時間を溶かす。
   さらに **`clean` でも足りない**: JDT LS は maven の実行中にも書き戻す
   (実測: clean 後の `mvn test` で 17 クラスが汚染され、`DataUtil.class` の mtime が
   maven 実行中の時刻だった)。確実なのは IDE の監視外へ複製してビルド・検証すること。
   検出は `CompiledClassesAreUsableTest` が自動化した — target/classes を走査して
   Eclipse が埋めるマーカ文字列を探す。落ちたら「clean 忘れ」ではなく
   「IDE が書き戻している」と読む。
3. **ビルドの失敗をパイプで潰さない。** `build-outside-ide.sh war 2>&1 | tail -1 && docker compose ... up -d --build`
   は**壊れている**: パイプの終了ステータスは `tail` のものなので常に 0 になり、WAR ビルドが
   落ちても `&&` を通過して**前回の `docker/core/core.war` がデプロイされる**。
   2026-08-11 にこれで 2 回、陰性対照を誤読しかけた (「壊した版が正しく動く」ように見えた)。
   成功は**文字列で**確認する:
   `... | tee /tmp/war.log | grep -q "Copied a verified WAR" && docker compose ...`。
   落ちる原因は多くが 2 の JDT LS 競合 (`Invalid argument` で class を書けない) なので、
   `rm -rf core/target` を挟んでリトライすれば通る。
4. **「スケジュールを assert しているテスト」を flaky と呼んで retry しない。**
   最終スイートで `CloudDirectorySyncServiceImplTest.testStartSync_ConcurrentSameKey_OnlyOneRuns`
   が 1 件落ちた (同一ホストでプローブを走らせていた)。単体では 3/3 通るので flaky に
   見えるが、原因はテスト側の欠陥だった: 4 スレッドを latch で同時に放して「全員が同じ
   result を受け取る」ことを期待していたが、製品が同じ result を返すのは**先行 sync が
   まだ RUNNING の間だけ**で、provider をモックした body は数マイクロ秒で終わる。
   遅れて来た呼び出しが**正当に**新しい sync を始めていた。
   計器を入れて分かったのはさらに悪い話で、元のテストの観測窓の内側では
   **sync body が 1 度も動いていなかった** — executor が遅いおかげで通っていただけ。
   直し方は「重なりを祈る」のをやめて**重なりを作る**こと: 先行 sync の body を
   最初のプロパティ読み出しで押さえ、後続の呼び出しを順番に投げる。
   実行された body の数 (=1) も検査するので、次に同じ形で空振りしたら落ちる。
   製品側のガードを外すと落ちることも確認済み。5/5 で安定。

### レビューで判明した横断的な弱点 (2026-08-09)

**NUL バイト混入を検出する仕組みが自動で動いていなかった。** `scripts/validate-soc-templates.sh`
の Phase 1.4.1 が `.java/.ts/.tsx/.js/.jsx` を走査するが、**手動実行のスクリプト**であり

ようにした (走査対象・除外ディレクトリはスクリプトと一致させ、両者が食い違わないように
してある)。この 1 件は本計画の ACL 課題とは無関係だが、**同じ検証プロセスの穴**なので
ここに記録する。

### Codex レビュー第 2 巡 (2026-08-10) — High 2 / Medium 5

P0-3・P1-2・P2-4・P3-2 を通した直後のレビューで、以下を追加修正した。

- **[High] staleness 判定が全リポジトリ横断だった**: reconcile キューを
  `list(1)` でグローバルに見ており、**他リポジトリの terminal FAILED タスク 1 件**で
  全リポジトリのクエリが恒久的に縮退しえた。リポジトリと status
  (PENDING / LEASED のみ) で絞る `hasOutstandingWork` を足し、2 秒キャッシュも
  リポジトリ単位にした。FAILED は人を待っている状態であって伝播中ではない。
- **[High] `NemakiCachePool.clear` が非安全**: 旧 CacheService を close してから
  差し替えており、同時実行中のリクエストが閉じたインスタンスを掴む。コンストラクタが
  投げれば閉じた service がプールに残る。`HashMap` も非同期化されていなかった。
  **作ってから publish し、最後に close** の順に変え、`ConcurrentHashMap` にした。
  この API を REST で公開したのは今回なので、既存の危険を外に出す前に直した。
- **[Medium] PrincipalLookupCache が無制限**: 論理的に失効しても削除されないため
  JVM 生存中は溜まり続ける。20,000 件の上限を入れ、超えたら全消し
  (失うコストは view クエリ 1 回ずつなので、遅くなるだけで誤らない)。
- **[Medium] レガシー principal 経路が世代を上げない**: `PrincipalDaoService` の
  `createUser` / `createGroup` / `updateUser` / `updateGroup` / `delete` は
  `UserItem`/`GroupItem` 経路と別で、世代を進めていなかった。5 箇所すべてで上げる。
- **[Medium] レプリカ間 poller が principal memo を落とさない**: 世代は JVM ローカル
  なので、他レプリカでの principal 変更に対して 10 秒 TTL が**バックストップではなく
  唯一の無効化**になっていた。poller から `PrincipalLookupCache.invalidateAll()` を
  呼ぶ。
- **[Medium] verdict が `fenced:false` のままだった**: 再起動後の完了済み移行を
  `STAMPED_BY_ANOTHER_RUN` と呼び分けても、派生する `fenced` は false のままで
  スクリプトは完了を確認できない。**完全に fence 済み (remaining == 0 かつ index 非空)
  なら誰が実施したかに関わらず `COMPLETE`** を返すよう改めた。部分的に fence された
  状態は `PARTIALLY_FENCED_NO_RUN_RECORD` とし、「移行が走った証拠」とは主張しない
  (通常の ACL 書き込みが 1 件ずつ bootstrap するため、その推論は成り立たない)。
- **[Low] RELEASE_NOTES の verdict 表**に新しい値と `COMPLETE` の意味変更を反映。
- **[Info→修正] キャッシュキーが区切り文字結合**だった。principal id は外部
  ディレクトリ由来でありうるので、長さ前置の曖昧さのない符号化に変えた。

## 6. 本計画で「やらない」と決めたこと

- **BCrypt cost の引き下げ** — 前計画で棄却済み。
- **CallerRunsPolicy の除去・キュー拡大** — 凍結制約。backpressure は正しい設計。
- **認可経路の非正規化 (子孫への ACL 焼き込み)** — 読み取り時継承が即時性の根拠。

  縮めるか (searcher 再オープン増とのトレードオフ) は**オーナー判断待ちの未決事項**

### ✅ A3 の残差: LRU 上限 2,048 は「チューニング値」ではなく「境界」だった (2026-08-12)

**なぜ測れていなかったか**。memo は 1 回の走査の中だけ生きて走査と一緒に消えるので、
上限が余裕なのか、きつくて捨てているのか、そもそも関係ないのかが**サーバを見ても
分からなかった**。2,048 は議論で決めた値で実測の裏付けが無い、というのが残差の中身。

そこで memo のカウンタをプロセス全体で集計し、`/api/v1/admin/search-index/metrics` に
出した (`traversalMemoEvictions` / `traversalMemoPeakEntries` / `traversalMemoHits` /
`traversalMemoInvalidations` / `traversalMemoMaxEntries`)。**これで運用中に判断できる**。

深さ 12・枝 6・約 301 ノードの木で実測 (`tools/acl-probe/traversal_memo_cap_probe.py`):

| | |
|---|---|
| memo hits | 2,669 |
| **eviction** | **0** |
| 実際に要った working set (peak) | **86 エントリ** |
| 上限 | 2,048 (**4.2% しか使っていない**) |

**分かったこと**: working set は**サブツリーのノード数ではなくフォルダ数**に比例する
(深さ 12 + 枝 72 = 84 ≒ peak 86)。文書は祖先にならないので memo に載らない。
access-order LRU が「共有される上の祖重鎖は残し、枝ごとの一時エントリを落とす」設計
どおりに効いている。

**したがって 2,048 は探索すべきチューニング値ではなく、境界**。
**1 回の走査が触るフォルダが約 2,000 を超えるまで eviction は起きない**。
それを超える規模のサブツリーに ACL を打つ運用では eviction が始まりうるが、
LRU が祖先鎖を優先するので失うのは一時エントリで、代償は再読み込み 1 回。
**`traversalMemoEvictions` を見ればよい** — 0 のままなら上限は 1 円も損をさせていない。

### ✅ 基準 2 の再測定 (2026-08-12)

**合格ラインを取り違えないこと。** 伝播の直列化そのものは設計上残る (executor 構造は
CLAUDE.md の凍結制約)。「小さいサブツリーが大きいものを追い越す」ことは合格条件では
**ない**。P1-1 が約束したのは 1 点だけ:

> リクエストスレッドが他人のサブツリーを走ることは、reconcile が配線されており、
> かつキューへの書込みが成功する限り、起きなくなる。

大サブツリー (1,200 文書) で唯一のワーカーを占有し、小フォルダ 320 件の applyACL を
叩き込んで queue 256 を溢れさせた。結果:

| | |
|---|---|
| caller-runs 発火 (`inlineRunsOnRequestThreads`) | **64** |
| 委譲 (`deferredToReconciliation`) | **64** |
| 溢れた applyACL の応答 | median 1.42s / max 3.84s |

**判定は `>=` ではなく `==`**。委譲カウンタは委譲成功時のみ増えるので、静穏な JVM なら
一致するのが正しい。`>=` を許すと、before スナップショットより前の caller-run の委譲が
後から加算された分が、**キュー書込みに失敗して inline 走査したタスクを覆い隠す**
(Codex 指摘)。多い側に振れたら合格ではなく INCONCLUSIVE。

**応答時間は判定に使わない**。applyACL は submit 時点で返るので測れるのは同期キャッシュ
退避の時間であり、走査の時間ではない。しかも溢れさせるサブツリーは 2 ノードなので、
リクエストスレッドが丸ごと走ってもなお速い。**最初の版はここで big のリクエスト時間と
比較し、自信を持って誤った FAIL を出した**。参考値として出すだけにした。

### 🔴→✅ move 経路には委譲が「一切無かった」 (Codex 指摘、2026-08-12 に修正)

上のプローブをレビューに掛けて出てきた**製品側の欠陥**。プローブの問題ではない。

applyACL と move は**同じ executor**を共有する。applyACL 側は caller-run を検出したら
`deferInlineRefreshToReconciliation` で委譲して返る。**move 側は同じ条件を計算し、
`PropagationProgress` に「inline で走っている」と報告したうえで、そのまま走査していた。**
つまりキュー飽和時、move リクエストは移動したサブツリー全体を自分のリクエスト
スレッドで書き換えていた — 基準 2 が禁じている当のものが、別の入口から成立していた。

**既存テストでは捕まらない形だった。** `InlineRefreshDeferralTest` は
`deferInlineRefreshToReconciliation` を単体で検証しており、欠陥は「呼び出し側の 1 つが
そもそも呼んでいない」こと。ヘルパのテストは、呼び忘れた呼び出し側が何個あっても通る。

修正は applyACL と同じ分岐を move 側に入れるだけ。epoch 的にはむしろ applyACL より
明快で、move 経路はもともと inline settle しない (retained task の re-drive が終端) ため、
委譲が残すタスクはその契約そのもの。

回帰テスト `MovedSubtreeInlineDeferralTest` は**本物の ThreadPoolExecutor を飽和させる**
(same-thread executor での模倣ではない)。`Thread.currentThread() == submittingThread` は
実際の reject でしか成立しないため。証人は **SolrUtil への interaction** —
`getChildren` は submit 前の同期キャッシュ退避walk も使うので証人にならない
(最初そう書いて混線した)。

### ✅ 基準 3 の再測定 (2026-08-12)

931 ノードの伝播 (実測 15.6 秒) を 0.5 秒間隔でポーリングし、各時点の
`estimatedRemainingMs` を**実際の残り時間**と突き合わせた。

| 進捗 | 誤差 (中央値) | ±20% 以内 |
|---|---|---|
| 0-20% | 4.0〜13.4% | 5/5 |
| 20-90% | **0.4〜7.5%** | 21/21 |
| 90-100% | 22.9% | 1/3 |

**判定窓 (進捗 20% 以降) で 21/23 = 91%**、全サンプルでも 93%。合格ライン
「80% 以上が ±20% 以内」を満たす。線引き (進捗 20% 以降 / 80% / ±20%) は
**測定前に宣言**したもので、結果を見てから動かしていない。

90-100% で誤差が跳ねるのは相対誤差の性質どおり (残り時間が小さいので分母が小さい)。
絶対誤差では 1 秒未満。

ETA が null になるサンプルが 1 件あった (走査開始直後、`MIN_SAMPLES_FOR_ETA` 未満)。
これは設計どおりで、**ETA を出さないこと**自体が「まだ言えない」という正しい報告。

### 3.3 の後でよい follow-up (2026-08-17 の最終レビューから)

> **2026-08-17 移管**: 本節の項目は [`v3.3.1-plan.md`](v3.3.1-plan.md) (非破壊) と
> [`authenticity-roadmap.md`](authenticity-roadmap.md) §2 (破壊的) に計画として
> 起こした。着手はそちらを正とする。本節は当時の記録として残す。

- **testuser patch は「有効時の失敗」は今も焼き付く** — `applyPerRepositoryPatch` 内の
  catch が例外を握り潰して正常復帰するため、seed に失敗しても履歴が記録される
  (無効時の焼き付きは S25 で解消済み)。QA fixture なので 3.3 では触らない。
  直すなら catch を throw 化して基底の per-repo catch に任せる (履歴は成功時のみになる)。
- **`currentState` と `lastProbedVersion` は別々に更新される** — 並行 reprobe で
  「状態と版数が同じプローブの結果」という原子的保証は無い。Setup Mode は単一操作者の
  ウィザードなので実害は薄いが、1 つの record にまとめる方が堅牢。

- **Setup Mode 中の `/setup/auth/apply` は version gate の外で動く** (System property の
  書き込みが主で、完了は gate 済みの `mark-complete` を通らないと成立しない)。害は限定的だが、
  補助エンドポイントにも同じ拒否を足すのが筋。
- security-scan の直書き検査は `key = value` (空白あり) 記法と検査対象ファイルの消失を
  検知できない。
- 反証で**棄却**: 「フレッシュ環境で Playwright の permissions/acl 系が testuser 不在により
  落ちる」— testuser の実在有無でサーバ挙動が分岐する経路が無いことを全数列挙で確認。
