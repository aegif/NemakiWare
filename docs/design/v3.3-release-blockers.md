## 0. 判定基準 (プロダクトオーナーと合意済み)

1. **大規模リポジトリで伝播に時間がかかること自体は許容する** (非同期なら数時間でも可)。
2. **その処理がアプリケーション全体の性能を落とすことは許容しない** (隔離が合格条件)。
3. **「いま伝播中である」「あとどれくらいで収束するか」が管理画面か、
   せめてログから判断できること** (可観測性が合格条件)。
4. 権限の**剥奪**が効くまでの遅延は、上限が有界かつ説明可能であること。

現状判定: **1 は合格** (権威データは読み取り時継承のため伝播不要、検索側のみ非同期
追いつき)。**2 は不合格** (§2.2)。**3 は不合格** (§2.4)。**4 は CMIS 経路は合格、
ただし例外が 3 つ** — C4 (revoke 窓の 400)、multi-replica のキャッシュ (D 群)、
RAG 経路 (R1、seed ゲートは確認済みだが未評価領域が残る)。

改善後の再判定手順は §7。

### 決定事項 (2026-08-09、オーナー judgment)

| 論点 | 決定 | 効果 |
|---|---|---|
| 隔離 (基準 2) の合格ライン | **協調的譲歩のみ** (P1-1 第一段) | CLAUDE.md の executor 凍結制約を一切変更しない。repo 単位ワーカー分離・並列化 (P1-1 第二段) は**やらない** |
| C4 (REVOKE 窓の 400) | **staleness 信号でゲートした限定縮退** | cheap-reject を通常経路で維持。滞留 reconcile / epoch 義務があるときだけ部分結果へ |
| 大規模 applyACL の同期応答 | **有界化しない** | **P1-3 は実施しない**。認可の即時性と REVOKE の即時性を一切緩めない。10 万件で応答 +30 秒は管理操作 1 本の遅さとして許容 |
| multi-replica | **3.3 のサポート対象に含める** | P3-1-2 (世代ベース無効化) と D4 (principal 世代) を**実装する**。「単一レプリカ前提で文書化」ではない |

## 1. 現状の伝播モデル (実測で確認済みの事実)

改善を論じる前に、何が**既に正しく速い**かを固定する。

### 1.1 認可 (getObject / ナビゲーション) は即時

実効 ACL は子孫に保存されず、読み取りのたびに祖先を辿って合成される
(`AclSemantics.effectiveAcesInternal` の再帰、AclSemantics.java:225-252)。
親の ACL を変えても子孫の CouchDB 文書は `_rev` ごと不変で、変わるのは読み取り結果だけ。

- 実測: 8 段上の親に applyACL → 子文書の CouchDB 実体は `acl={"entries":[]}` のまま、
  CMIS getAcl は 17ms 後に新 ACE を `isDirect=false` で返した。
- 実測: 122 ノードのサブツリーで applyACL 直後の getObject が 120/120 成功
  (陰性対照ユーザは全期間 403 / 0 件)。
- コスト: warm 1.7ms (深さ非依存、aclCache に memoize)、cold 約 1.4ms/hop
  (depth 60 で 84.8ms)。AclServiceDelegate.java:63-74。

この即時性は applyAcl 内の**同期キャッシュ退避 BFS** (AclServiceImpl.java:1081-1111)
が支えている。ここを非同期化・有界化すると即時性が壊れる。**触るなら代替の無効化
機構とセット**でなければならない (§3 P1-3 — これは基準 1 ではなく**基準 4 の問題**)。

### 1.2 検索 (Solr readers) だけが非同期で追いつく

Solr の `readers` フィールドは実効 ACL の非正規化で、親の ACL 変更後は
子孫 1 件ずつ書き直される (AclServiceImpl.java:489 → :905-1060)。

- 可視化の上乗せは経路で異なる: **readers の fenced write は commitWithin=1000ms
  (AclEpochIndexWriter.java:64,:308) で約 1 秒以内**。autoSoftCommit maxTime=3000ms
  (最大約 3 秒) が効くのは commitWithin を付けない全文書索引経路
  (SolrUtil.indexDocument) だけ。
- 端到端の実測 (applyACL 発行 → 非 admin の検索に全件出るまで、可視化ラグ込み。
  フォルダ ACE 2〜3 件・深さ 1・relationship 無しの条件、陰性対照つき):

  | 子孫数 | GRANT 検索収束 | REVOKE 検索収束 | GRANT getObject | applyACL 応答 |
  |---|---|---|---|---|
  | 10 | 1.01 秒 | **0.06 秒** | 0.08 秒 | 147 / 153 ms |
  | 100 | 2.25 秒 | **0.18 秒** | 0.08 秒 | 204 / 218 ms |
  | 348 | 5.93 秒 | **0.53 秒** | 0.59 秒 | 258 / 259 ms |

  3 点は **T ≈ 1.0 秒 (commitWithin 下限) + S × 約 14ms (書込 ≈ 70 docs/s)** の
  線形にほぼ正確に乗る (予測 1.1 / 2.4 / 5.9 秒)。applyACL 応答は S にほぼ非依存
  (+約 0.3ms/子孫 — B1 の同期 BFS ぶん)。
- **書込レートは ACE 数と深さに強く依存する**。経路解析時の別測定 (ACE 11 件・
  relationship 検査込み) では 41 件 ≈ 4.3 秒、120 件 ≈ 3.58 秒と、1 ノードあたり
  約 100ms (≈10〜30 docs/s) まで落ちた。1 ノードのコスト内訳は CouchDB 生 GET
  2×(1+深さ) 回 + principal lookup 2×ACE 数 + relationship view 2 回 +
  Solr RTG/atomic update 各 1 回 (A3/A4)。
- 外挿: 子孫 10 万件の GRANT 検索収束は **ACE 少なめ・浅い構成で約 25 分、
  ACE 多め・深い構成で 1〜3 時間**。基準 1 により時間そのものは許容範囲 —
  問題は隔離 (§2.2) と可観測性 (§2.4)。

### 1.3 GRANT と REVOKE は非対称 (REVOKE が安全側)

非 admin のクエリは Solr で `readers` fq により絞られ、その後 in-memory の
`getFiltered` (PermissionServiceImpl.java:532-566) が**取り除く方向にだけ**再検査する。

- **REVOKE は即時に効く**。実測: 剥奪直後 t+0.06 秒で検索 0 件 (Solr readers に
  剥奪済みトークンが残った状態でも)。getObject は 65ms で 403。
- **GRANT だけが readers 書き換え + soft commit を待つ**。実測 t+1.0 秒 (S=10)。
  この間「getObject では読めるのに検索に出ない」窓が開く (§2.4 E5)。
- ただし REVOKE にも例外がある: 伝播完了までの間、`numFound` は stale-permissive の
  まま過大で、**ACL scan cap を跨ぐと 400 になる** (C4)。結果行は正しいのに
  「検索が壊れた」ように見える。

### 1.4 applyACL の同期応答時間は子孫数にほぼ依存しない (現規模では)

実測: 子孫 0 件で約 215〜232ms、10 件 147ms、122 ノード 207ms、348 件 258ms、
depth60 チェーン 278ms。
支配項は子孫走査ではなく **ACL-epoch の簿記** (§2.2 B2) と **ACE 数** (+8ms/ACE、
1 ACE 180ms → 22 ACE 363ms。原因は ACE ごとの非キャッシュ principal view lookup、
AclSemantics.java:312-378 → cached 側 PrincipalDaoServiceImpl.java:107-134 が素通し)。

ただしキャッシュ退避 BFS はフォルダごとに `getChildren` view クエリを発行するため
(AclServiceImpl.java:1098)、**子孫が数万件になれば応答時間はそこに支配される**。
上限・ページング・バッチは無い (§2.2 B1)。

## 3. 改善計画

### 凍結制約との整合 (最初に明記する)

CLAUDE.md は「**ThreadPoolExecutor の構造 (キューサイズ・CallerRunsPolicy 等) は
バックプレッシャー維持のため変更不可**」と定める。本計画はこれを次のように解釈し、
**逸脱する提案は明示的にオーナー判断を仰ぐ**:

- キューサイズ・CallerRunsPolicy・キュー実装は変更しない (P1-1 第一段が準拠)。
- `ragAclExecutor` の並列化 (max=1 → N) は fenced write の順序前提の証明なしには
  不可。P1 の主軸は**構造を変えない範囲でのスループット向上** (P1-2) とし、
  並列化はオーナー承認 + 設計精査を条件とする第二段。

### P0 — 権限の正しさ (最優先。性能より先)

**P0-1 (C1): ACLPropagation の意味論を正直にする。objectonly の拒否は行わない。**
初版の「constraintAclPropagationDoesNotMatch で拒否」は**撤回**する。理由は 2 つ:
(1) CMIS 1.1 §2.1.12.3 は propagate 宣言が objectonly の支持を含むと読め、拒否は
逆に非適合を作り込む恐れがある。(2) **自社 UI の継承ブレークが objectonly を送る**
(PermissionResource.java:229-231 が breakInheritance=true で OBJECTONLY を強制、
UI → cmis.ts:1690-1706 → この経路)。拒否すれば継承ブレークが全滅し、
AclResourceIT.testApplyAcl_WithObjectOnlyPropagation_ReturnsOk も赤化する。
代わりにやること:
1. PermissionResource.java:229-231 の **OBJECTONLY 強制を撤去** (継承ブレークの実体は
   :344-350 の inherited=false 拡張であり、propagation 値は無関係 — 独立に実施可能)。
2. capability 宣言を `REPOSITORYDETERMINED` へ変更するかを**オーナー判断に掛ける**
   (NemakiWare の実態 — サーバが読み取り時継承で決める — の正直な表明。
   全 3 値の受理は維持し、constraint 拒否は導入しない)。
3. 空の `constraintAclPropagationDoesNotMatch` には「全値受理は設計判断」の
   コメントを付ける (無言の no-op をやめる)。
*検証*: 自作の統合テストで propagation 3 値それぞれの応答と保存 ACE を assert。
**TCK は検証にならない** (ACLSmokeTest は aclPropagation=null を送り、checkACL は
principal/permissions の非空しか見ない — TCK 緑維持の確認のみ)。

**P0-2 (C2): direct フラグの反転を直す (整理レベル)。**
applyACL で保存する ACE は常に direct=true にする (`new Ace(principalId, permissions,
objectOnly)` → `true`)。**実機再現は陰性で確定済み** — 永続層が direct を保存しない
(CouchContent.java:354-366) ため既存データの移行は**論理的に不要**、wire は compileAcl が
リスト所属から再計算するため互換影響なし。修正の意味は、in-memory 期間・orphan 分岐
(AclSemantics.java:238-247)・ZipExporter 出力 (:321,:363) に残る誤値の除去と、
CMIS §2.1.12.1 (direct=TRUE は直接付与) との整合。hotfix 前倒しは**不要**。
*検証*: 再現テスト (陰性のまま) + orphan 分岐のユニットテスト。

**P0-3 (C4): REVOKE 窓の 400 — 発動条件を観測可能な信号にゲートする。**
初版の「stale-permissive な numFound が cap を押し上げた場合に限り縮退」は
**そのままでは実装不可能** — クエリ時に得られるのは Solr の numFound だけで、
stale による過大か本当に広いクエリかを区別する信号がない。また無条件の縮退は
cheap-reject 設計 (rows=0 プローブで $top=1 でも安価に拒否、
SolrQueryProcessor.java:719-725) を放棄し、cap 行フェッチ + 行ごと getContent
(cap 既定 10,000) を毎回許す DoS 面の後退になる。書き直し:
1. 縮退の発動を **staleness 信号にゲートする**: 当該リポジトリに未収束の
   reconcile タスク / epoch 義務が滞留していること (E7 の既存 API で live 集計可能)。
   信号が無いときは現行どおり 400。
2. 縮退時のページング契約を定義する: 「skipCount が確定行数以上のページは
   **hasMoreItems=false** で返す」+ 応答拡張で truncated=true を通知。
   0 行 + hasMoreItems=true の組は**返さない** (OpenCMIS ItemIterable が
   無限ループするため)。前進保証: 確定 0 行になった場合は最低 1 行確定するまで
   次バッチを取るか、hasMoreItems=false で正直に打ち切る。
3. フェッチ量に上限 (skip+maxItems ベース) を入れ、cheap-reject は信号なし経路で維持。
「over-cap クエリ全体の挙動変更」に踏み込むかは query-scan-cost.md の cap 運用と
統合して**オーナー判断**。
*検証*: REVOKE 直後に cap を跨ぐ統合テスト + ページング完走テスト (クライアント
ループが有限で終わること) + 信号なし時に 400 が維持されること。

**P0-4 (C5): 深さ 50 打ち切りを「静かな失敗」から「観測される失敗」へ。**
(a) WARN に加えメトリクスカウンタ、(b) **打ち切り結果は短 TTL (例 30 秒) の隔離
キャッシュに入れ、通常の joinedGroupCache には入れない** (負キャッシュ全面禁止だと
該当ユーザの全リクエストが毎回 50 ラウンド × view クエリ ≈ 1 秒を再実行する恒常
負荷源になる)。実装注記: 現在の `List<String>` 戻りでは cached 層が打ち切りを判別
できないため、打ち切りシグナルの伝搬手段 (戻り値型 or スレッドローカル) が要る。
上限 50 自体は**作業量上限として**残す (サイクル対策ではない — それは visitedGroups
の仕事。§0 基準 4 の「50 段超は想定外」合意が残置の根拠)。
**決定 (計画からの逸脱を明示)**: 「短 TTL の隔離キャッシュ」は作らず、**打ち切り結果を
一切キャッシュしない**方針にした。打ち切りは誤った答えであり、キャッシュすると
一時的な設定ミスが恒久的な認可エラーになる。再計算コスト (該当ユーザだけ 1 リクエスト
約 1 秒) は、鎖を浅くした瞬間に自動回復することと引き換えに受け入れる。グループを
作れるのは管理者だけなので、一般利用者から到達できる負荷面ではない。

**この修正が直さないこと (明示)**: 深さ 51 段以上のユーザは**依然として上位グループの
ACE を失う** (検索 0 件・getObject 403)。§0 の合意により 50 段超は想定外とし、
直すのは「静かに失敗する」ことだけである。打ち切りは WARN + メトリクス
(`groupResolutionTruncations`) で必ず表面化する。

*検証*: TruncatedGroupResolutionTest (型・カウンタ・cached 層が打ち切りを
キャッシュしないことの配線)。55 段の実挙動は tools/acl-probe/group_depth_cliff.py。

**P0-5 (C6): 親子サイクルを潰す — ただし move ガード単独では防げない。**
1. moveObject に「移動先が自分自身または自分の子孫なら constraint」ガードを追加。
   **TOCTOU 対策**: 当初は「移動対象と移動先の 2 つを ID 順に write lock」で足りると
   考えたが、**これは不十分**。並行レビューの指摘どおり、A を B の**子**の下へ、
   B を A の**子**の下へ動かす組は、ロック集合が {A, B_child} と {B, A_child} で
   交差しないため互いを排除できず、両方がガードを通過してサイクルを作れる。
   ロック集合を広げても解決しない (押さえるべきは祖先チェーン全体で、それこそが
   相手の変更対象)。したがって**フォルダの move はリポジトリ単位の write lock で
   直列化する**。稀な管理操作であり、サイクルの代償 (配下の実効 ACL が計算不能に
   なる) に見合う。文書の move は子を持たずサイクルを作れないので並行のまま。
2. ガード自身の祖先ウォークにも visited + hop 上限 (既存サイクルで無限ループしない)。
3. AclSemantics の読み取り側にも hop 上限 128 + visited を入れ、到達時は epoch 側
   (AclEffectiveEpochService.java:640-675) と同じく **throw = fail-closed**
   (縮退して読めるより、読めない方が安全)。
*検証*: ConcurrentFolderMoveCycleTest — 実スレッド 2 本で敵対的にインターリーブし、
**旧実装 (オブジェクト単位ロックのみ) ではサイクルが再現すること**と、
**直列化するとサイクルが成立しないこと**を両方向で示す。加えて実機で自己子孫 move の
409、自分自身への move の 409、正常な move の 201 を確認済み。

**P0-6 (B3/B4): applyAcl のキャッシュ整合 — write lock では閉じないので世代フェンスで。**
write lock 化で閉じるのは対象オブジェクト自身の窓だけ (B3 参照 — 子孫の read-through は
別ロックキー、祖先ウォークはロック無し)。主軸を変える:
1. **aclCache への put を世代付き compare-and-put にする**。世代は既存の epoch
   カウンタ (P3-1-2 と同じ値)。put 時に「読み始めた時点の世代」を添え、現在世代が
   進んでいたら捨てる。これで子孫を含む再投入レースが閉じる。
2. B4: clearCachesRecursively を try/catch し、失敗時は move 経路と同じ
   CACHE_EVICTION_FAILURE で enqueue。**退避失敗時は再索引を提出せず epoch marker を
   保持して re-drive に委ねる** (move 経路の仕様に合わせる)。
3. write lock 化は行わない (Striped 4096 共有ストライプのため、大サブツリーの
   同期区間が同一ストライプの無関係オブジェクトの全読者を巻き添えにする)。
*検証*: 並行 read + applyAcl のレース再現テスト (retry ループで stale 検出、
世代フェンス導入後に消えること)。

**P0-7 (D3): applyAcl 迂回経路の stale。**
cached DAO の update() 系に aclCache 退避を追加する (最小修正)。
**フォルダ ACL を書く迂回経路は無いことを確認済み** (ZipImporter:552,:1238 /
FilesystemImporter / CanonicalImportServiceImpl とも document・relationship のみ) —
子孫走査の挿入は不要。性能影響は「ACL を変えない update でも退避が走る」ことによる
次回認可時の warm 再計算 ~1.7ms で無視できる。
*検証*: importer で ACL 付き取込 → 同一 JVM で即座に calculateAcl が新 ACL を返す
テスト (新規取込・再取込の両方)。

### P1 — 隔離 (基準 2 の合格ライン)

**P1-1 (A1/A5): 実行面の隔離。二段構え。**

*第一段 (構造凍結内)*: `updateSearchIndexACLRecursively` に協調的譲歩を入れる。
サブツリー走査を N ノードごと (例: 100) に区切り、区切り目でキューに他のサブツリー
タスクが待っていれば残りを継続タスクとして re-submit して返る。
**効果の正確な言明**: 有界化されるのは**キューに空きが生じる場合**であり、キュー
満杯が続く間は継続 re-submit も CallerRuns で即時実行され現状同等 (改善はするが
保証ではない)。
継続タスクの設計条件 (レビューで確定):
- **settle (`settleEpochObligationAfterRefresh`) は最終セグメントのみ**が行う。
  途中セグメントは epochMutationId と cleared 状態を継続タスクへ引き継ぐ
  (現実装のコメントが warn する「先に settle すると crash 窓で子孫回収タスクが
  失われる」stranding を避ける)。
- 途中放棄時は reconcile タスクを残す (既存 TRAVERSAL_FAILURE パターン)。
- 順序が崩れても安全な根拠を明文化: AclEpochIndexWriter はノードごとに権威
  snapshot から readers を再計算し fence が古い書込みを落とすため、re-submit で
  FIFO が崩れても収束と epoch 単調性は保たれる (この根拠自体をコードコメントに書く)。
- **A5 対応が前提条件**: reconcile 側の re-drive にも同じ譲歩を適用するか、
  purge 系 (RAG_PURGE / PWC) と ACL_REINDEX の実行レーンを分離する
  (claimDue の operation 別クォータでも可)。これ無しで委譲を増やすと、
  剥奪系タスクの HOL を悪化させる。
*検証*: A1 の実測 probe (big/small 2 並列 applyACL) を再走し、small の伝播完了が
「N ノード × 実測レート + 定数」以内に収まること。キュー満杯時の挙動も別途測る。

*第二段 (オーナー判断)*: リポジトリ単位のワーカー分離。同一 repo 内の順序性は
保たれ、fence が repo 間の干渉を防ぐ。CLAUDE.md の凍結趣旨との整合をオーナーに
確認の上で。

**P1-2 (A2/A3/A4): 構造を変えずスループットを上げる。見積りは約 2 倍 + α。**
1. **祖先チェーン再利用** (A3): §4.6 が許可するのは **snapshot 側のみ**。
   revalidation の祖先再読は fence の正しさの根拠なので**削減対象外**。
   削減効果は 2×(1+D) → (1+D)+1、つまり**約 2 倍が上限** (初版の 6 倍は誤り)。
   実装条件: step 4 不一致で restart する際は共有チェーンを破棄してフレッシュな
   walk からやり直す。
2. **principal lookup の短 TTL キャッシュ** (A4): 成功のみ・30 秒、
   VerifiedPasswordCache と同型。同期側 +8ms/ACE と非同期側の ACE 比例分が縮む。
   **剥奪整合の注記**: グループ削除直後の最大 30 秒、削除済みグループのトークンが
   readers に残りうる — これは既存の joinedGroupCache (TTI 3600s) より厳しい既定で
   あり基準 4 の範囲内だが、明記して合意を取る。
3. **Solr バッチ** (A2): fenced write の 1 件ずつ `_version_` CAS が正しさの根拠
   なので、バッチ化は epoch 設計の精査が先。1+2 で足りるなら捨てる。
*検証*: 伝播スループット (docs/s、可視化ラグ控除) を before/after で。
正しさは epoch verdict + GRANT/REVOKE の陰性対照付き統合テスト。

**P1-3 (B1): 実施しない (§0 の決定)。**
応答前 BFS を「最大 M ノード」に制限する案は、M+1 件目以降の aclCache に
stale-permissive な実効 ACL が残る = **REVOKE 済みユーザが読める窓**を作る。
オーナー判断により、大規模フォルダの applyACL 応答が子孫数に比例して伸びること
(実測 +0.3ms/子孫、10 万件で約 +30 秒) を受け入れ、**認可の即時性と REVOKE の
即時性を一切緩めない**方針とした。B1 は「既知の特性」として文書化し、実装しない。
将来やるなら pending-aware キャッシュバイパス (設計 §7(a)) が有界化と両立する唯一の
形だが、伝播中の読みが全て cold になるコストを伴う。

**P1-4 (C7): pending gate を非カウントに — 可観測性要件とセットで。**
`retryLaterWithoutCountingAnAttempt` を AclEpochPendingException 由来にも広げる。
ただし非カウント化は「永遠に terminal FAILED に到達しない」を意味するので、
quarantine の前例 (§5.1: quarantineBlockedTasks メトリクス + blocker id) と同型の
**pendingBlockedTasks メトリクス + ブロック元 objectId** を必須とする。
実装注記: 現在 AclEpochPendingException は scheduler の汎用 catch(Exception) で
clean=false に潰されるため、例外型の伝播経路の整備が要る。pending の解消は
scanner (既定 300s) に依存する liveness であることを明記。
**配線 (ここが抜けると偽修正になる)**: 型を投げるだけでは scheduler が
`catch (Exception)` で拾って `retryLater` に落とすため attempts が増え続ける。
`SearchIndexRefreshPendingException` 専用の catch を **generic catch より前**に置き、
`retryLaterWithoutCountingAnAttempt` を呼ぶところまでが 1 セット。

*検証*: RefreshCountersTest — pending のみ / 本物の失敗が混在 / 失敗ゼロ の 3 分岐、
JVM 単位カウンタ、**scheduler が専用 catch を generic より前に持ち
`retryLaterWithoutCountingAnAttempt` を呼び `markFailed` を呼ばないこと**、
**re-drive から型のまま外へ出ること**を検査する。

### P2 — 可観測性 (基準 3 の合格ライン)

**P2-1 (E1/E2)**: 開始 INFO (`repo / root / 推定件数`) + :494 の文言を completed に
修正 + :1110 の件数を INFO へ。ほぼゼロコスト。**最初に入れる**。

**P2-2 (E3)**: `GET /api/v1/admin/search-index/metrics` を新設。
**計画からの変更**: queueDepth / activeCount の直接公開はやめた。executor は所有
サービスの private フィールドで、メトリクスのためだけに API を広げることになる上、
深さのサンプリングはタイミング依存で「溢れた瞬間」を取り逃す。代わりに
**溢れた事実そのもの**を実行地点で観測する `inlineRunsOnRequestThreads` を出す
(CallerRunsPolicy が発火して submit 元スレッドが走らせたら +1)。あわせて
`pendingGateBlocks` (P1-4) と `groupResolutionTruncations` (P0-4) も同じ面に出す —
どちらも「静かに壊れている」ことの唯一の手掛かりになる。

**P2-3 (E4/E5)**: 進行中レジストリ (`PropagationProgress`、repo+root キー)。
`GET /api/v1/admin/search-index/propagation` が実行中の traversal を
`{repositoryId, rootObjectId, expectedNodes, doneNodes, elapsedMs,
estimatedRemainingMs, etaReliable, runningInlineOnRequestThread}` で返す。
ETA は**この traversal で実測したレート**から出す (ノード単価は ACE 数と深さで
1 桁変わるので、固定レートでは大半の木で外れる)。**正直に出さない条件を 3 つ持つ**:
総数が不明 / サンプルが 20 ノード未満 / CallerRuns で追い越しが起きた。いずれも
`etaReliable=false` になる。UI は SchedulerStatusTab の隣に 1 枚 (未着手)。

**P2-4 (E6)**: verdict の `NOT_RUN` を「不明 (この JVM に記録なし)」と
「未実施 (Solr に epoch stamp 痕跡なし)」に分離する。後者は
`effective_acl_epoch` の存在集計 (既に live で数えている) から判定できる。

### P3 — multi-replica の正しさ (§0 の決定により 3.3 のサポート対象。全項目を実装する)

**P3-1**: 順序が重要。
1. **TTI を止める** (ehcache.yml の default から timeToIdleSeconds を外すか、
   acl/content/user/joinedGroup 各キャッシュに timeToLiveSeconds のみを明示)。
   stale 上限が「無期限」→「最大 3600 秒」になる。設定変更のみ、リスク小。
   **既に実装済み** (ehcache.yml の default から timeToIdleSeconds を除去)。
   あわせて docs/MULTI-REPLICA-DEPLOYMENT.md:77 の誤記述を訂正。
2. **世代ベース無効化 — 適用範囲は object-ACL 変更の伝播に限る**。既存 epoch
   カウンタをキャッシュ世代として各レプリカが定期読取 (例: 5 秒) し、進んでいたら
   aclCache / contentCache を clear する。**限界を明記**: epoch カウンタは
   ACL-affecting mutation でしか進まない (allocate の呼び出し元は finalize の
   1 箇所のみ) ため、**パスワード変更・admin フラグ・グループ除名には効かない**。
   設計条件: 自レプリカ起点の世代前進はスキップ (最後に自分が finalize した epoch を
   記録して比較) / バースト時の全落とし頻度に下限 (例: 直近クリアから 60 秒) /
   単一レプリカ構成ではポーラ無効を既定に。剥奪が別レプリカに届く上限 =
   「ポーリング間隔 + crash 時は scanner 周期 300 秒」と説明する。
3. **principal 系の剥奪** (D4): **別世代を実装する** (§0 の決定)。epoch カウンタは
   ACL 変更でしか進まないので、principal 書込み経路 (ユーザ作成・更新・削除、
   グループ membership 変更) で bump する repo 単位の principal-generation 文書を
   立て、各レプリカが同じポーラで読んで userCache / usersCache / groupCache /
   groupsCache / joinedGroupCache を落とす。パスワード変更時の userCache targeted
   退避 (変更レプリカ内) は世代と独立に入れる。
*検証*: 2 レプリカ compose で ACL 変更 / パスワード変更後の stale 上限を実測。

**P3-2 (D5)**: `POST /api/v1/admin/cache/{repo}/clear` を配線 (実装は既存)。
multi-replica では各レプリカに直接叩く運用手順を docs に明記。

### レビューで判明した横断的な弱点 (2026-08-09)

**NUL バイト混入を検出する仕組みが自動で動いていなかった。** `scripts/validate-soc-templates.sh`
の Phase 1.4.1 が `.java/.ts/.tsx/.js/.jsx` を走査するが、**手動実行のスクリプト**であり
ビルドにも git hook にも繋がっていない。同スクリプトのコメント自身が「この RC サイクル
だけで NUL 混入が 2 件」と記録しており、本作業でさらに 2 件見つかった (新規 1・既存 1)。
NUL が 1 つ入ると git はそのファイルを binary と判定し、**以後 diff が消えてレビュー
不能になる**。Java も TypeScript もコンパイルは通るので他に気づく機会がない。

対策として `SourceTreeNulByteTest` を追加し、`mvn test` で毎回リポジトリ全体を走査する
ようにした (走査対象・除外ディレクトリはスクリプトと一致させ、両者が食い違わないように
してある)。この 1 件は本計画の ACL 課題とは無関係だが、**同じ検証プロセスの穴**なので
ここに記録する。

## 6. 本計画で「やらない」と決めたこと

- **BCrypt cost の引き下げ** — 前計画で棄却済み。
- **CallerRunsPolicy の除去・キュー拡大** — 凍結制約。backpressure は正しい設計。
- **認可経路の非正規化 (子孫への ACL 焼き込み)** — 読み取り時継承が即時性の根拠。
- **ragAclExecutor の単純な maxPool=N 化** — 順序前提の証明なしには不可 (P1-1 第二段)。
- **B2 (epoch 4 putBack の圧縮)** — 正典 §11.4 に触れる。別途設計レビュー。
- **objectonly 要求の constraint 拒否** — 仕様上の疑義 + 自社 UI 破壊のため撤回 (P0-1)。
- **commitWithin=1000ms の短縮** — GRANT 可視化窓 (~1 秒) を仕様として受け入れるか、
  縮めるか (searcher 再オープン増とのトレードオフ) は**オーナー判断待ちの未決事項**
  として登録する。決まるまで現状維持。
