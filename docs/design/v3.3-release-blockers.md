## 0. 判定基準 (プロダクトオーナーと合意済み)

1. **大規模リポジトリで伝播に時間がかかること自体は許容する** (非同期なら数時間でも可)。
2. **その処理がアプリケーション全体の性能を落とすことは許容しない** (隔離が合格条件)。
3. **「いま伝播中である」「あとどれくらいで収束するか」が管理画面か、
   せめてログから判断できること** (可観測性が合格条件)。
4. 権限の**剥奪**が効くまでの遅延は、上限が有界かつ説明可能であること。

現状判定: **1 は合格** (権威データは読み取り時継承のため伝播不要、検索側のみ非同期
追いつき)。**2 は不合格** (§2.2)。**3 は不合格** (§2.4)。**4 は CMIS 経路は合格、
ただし例外が 3 つ** — C4 (revoke 窓の 400)、multi-replica のキャッシュ (D 群)、
RAG 経路 (R1、seed ゲートは確認済みだが未評価領域が残る)。

改善後の再判定手順は §7。

### 決定事項 (2026-08-09、オーナー judgment)

| 論点 | 決定 | 効果 |
|---|---|---|

## 1. 現状の伝播モデル (実測で確認済みの事実)

改善を論じる前に、何が**既に正しく速い**かを固定する。

### 1.1 認可 (getObject / ナビゲーション) は即時

実効 ACL は子孫に保存されず、読み取りのたびに祖先を辿って合成される
(`AclSemantics.effectiveAcesInternal` の再帰、AclSemantics.java:225-252)。
親の ACL を変えても子孫の CouchDB 文書は `_rev` ごと不変で、変わるのは読み取り結果だけ。

- 実測: 8 段上の親に applyACL → 子文書の CouchDB 実体は `acl={"entries":[]}` のまま、
  CMIS getAcl は 17ms 後に新 ACE を `isDirect=false` で返した。
- 実測: 122 ノードのサブツリーで applyACL 直後の getObject が 120/120 成功
  (陰性対照ユーザは全期間 403 / 0 件)。
- コスト: warm 1.7ms (深さ非依存、aclCache に memoize)、cold 約 1.4ms/hop
  (depth 60 で 84.8ms)。AclServiceDelegate.java:63-74。

この即時性は applyAcl 内の**同期キャッシュ退避 BFS** (AclServiceImpl.java:1081-1111)
が支えている。ここを非同期化・有界化すると即時性が壊れる。**触るなら代替の無効化
機構とセット**でなければならない (§3 P1-3 — これは基準 1 ではなく**基準 4 の問題**)。

### 1.2 検索 (Solr readers) だけが非同期で追いつく

Solr の `readers` フィールドは実効 ACL の非正規化で、親の ACL 変更後は
子孫 1 件ずつ書き直される (AclServiceImpl.java:489 → :905-1060)。

- 可視化の上乗せは経路で異なる: **readers の fenced write は commitWithin=1000ms
  (AclEpochIndexWriter.java:64,:308) で約 1 秒以内**。autoSoftCommit maxTime=3000ms
  (最大約 3 秒) が効くのは commitWithin を付けない全文書索引経路
  (SolrUtil.indexDocument) だけ。
- 端到端の実測 (applyACL 発行 → 非 admin の検索に全件出るまで、可視化ラグ込み。
  フォルダ ACE 2〜3 件・深さ 1・relationship 無しの条件、陰性対照つき):

  | 子孫数 | GRANT 検索収束 | REVOKE 検索収束 | GRANT getObject | applyACL 応答 |
  |---|---|---|---|---|
  | 10 | 1.01 秒 | **0.06 秒** | 0.08 秒 | 147 / 153 ms |
  | 100 | 2.25 秒 | **0.18 秒** | 0.08 秒 | 204 / 218 ms |
  | 348 | 5.93 秒 | **0.53 秒** | 0.59 秒 | 258 / 259 ms |

  3 点は **T ≈ 1.0 秒 (commitWithin 下限) + S × 約 14ms (書込 ≈ 70 docs/s)** の
  線形にほぼ正確に乗る (予測 1.1 / 2.4 / 5.9 秒)。applyACL 応答は S にほぼ非依存
  (+約 0.3ms/子孫 — B1 の同期 BFS ぶん)。
- **書込レートは ACE 数と深さに強く依存する**。経路解析時の別測定 (ACE 11 件・
  relationship 検査込み) では 41 件 ≈ 4.3 秒、120 件 ≈ 3.58 秒と、1 ノードあたり
  約 100ms (≈10〜30 docs/s) まで落ちた。1 ノードのコスト内訳は CouchDB 生 GET
  2×(1+深さ) 回 + principal lookup 2×ACE 数 + relationship view 2 回 +
  Solr RTG/atomic update 各 1 回 (A3/A4)。
- 外挿: 子孫 10 万件の GRANT 検索収束は **ACE 少なめ・浅い構成で約 25 分、
  ACE 多め・深い構成で 1〜3 時間**。基準 1 により時間そのものは許容範囲 —
  問題は隔離 (§2.2) と可観測性 (§2.4)。

### 1.3 GRANT と REVOKE は非対称 (REVOKE が安全側)

非 admin のクエリは Solr で `readers` fq により絞られ、その後 in-memory の
`getFiltered` (PermissionServiceImpl.java:532-566) が**取り除く方向にだけ**再検査する。

- **REVOKE は即時に効く**。実測: 剥奪直後 t+0.06 秒で検索 0 件 (Solr readers に
  剥奪済みトークンが残った状態でも)。getObject は 65ms で 403。
- **GRANT だけが readers 書き換え + soft commit を待つ**。実測 t+1.0 秒 (S=10)。
  この間「getObject では読めるのに検索に出ない」窓が開く (§2.4 E5)。
- ただし REVOKE にも例外がある: 伝播完了までの間、`numFound` は stale-permissive の
  まま過大で、**ACL scan cap を跨ぐと 400 になる** (C4)。結果行は正しいのに
  「検索が壊れた」ように見える。

### 1.4 applyACL の同期応答時間は子孫数にほぼ依存しない (現規模では)

実測: 子孫 0 件で約 215〜232ms、10 件 147ms、122 ノード 207ms、348 件 258ms、
depth60 チェーン 278ms。
支配項は子孫走査ではなく **ACL-epoch の簿記** (§2.2 B2) と **ACE 数** (+8ms/ACE、
1 ACE 180ms → 22 ACE 363ms。原因は ACE ごとの非キャッシュ principal view lookup、
AclSemantics.java:312-378 → cached 側 PrincipalDaoServiceImpl.java:107-134 が素通し)。

ただしキャッシュ退避 BFS はフォルダごとに `getChildren` view クエリを発行するため
(AclServiceImpl.java:1098)、**子孫が数万件になれば応答時間はそこに支配される**。
上限・ページング・バッチは無い (§2.2 B1)。

## 3. 改善計画

### 凍結制約との整合 (最初に明記する)

CLAUDE.md は「**ThreadPoolExecutor の構造 (キューサイズ・CallerRunsPolicy 等) は
バックプレッシャー維持のため変更不可**」と定める。本計画はこれを次のように解釈し、
**逸脱する提案は明示的にオーナー判断を仰ぐ**:

- キューサイズ・CallerRunsPolicy・キュー実装は変更しない (P1-1 第一段が準拠)。
- `ragAclExecutor` の並列化 (max=1 → N) は fenced write の順序前提の証明なしには
  不可。P1 の主軸は**構造を変えない範囲でのスループット向上** (P1-2) とし、
  並列化はオーナー承認 + 設計精査を条件とする第二段。

### P0 — 権限の正しさ (最優先。性能より先)

**P0-1 (C1): ACLPropagation の意味論を正直にする。objectonly の拒否は行わない。**
初版の「constraintAclPropagationDoesNotMatch で拒否」は**撤回**する。理由は 2 つ:
(1) CMIS 1.1 §2.1.12.3 は propagate 宣言が objectonly の支持を含むと読め、拒否は
逆に非適合を作り込む恐れがある。(2) **自社 UI の継承ブレークが objectonly を送る**
(PermissionResource.java:229-231 が breakInheritance=true で OBJECTONLY を強制、
UI → cmis.ts:1690-1706 → この経路)。拒否すれば継承ブレークが全滅し、
AclResourceIT.testApplyAcl_WithObjectOnlyPropagation_ReturnsOk も赤化する。
代わりにやること:
1. PermissionResource.java:229-231 の **OBJECTONLY 強制を撤去** (継承ブレークの実体は
   :344-350 の inherited=false 拡張であり、propagation 値は無関係 — 独立に実施可能)。
2. capability 宣言を `REPOSITORYDETERMINED` へ変更するかを**オーナー判断に掛ける**
   (NemakiWare の実態 — サーバが読み取り時継承で決める — の正直な表明。
   全 3 値の受理は維持し、constraint 拒否は導入しない)。
3. 空の `constraintAclPropagationDoesNotMatch` には「全値受理は設計判断」の
   コメントを付ける (無言の no-op をやめる)。
*検証*: 自作の統合テストで propagation 3 値それぞれの応答と保存 ACE を assert。
**TCK は検証にならない** (ACLSmokeTest は aclPropagation=null を送り、checkACL は
principal/permissions の非空しか見ない — TCK 緑維持の確認のみ)。

**P0-2 (C2): direct フラグの反転を直す (整理レベル)。**
applyACL で保存する ACE は常に direct=true にする (`new Ace(principalId, permissions,
objectOnly)` → `true`)。**実機再現は陰性で確定済み** — 永続層が direct を保存しない
(CouchContent.java:354-366) ため既存データの移行は**論理的に不要**、wire は compileAcl が
リスト所属から再計算するため互換影響なし。修正の意味は、in-memory 期間・orphan 分岐
(AclSemantics.java:238-247)・ZipExporter 出力 (:321,:363) に残る誤値の除去と、
CMIS §2.1.12.1 (direct=TRUE は直接付与) との整合。hotfix 前倒しは**不要**。
*検証*: 再現テスト (陰性のまま) + orphan 分岐のユニットテスト。

**P0-3 (C4): REVOKE 窓の 400 — staleness でゲートした限定縮退。実装済み。**

cap そのものは緩めない。変えたのは「多すぎる」と「伝播中で数え過ぎている」を
区別できるようにした点だけ。

1. cap 超過を検出したとき、**そのときだけ** `AclPropagationStaleness` に問う。
   本レプリカで走行中の伝播 (`PropagationProgress`、メモリ内で無料) か、
   耐久化された reconcile キューが空でないか。どちらも無ければ従来どおり 400。
   **通常経路は 1 命令も変わらない** — cheap-reject (rows=0 プローブで $top=1 でも
   安価に拒否) が保たれ、追加コストは元々失敗する予定だったクエリだけが払う。
2. 縮退時は cap 内の確定行を返し、`truncatedByAclScanLimit` 拡張を付け、WARN を出し、
   メトリクス `queriesDegradedByAclScanLimit` を増やす。行そのものは in-memory gate を
   通っているので正しい。変わるのは「総数」の意味だけで、numItems は下界になる。
3. `hasMoreItems` は元々 cap 内の確定集合に対して計算されるので、窓の終端で false に
   なる。**0 行 + hasMoreItems=true を返す組み合わせは発生しない**。
4. 信号が読めない (キュー照会が失敗した) ときは fail-closed で「収束済み」とみなし、
   従来どおり 400 にする。検証できない言い訳で部分結果を返さない。

*検証*: SolrQueryProcessorScanCapTest — 伝播中のみ縮退すること、伝播していなければ
従来どおり拒否すること、cap 内のクエリは伝播中でも truncated にしないこと
(無関係なクエリまで疑わしくすると全ページが信用できなくなる)、rows=0 プローブと
cap 上限のフェッチが維持されること。既存 9 件は「縮退を許さない」で全て通る。

**P0-4 (C5): 深さ 50 打ち切りを「静かな失敗」から「観測される失敗」へ。**
(a) WARN に加えメトリクスカウンタ、(b) **打ち切り結果は短 TTL (例 30 秒) の隔離
キャッシュに入れ、通常の joinedGroupCache には入れない** (負キャッシュ全面禁止だと
該当ユーザの全リクエストが毎回 50 ラウンド × view クエリ ≈ 1 秒を再実行する恒常
負荷源になる)。実装注記: 現在の `List<String>` 戻りでは cached 層が打ち切りを判別
できないため、打ち切りシグナルの伝搬手段 (戻り値型 or スレッドローカル) が要る。
上限 50 自体は**作業量上限として**残す (サイクル対策ではない — それは visitedGroups
の仕事。§0 基準 4 の「50 段超は想定外」合意が残置の根拠)。
**決定 (計画からの逸脱を明示)**: 「短 TTL の隔離キャッシュ」は作らず、**打ち切り結果を
一切キャッシュしない**方針にした。打ち切りは誤った答えであり、キャッシュすると
一時的な設定ミスが恒久的な認可エラーになる。再計算コスト (該当ユーザだけ 1 リクエスト
約 1 秒) は、鎖を浅くした瞬間に自動回復することと引き換えに受け入れる。グループを
作れるのは管理者だけなので、一般利用者から到達できる負荷面ではない。

**この修正が直さないこと (明示)**: 深さ 51 段以上のユーザは**依然として上位グループの
ACE を失う** (検索 0 件・getObject 403)。§0 の合意により 50 段超は想定外とし、
直すのは「静かに失敗する」ことだけである。打ち切りは WARN + メトリクス
(`groupResolutionTruncations`) で必ず表面化する。

*検証*: TruncatedGroupResolutionTest (型・カウンタ・cached 層が打ち切りを
キャッシュしないことの配線)。55 段の実挙動は tools/acl-probe/group_depth_cliff.py。

**P0-5 (C6): 親子サイクルを潰す — ただし move ガード単独では防げない。**
1. moveObject に「移動先が自分自身または自分の子孫なら constraint」ガードを追加。
   **TOCTOU 対策**: 当初は「移動対象と移動先の 2 つを ID 順に write lock」で足りると
   考えたが、**これは不十分**。並行レビューの指摘どおり、A を B の**子**の下へ、
   B を A の**子**の下へ動かす組は、ロック集合が {A, B_child} と {B, A_child} で
   交差しないため互いを排除できず、両方がガードを通過してサイクルを作れる。
   ロック集合を広げても解決しない (押さえるべきは祖先チェーン全体で、それこそが
   相手の変更対象)。したがって**フォルダの move はリポジトリ単位の write lock で
   直列化する**。稀な管理操作であり、サイクルの代償 (配下の実効 ACL が計算不能に
   なる) に見合う。文書の move は子を持たずサイクルを作れないので並行のまま。
2. ガード自身の祖先ウォークにも visited + hop 上限 (既存サイクルで無限ループしない)。
3. AclSemantics の読み取り側にも hop 上限 128 + visited を入れ、到達時は epoch 側
   (AclEffectiveEpochService.java:640-675) と同じく **throw = fail-closed**
   (縮退して読めるより、読めない方が安全)。
*検証*: ConcurrentFolderMoveCycleTest — 実スレッド 2 本で敵対的にインターリーブし、
**旧実装 (オブジェクト単位ロックのみ) ではサイクルが再現すること**と、
**直列化するとサイクルが成立しないこと**を両方向で示す。加えて実機で自己子孫 move の
409、自分自身への move の 409、正常な move の 201 を確認済み。

**P0-6 (B3/B4): 世代フェンスでキャッシュ再投入レースを閉じる。実装済み。**
write lock 化では対象オブジェクト自身の窓しか閉じない (子孫の読み手は別ロックキー、
祖先ウォークは無ロック、退避 BFS も無ロック)。押さえるべきはサブツリー全体で、
それは走査中ずっと保持できない。代わりに**計算に日付を付ける**:

1. 読み手は祖先を辿る前に世代を記録し、`aclCache` への put はその世代がまだ現行の
   ときだけ行う (`AclServiceDelegate.putIfStillCurrent`)。掃過を跨いだ計算は
   公開を断られ、次の読みで再計算されるだけで済む。
2. 世代を上げるのは `clearCachesRecursively` の**冒頭** — 退避より前。後ろに置くと
   掃過中の読み手が「まだ現行」と判定される窓が残る。呼び出し元 (applyAcl / move /
   reconcile) を一括で覆える位置でもある。
3. 世代を記録し忘れた呼び出しは fail-closed で拒否する。
4. B4: applyAcl の退避失敗を捕捉し、move 経路と同じ CACHE_EVICTION_FAILURE で
   enqueue する。**索引リフレッシュは提出しない** — 退避できなかったキャッシュから
   readers を再計算すると、その stale 値を Solr に焼き込んで恒久化してしまう。

*検証*: AclCacheGenerationTest — 実スレッド 2 本で「読み手開始 → 書き手が世代を上げて
掃過 → 読み手が公開を試みる」を走らせ、再投入されないことを確認。あわせて
`aclCache.put` がファイル内に 1 箇所 (ガード付き) しか無いこと、世代 bump が退避より
前にあることも固定する。

**P0-7 (D3): applyAcl 迂回経路の stale。**
cached DAO の update() 系に aclCache 退避を追加する (最小修正)。
**フォルダ ACL を書く迂回経路は無いことを確認済み** (ZipImporter:552,:1238 /
FilesystemImporter / CanonicalImportServiceImpl とも document・relationship のみ) —
子孫走査の挿入は不要。性能影響は「ACL を変えない update でも退避が走る」ことによる
次回認可時の warm 再計算 ~1.7ms で無視できる。
*検証*: importer で ACL 付き取込 → 同一 JVM で即座に calculateAcl が新 ACL を返す
テスト (新規取込・再取込の両方)。

### 🟡 A6: ロック順の逆転によるリポジトリ全停止 (計測して大半を除去、残りは可視化)

**2026-08-10 に実機で発生。リポジトリが復旧不能に固まった。** 今回の変更とは無関係の
既存欠陥だが、**基準 2 の最も重い違反**なので v3.3 のブロッカーに上げた。

観測できたのは「どのスレッドがどの行で park したか」までで、**ロックの identity は
採れていなかった**。当初はここから `deleteTree` (親 write → 子 write) と
`getFolderParent` (子 read → 親 read) のペアだと推定したが、**この推定は外れていた**
(レビュー指摘。後述の実測にそのペアは 1 件も出ていない)。推定で直していたら、
直った気になって別の環が残っていた。

#### なぜ推定が危険だったか

ロックは **striped** で、`ReentrantReadWriteLock` が 4096 本しかない。
リポジトリには 6 万件超のオブジェクトがあるので、**無関係な 2 オブジェクトが同じ
ロックを共有する**。「常に祖先を先に取る」のような**階層で表現した順序規則は、
そもそも問題に届かない** — 環の両端は親子とは限らないため。

#### 計測 (推定をやめて事実を採った)

`LockOrderMonitor` を入れて実機に投入し、全テストスイートを 1 周させた。
検出するのは 2 つ:

- **upgrade**: 同一スレッドが read 保持のまま write を要求。
  `ReentrantReadWriteLock` は昇格できないので**確実・即時・恒久の自己デッドロック**。
  取得の**前**に報告する (取得は戻ってこないので、後で報告する実装では何も残らない)。
- **inversion**: あるスレッドが A→B、別のスレッドが B→A。
  まだ刺さっていなくても報告する。刺さるのを待つのは、障害で学ぶのと同じ。

| | 修正前 | 修正後 |
|---|---|---|
| upgrade | 0 | 0 |
| inversion (件数) | **217** | 23 |
| inversion (相異なるペア) | **60** | 6 |

検出されたペアには**ルートフォルダが含まれていた**。例外的な相互作用ではなく、
日常のトラフィックで起きていた。

#### 原因は 1 つの形だった

スタックを集計すると発生元は 4 箇所で、**すべて同じ形**だった:
**順序付きセットの「外側」で取ったロックを、そのセットの間ずっと保持している**。
セット内をソートしても、セットの外で取ったロックはそのセットに対して順序を持たない。

| 発生元 | 件数 |
|---|---|
| `NavigationServiceImpl.getChildrenInternal` (子の bulkLock) | 51 |
| `NavigationServiceImpl.getObjectParents` | 6 |
| `NavigationServiceImpl.getFolderParent` | 2 |
| `SolrQueryProcessor` の検索結果 bulkLock (`DiscoveryServiceImpl.query` 経由) | 1 |

#### 対処

1. **`readLocks` / 新 `orderedLocks` がストライプ順に揃える**。以前は呼び出し側の
   リスト順 (= Solr が返した順) のままで、Guava が `bulkGet` で明示的に警告している
   まさにその使い方だった。同一ストライプに落ちる id は 1 つに畳む
   (二重取得すると `bulkUnlock` が 1 回しか返さず、スレッド寿命ぶん保持が漏れる)。
2. **`getFolderParent` / `getObjectParents`**: 親をロック前に解決し、
   子と親を**1 つの順序付きセット**として取る。親はロック下で読み直し、
   **一致しなければ解放して再プレビューからやり直す** (有界リトライ、尽きたら 409)。
   初版は不一致を即 409 にしていたが、それは「move をロック待ちで見送った読み取り」——
   旧コードなら正しい新親を返せていたケース——を決定的に失敗させる劣化だった
   (レビュー指摘 NAV-002)。リトライで通常ケースは正しい新親に収束し、
   409 が出るのは move が続いている間だけになる。
3. **`getChildren`**: フォルダのロックを**フォルダ自身の compile までに狭め**、
   `getChildrenInternal` が **{フォルダ}∪{子}** を 1 セットで取る (両分岐)。
   空フォルダの早期 return 分岐にも存在確認を追加 (レビュー指摘 NAV-001/TQ-4)。
   deleteTree は子を先に消すので「窓の間に削除されたフォルダ」は子 0 件として
   まさにこの分岐に入り、ガード無しでは 404 のはずが空の 200 になっていた。
4. **`bulkLock` を有界化**: セット 1 試行 30 秒・総 300 秒 (試行の締切は総締切で
   打ち切られるので 300 秒は**厳密な**上限)、**試行の間で全解放**、最終的に
   `LockAcquisitionTimeoutException`。これが**恒久停止そのものを塞ぐ**。
   セット内をいくら揃えても、外側の保持を通って閉じる環はセットの中からは見えない。
   見えないものを順序で直すことはできないが、**待ち続けないことはできる**。
   タイムアウトした側がセットを手放せば、相手は前に進める。

#### 検出器自体の欠陥を直した (レビュー指摘)

初版は**保持スタックの先頭としか比較していなかった**。A→B→C を保持している状態で
A→C を記録しないので、「外側のロックを内側のセットの間ずっと保持する」という
**まさにこの問題の形が見えない**。「発生元は 4 箇所」は「この不完全なモデルで見えた
4 箇所」であって、それ以上の主張ではなかった。**最古 16 本** (= 外側スコープ) と
比較するよう修正。16 本で打ち切るのは意図的で、コストを抑えつつ「外側保持 vs 内側
セット」という今回の障害の形は必ず比較対象に入る。打ち切りが起きた回数は
`depthLimitedAcquisitions` として `/lock-order` に出るので、「inversion 0」は
「どれだけ見た上での 0 か」と併読できる。

第 3 ラウンドのレビューでさらに 3 つ直した:

- **upgrade 判定が mode を見ていなかった**。W→R→W (合法な降格 + 再入 write) を
  「確実な自己デッドロック」と誤報する。同一ストライプの保持に **write が 1 つも
  無い**ときだけ upgrade とするよう修正。
- **確定した upgrade に 300 秒払っていた**。判定した瞬間に失敗が確定しているのに
  単独 lock() は上限まで待ち、その間キュー先頭の writer が後続 reader を全部止める。
  `beforeAcquire` が verdict を返し、**即時に拒否**するようにした (誤検出を先に
  直したから安全にできる — 逆順だと合法な取得を即時 503 にしていた)。
- **findings がオブジェクトペアでキーされ基数無限**だった。ホットな 1 箇所が
  組み合わせごとに finding を鋳造し、上限 500 を埋めた後は新規 (将来の upgrade 含む)
  が**ログにも出ない**。**ストライプペア**でキーし直し、上限到達は一度だけ ERROR +
  `findingsCapReached` で可視化。加えて `released(stripe, mode)` (mode 無視の解放は
  降格パターンで幻の write を残す)、`unlocksWithoutHold` カウンタ (別ラッパ経由の
  unlock は旧実装と違い**解放されずリークする**ようになったので、その唯一の症状)。

そのため**修正前後の件数は直接比較できない** (計測器が変わっている)。
比較できるのは発生元の数と形:

| | 修正前 | 修正後 |
|---|---|---|
| 発生元 | 4 箇所 | 3 箇所 |
| 形 | 外側の単独ロック + 内側のセット | **同型が残存** (getDescendants が各階層のセットを保持したまま次の階層のセットを取る) + セット同士 |
| upgrade | 0 | 0 |
| **リクエストの恒久停止** | **しうる** | **しない** (有界化) |

(旧版のこの表は残存形を「入れ子のセット同士」とだけ書いていたが、実測ログの
残存 3 箇所には外側保持の形も含まれる。除去したのは Navigation 系 4 箇所の
「単独ロック + セット」であって、形そのものが絶滅したわけではない。)

#### 上限は 2 つに分けた (自分の誤りを 2 回踏んで確定した)

最初、単独ロックも 30 秒で切った。結果、MultiThreadTest の**正当な輻輳**
(同一フォルダへの並行 create) が失敗した。デッドロックではなく、混んでいただけ。
次に、セットの上限を「3 回試行」に固定したままにしたら、今度は
`getFolderParent` の 2 ロックが 30 秒×3 で足りず、通常の読み取りが 63 件失敗した。

**リトライは環を壊すためのもの、総時間は輻輳のためのもの**で、混ぜると
「混んでいる」が「壊れている」に見える。分離した:

| | 値 | 役割 |
|---|---|---|
| セットの 1 試行 | 30 秒 | この周期で**全解放**する。解放が環を壊す |
| セットの総時間 | 300 秒 | 輻輳をどこまで待つか |
| 単独ロック | 300 秒 | デッドロック破りのみ。15 秒で WARN (失敗ではない) |

実測: 全スイート 1 周で「30 秒で取れず再試行」の WARN が 62 件、
**例外は 0 件**、テスト全緑 (当時 4,890 件、最終 4,904 件)。つまり輻輳は
待ち切れており、上限は本当にデッドロック用の網になっている。
なお上限系は**実測だけに頼らず単体で失敗経路を実行する**ようにした
(注入可能な上限で: 単独タイムアウトの throw と 503 契約、bulk タイムアウト後の
全解放、試行が総締切で打ち切られること — `ThreadLockServiceImplTest`)。
「例外 0 件」は網が誤爆しない証拠ではあっても、網が受け止められる証拠では
なかったため (レビュー指摘 TQ-1)。

#### 残っているもの (可視化済み・恒久停止はしない)

**修正済み検出器での再計測** (2026-08-11、新 WAR + 全スイート 1 周):

| | 値 |
|---|---|
| inversion (発生回数) | 1,815 |
| inversion (相異なるストライプペア) | 162 |
| upgrade | 0 |
| depth 打ち切り (`depthLimitedAcquisitions`) | 12,798 |
| `unlocksWithoutHold` | 0 |
| 例外 (LockAcquisitionTimeout) | 0 |
| テスト | 4,904 / 0 failures |

旧検出器の「23 件 / 6 ペア / 3 箇所」は**大幅な過小計上だった** — 盲点 (先頭比較・
深さ 16 で照合ごとスキップ) が数字を作っていた。レビューの「3 箇所という主張は
このモデルの範囲でしか言えない」はそのとおりだった。

正しい検出器での発生元は**事実上 1 箇所**:

- **161/162**: `getDescendantsInternal` → `getChildrenInternal` — 階層を降りながら
  各階層の {フォルダ}∪{子} セットを保持したまま次の階層のセットを取る、外側保持の
  入れ子。ルートフォルダを含むペアが大半 (descendants はルートから歩くため)。
- **1/162**: `VersioningServiceImpl.evictLatestVersionCache` — オブジェクト write を
  保持したまま latest の write を取る意図的な入れ子 (タイムアウトしても伝播させない
  設計に変更済み。上の変換状況表を参照)。

(旧版はここに「getObjectParents / getFolderParent の compile 中に内側で取られる
ロック」という発生元を挙げていたが、**そのような取得はコード上存在しない** —
レビュー指摘 A6-3。リトライ化後の再計測では Navigation の親子ペア系は消えている。)

`bulkLock` が有界なので、**これらが環を作ってもリポジトリは止まらない** —
片方がタイムアウトして解放し、リクエスト 1 本が retryable な失敗になる。
恒久停止 → 一過性の失敗、への格下げは達成できている。

**多重ロック点の変換状況** (レビュー指摘を受けて追加対応):

| 箇所 | 状態 |
|---|---|
| `PolicyServiceImpl` (object + policy) | ✅ 1 つの順序付きセットに変換 |
| `ObjectServiceImpl.moveObject` | ✅ id 順 → **ストライプ順**に変換。id 順はストライプの順序を何も保証しない |
| `VersioningServiceImpl` の内側 `latestLock` | ✅ 対処済み (別問題として)。checkIn / cancelCheckOut の内側 latestLock は**ミューテーション確定後**にあり、そこで 503 を出すと「safe to retry」が偽になる (再試行は PWC 消滅で失敗し、成功した事実をクライアントが知れない) 上にキャッシュ退避も飛ぶ — レビュー 3 者が一致して指摘。タイムアウト時は**ロック無しで退避して成功を報告**するよう変更 (退避は冪等で、ロック下でも再取込レースは防げていなかった) |
| `ObjectServiceInternalImpl.deleteObjectInternal` の再帰 | ⚠️ 未変換。**構造上バッチにできない** (親を保持したまま子へ降りる)。有界化で恒久停止はしない |

**単独 `lock()` も有界**になったので、単独ロックだけで構成される環も恒久停止しない。

#### 出荷判断

達成: 観測された停止の**再現と原因特定** (推定ではなく実測)、主要因の除去、
そして**恒久停止という故障モードそのものの除去** — すべての取得が有界になったので、
環ができても片方がタイムアウトして解放し、リクエスト 1 本が retryable な
`CmisServiceUnavailableException` (503) になる。リポジトリは止まらない。
(「すべて」は第 3 ラウンドで文字どおりになった: 呼び出し元ゼロのまま無防備だった
`lockInterruptibly` も同じ上限に入れた。)

**503 が 503 のまま届くことも全経路で確認・修正した** (レビュー指摘 A6-EX 系)。
Browser binding のコンテンツ取得だけ catch (Exception) → 500 で信号を失っていた。
/api/v1 は `CmisServiceUnavailableException` の getCode()==0 を「クライアントエラーに
非ず」= 500 と写像していた上、リソース層の catch (Exception) → internalError 包みでも
消えていた — マッパに型分岐と cause 連鎖の復元を入れた (cause を渡さない一部の
wrap 箇所 (136 中 29) は救えない。残余として記録)。bulkUpdateProperties は
例外を**無言で**畳んでいた (対象がログ 0 行で結果から消える) → WARN + retryable の
明示。deleteTree はロックタイムアウトを「orphan、CouchDB 直接掃除」と誤誘導する
ログにしていた → transient と分類し「再実行せよ」に変更。

残るのは「輻輳下で読み取りが 503 で失敗しうる」こと (300 秒待っても取れない場合)。
実測ではスイート 1 周で 0 件。**恒久停止 → 一過性の失敗**という格下げが A6 の到達点で、
「逆転が 1 件も無い」ではない。逆転は実質 1 箇所 (getDescendants の入れ子。162 ペア中
161) + versioning の意図的入れ子 1 件が残り、`/v1/admin/search-index/lock-order` で
見える (上の再計測表を参照)。

第 5 ラウンド (最終検証) で見つかった退行・新規 6 件も修正済み:
親リトライの例外経路でロックが恒久リーク (**A6 の主張を直接壊す退行**。回帰テストで
固定)、`__…__` パターン一致による named lock がリクエスト由来 id で無制限に増える
(許可リスト方式に変更 — named 扱いは閉じた列挙で、クライアント id は従来どおり
ストライプへ)、割込み済みスレッドの upgrade 拒否が InterruptedException に先行する、
バックオフ睡眠が総締切を突き抜ける (これで 300 秒は本当に厳密)、cause 循環でマッパが
回り続ける (深さ 16 で打ち切り)、named lock の WARN が律速されない。

**受容済みの残余** (いずれも有界):
- checkIn / cancelCheckOut のロック無し退避は、変更前に読んだ読者の stale 再取込に
  先行され得る。5 秒後の二次退避で窓を狭め、キャッシュ TTL が最終防波堤
  (「503 で成功を隠す」よりは stale 数秒〜TTL の方を取った)。
- /api/v1 の cause を渡さない wrap 箇所 (29/136) では 503 が 500 に落ちる。
- 検出器の深さ 16 打ち切り (`depthLimitedAcquisitions` で可視)。

出荷するなら、オーナーが受容するのは
「リポジトリ全停止は無くなった。代わりに極端な輻輳下で個別リクエストが 503 になる」。

### P1 — 隔離 (基準 2 の合格ライン)

**P1-1 (A1/A5): 実行面の隔離。実装済み — ただし手段を差し替えた。**

*当初案 (協調的譲歩) を採らなかった理由*。
オーナー決定は「第一段 = 協調的譲歩のみ」だった。実装に入って設計条件を詰めた
結果、**この手段は肝心のケースで効かない**ことが確定したので、同じ制約の中で
別の手段に差し替えている。判断の根拠は次のとおり。

譲歩とは「N ノードごとに区切り、残りを継続タスクとして re-submit して返る」こと。
re-submit 先は同じ `ragAclExecutor` である。**キューが満杯だから CallerRuns が
発火している**のだから、その継続 re-submit もまた CallerRuns で同じスレッドに
即座に返される。つまり基準 2 が壊れる唯一の局面 (リクエストスレッドがサブツリー
全走査を負う) では、譲歩は 1 ノードも仕事を減らさない。当初案自身が
「キュー満杯が続く間は現状同等」と正直に書いていたが、**それは効果の限界ではなく
効果の不在**だった。

*実装した手段: inline 流出の耐久キューへの委譲*。
タスク本体で `Thread.currentThread() == submittingThread` を見て CallerRuns で
リクエストスレッドに落ちたことを検出したら、走査を **一切せず** に root を
reconcile キューへ `TRAVERSAL_FAILURE` + epoch 付きで積んで返る。

- executor の構造 (core=0 / max=1 / queue 256 / CallerRunsPolicy) は**一切変更
  していない**。CLAUDE.md の凍結制約も、オーナーが除外した repo 単位ワーカー
  分離・並列化 (第二段) も、そのまま。
- **仕事は失われない**。reconcile の re-drive が root から引き受ける。
  代償は「root からの再走査」であり、リクエストを人質に取るより明確に良い。
- **epoch 義務はここで settle しない**。settle するのは re-drive の終端のみ。
  (当初案が継続タスクに課していた「最終セグメントのみ settle」条件は、
  セグメントが存在しなくなったので自動的に満たされる。)
- reconcile service が未配線の構成では委譲せず inline 走査する。
  黙って落とすより遅いリクエストの方がまし、という判断を WARN で明示する。

*キュー書込みが失敗したら委譲しない*。`enqueueOrThrow` を使い、例外なら `false` を
返してその場で走査する。fail-soft な `enqueue` は CouchDB 障害をメトリクスに
飲み込むので、「委譲した」と偽って早期 return すると**遅いリクエストが失われた
リフレッシュに化ける**。

*観測*。`/v1/admin/search-index/metrics` に `deferredToReconciliation` を追加。
既存の `inlineRunsOnRequestThreads` と**並べて読む**のが正しい読み方で、
両方が揃って増えるのが健全 (溢れた分はすべて耐久キューへ移った)。caller-runs だけが
増えて deferrals が平坦なら、reconcile 未配線で実際にリクエストが走査している。

*効果の正確な言明*。基準 2 で問題になる「リクエストスレッドが他人のサブツリーを
走る」ことは、**reconcile が配線されており、かつキューへの書込みが成功する限り**
起きなくなる。CouchDB が落ちている等で `enqueueOrThrow` が失敗した場合は
意図的に inline 走査へ落ちる (捨てるよりまし)。つまり保証の前提は「配線」だけでなく
**キューが書ける**ことまで含む。一方、伝播そのものが
速くなるわけではなく、キュー満杯が続けば耐久キューのバックログが伸びる。
バックログは可視 (metrics / reconcile 状態) で、リクエスト遅延には変換されない。
これはオーナーの受入条件 (遅くてよい / アプリ全体を落とすのは不可) に一致する。

**A5 (剥奪系タスクの HOL): 実装済み — レーン分離。**
上の委譲で ACL_REINDEX のバックログが増えるため、**A5 は委譲の前提条件**だった。

最初はバッチの 1/4 を purge に予約するクォータで実装したが、**それでは効かない**ことが
レビューで判明した。理由は**ブロックの単位**にある。scheduler は claim したバッチを
**直列に**処理し、その 1 件が数分〜数時間かかるサブツリー走査でありうる。バッチを
claim した 1 秒後に届いた purge は、その走査が終わるまで **claim すらされない** —
バッチの何割を予約していようと関係ない。予約は claim を守るが、待たされている場所は
claim ではない。

そこで **専用ポーリングスレッド** (`SearchIndexReconcile-purge`) を追加した。
purge は有界かつ冪等な delete なので、このレーンが長時間ブロックすることはない。
- `claimDuePurges` は `operation=RAG_PURGE` で**クエリ側**を絞る (後段フィルタでは
  CouchDB が due 全域を走査してしまうため)。期限切れリースの purge も回収する。
- **共有レーンは operation で絞らない**。purge レーンが未配線・停止しても孤児に
  しないため。分離の目的は「purge を待たせない」ことであって、共有レーンが purge を
  実行できないからではない。
- ただし絞らない以上、共有レーンが `[長い ACL_REINDEX, RAG_PURGE]` という混在バッチを
  掴むことがある。claim した時点で両方 LEASED になるので purge レーンはもう手を出せず、
  直列ループが再駆動を先に回せば purge は結局数時間待つ — 分離した意味が消える。
  そこで **`processClaimed` はバッチ内で purge を先に回す**。混在バッチに入っても
  purge に対して最初に行うのはその処理、という状態を保つ。
- `claimDuePurges` は **期限切れリースを先に**引く。PENDING を先に満たすと、
  新規 purge が毎 poll バッチを埋める状況で、クラッシュしたワーカーが放棄した purge が
  永久に見られない (新しいものに押し出され続ける)。
- 両レーンは同じ `_rev` CAS で claim するので、同じ文書を掴んでも二重実行しない。
- **Mango index を追加** (`type/status/operation/nextAttemptAt` と同 `leaseExpiresAt`)。
  無いと CouchDB が status index で答えて operation を後段フィルタし、
  大きな再駆動バックログに紛れた稀な purge を探して due 全域を走査する —
  アプリのリクエストを捌いている同じ CouchDB に負荷をかけることになり、本末転倒。
  patch 名の suffix も `-20260810d` に上げたが、**この patch に関しては効果は無い** —
  `AbstractNemakiPatch.apply()` は `isApplied()` 判定より前に `applySystemPatch()` を
  呼び、`PatchService` 側も名前で門を作っていないので、system 側の index 登録は
  毎起動走る (`postIndex` は冪等)。suffix は per-repository 側の慣習に合わせただけ。

**レーン分離で顕在化した既存欠陥 (修正済み)**。2 レーンにしたことで purge と ACL
再構築が**同時に走り得る**ようになったため確認したところ、`purgeDocumentBlocks` が
per-ragId ストライプ (`ragBlockLocks`) を**取っていなかった**。`updateDocumentACL` は
Block Join の制約から read-rebuild-write (親と全チャンクを読み、readers を差し替えて
ブロックごと再 add) なので、その read と write の間に delete が入ると**再構築が
delete を打ち消す** — purge は「消えた」と検証済みで成功を報告しているのに、
剥奪されたリーダーのブロックが索引に戻る。purge が消したかったオラクルそのものが
黙って復活する。

**multi-replica も閉じた** (realtime GET による版フェンス)。
ストライプはプロセスローカルなので、それだけでは別レプリカの purge を止められない。
コード上のコメントが既に正解を指していた: 「`_version_` CAS は一度試して revert した。
親を **searcher クエリ**で読んでいるので soft commit 遅延で版が古く、偽の 409 が出た。
正しい CAS には **realtime GET** が要る」。そのとおりに実装した。

- ブロック再 add の直前に `getById` (realtime GET = update log を読むので soft commit
  遅延の影響を受けない) で親の権威ある `_version_` を取り、それを CAS トークンとして
  add に載せる。
- **realtime GET が「無い」と答えたら add しない**。再構築中に purge が勝った証拠で、
  ここで add することが復活そのものだから。
- 正の `_version_` は「この版でちょうど存在すること」を意味するので、
  別レプリカの同時ブロック書込み (版が上がる) でも purge (消える) でも add は棄却される。

*検証 (単体)*: `RagPurgeVsAclRebuildRaceTest` は 2 ケース。同一インスタンス
(ストライプが効く) と、**別インスタンス = ストライプを共有しない multi-replica 相当**。
後者はフェンスを外すと `[delete, add]` で落ちることを実測確認済み
(フェンス有効時は `[delete]`)。

*検証 (実機 Solr、2026-08-10)*。「Solr が Block Join の親に対して楽観ロックを
本当に効かせるのか」はモックでは確かめられないので、nb33 の Solr に直接当てた。

| 確認 | 結果 |
|---|---|
| 親 (子付き) の realtime GET で `_version_` が取れる | ✅ `1873119855048130560` |
| `_root_` 削除の**直後**に realtime GET | ✅ `{"doc":null}` (searcher の遅延を受けない) |
| 旧版を載せたブロック再 add | ✅ **409** `expected=1873119855048130560 actual=-1` |
| 正しい版での連続更新 3 回 | ✅ 3 回とも status 0 (**偽 409 なし**) |
| CAS 付き置換後もチャンクが残る | ✅ ブロック内 2 docs |

つまり復活は**二重に**塞がれている: realtime GET の null 判定と、Solr 側の版 CAS。

**P2 の兄弟欠陥も塞いだ** (レビュー指摘 A6-INT-2)。同じ soft-commit 遅延 (既定 10 秒) で
**searcher が「無い」と答える枝**は、これまで「未索引 — 次の索引で反映」として正常 return
していた。しかしブロックが update log には存在する (= 直前に書かれた) 場合、これは
**GRANT を無音で落とす**: 新規許可ユーザは次のコンテンツ再索引まで RAG 検索から欠落し、
reconcile タスクも積まれないので収束機構が無い (REVOKE 側は live-ACL ゲートが実害を
止めるため機密漏れは無い)。修正: 空 searcher でも realtime GET を照会し、update log に
在れば P2 と同じく throw して再駆動に委ねる。realtime も null なら従来どおり skip
(purge 勝ち / 本当に未索引)。

**さらに: CAS トークンと データ が同じ版であることを要求する** (レビュー指摘)。
realtime GET で取った「現在の版」を、**前に読んだ snapshot** に貼って書くと、
CAS は「直前の数マイクロ秒に変化が無かった」ことしか証明しない。読取り後・GET 前に
別レプリカが新しいブロックを書いていた場合、こちらが提示する版は本当に現在の版なので
**Solr は受理し、新しい readers とチャンクが古いもので置き換わる** — 剥奪したはずの
アクセスが戻る。そこで searcher から読んだ親の `_version_` を snapshot 版として保持し、
realtime 版と**一致しなければ書かずに例外**にする。呼び出し側がノード単位の失敗として
記録し、reconcile が競合相手の書込みが落ち着いた後に再駆動する。
静かに `return` すると「更新した」と報告してしまうので、ここは必ず throw。

**この欠陥はレーン分離以前から存在していた** (async applyAcl の refresh は
`ragAclExecutor` 上、`handlePwcPurge` はリクエストスレッド上で、既に別スレッド)。
分離は発生確率を上げるだけだが、修正は必須。`purgeDocumentBlocks` で同じストライプを
取るようにした。`RagPurgeVsAclRebuildRaceTest` が read/write 窓を実スレッドでこじ開けて
順序を固定する (**ロックを外すと `[delete, add]` で落ちることを実測確認済み**)。

**残る性質 (意図的)**: 共有レーンは古い順で公平なので、purge が大量に来続ければ
再駆動はその分後ろになる。purge レーンが並行して捌くため滞留は縮むが、
再駆動の下限保証は置いていない。剥奪の洪水が続く状況で再駆動を優先する理由が無い。

*検証*: `ReconcilePurgeLaneTest` (5) が「purge レーンは purge しか取らない」
「期限切れ purge も回収する」「共有レーンは絞らない」「期限切れ優先」
「重複してもバッチが埋まり切る」を固定。`InlineRefreshDeferralTest` (6) が
委譲時の enqueue・epoch 引継ぎ (null 含む)・未配線時に落とさないこと・
**キュー書込み失敗を成功と報告しないこと**・settle しないことを固定。

**P1-2 (A2/A3/A4): 構造を変えずスループットを上げる。見積りは約 2 倍 + α。**
1. **祖先チェーン再利用** (A3): §4.6 が許可するのは **snapshot 側のみ**。
   revalidation の祖先再読は fence の正しさの根拠なので**削減対象外**。
   削減効果は 2×(1+D) → (1+D)+1、つまり**約 2 倍が上限** (初版の 6 倍は誤り)。
   実装条件: step 4 不一致で restart する際は共有チェーンを破棄してフレッシュな
   walk からやり直す。
2. **principal lookup の短 TTL キャッシュ** (A4): **実装済み**。ただし当初案の
   「成功のみ・30 秒」から変更した。principal の by-id 参照がキャッシュを迂回していた
   理由は「served できなかった (UNAVAILABLE) を『不在』と取り違えると reader 集合が
   静かに縮む」ことなので、そこを壊さない形にした:
   - **UNAVAILABLE は絶対に保存しない**。FOUND / NOT_FOUND だけを記憶する。
     障害を答えとして再生しない。
   - **principal 世代をキーに含める** (P3-1-3 のカウンタ)。ユーザ・グループの
     create / update / **delete** が世代を上げるので、剥奪は TTL を待たずに
     全エントリが一斉に到達不能になる。
   - TTL 10 秒は、他レプリカでの principal 変更が世代ポーラ経由で届くまでの
     バックストップ。既存キャッシュの 1 時間より桁違いに短い。
   記憶するのは principal の**種別 (user か group か)** だけで、所属や権限は含まない。
3. **Solr バッチ** (A2): fenced write の 1 件ずつ `_version_` CAS が正しさの根拠
   なので、バッチ化は epoch 設計の精査が先。1+2 で足りるなら捨てる。
*検証*: 伝播スループット (docs/s、可視化ラグ控除) を before/after で。
正しさは epoch verdict + GRANT/REVOKE の陰性対照付き統合テスト。

**P1-3 (B1): 実施しない (§0 の決定)。**
応答前 BFS を「最大 M ノード」に制限する案は、M+1 件目以降の aclCache に
stale-permissive な実効 ACL が残る = **REVOKE 済みユーザが読める窓**を作る。
オーナー判断により、大規模フォルダの applyACL 応答が子孫数に比例して伸びること
(実測 +0.3ms/子孫、10 万件で約 +30 秒) を受け入れ、**認可の即時性と REVOKE の
即時性を一切緩めない**方針とした。B1 は「既知の特性」として文書化し、実装しない。
将来やるなら pending-aware キャッシュバイパス (設計 §7(a)) が有界化と両立する唯一の
形だが、伝播中の読みが全て cold になるコストを伴う。

**P1-4 (C7): pending gate を非カウントに — 可観測性要件とセットで。**
`retryLaterWithoutCountingAnAttempt` を AclEpochPendingException 由来にも広げる。
ただし非カウント化は「永遠に terminal FAILED に到達しない」を意味するので、
quarantine の前例 (§5.1: quarantineBlockedTasks メトリクス + blocker id) と同型の
**pendingBlockedTasks メトリクス + ブロック元 objectId** を必須とする。
実装注記: 現在 AclEpochPendingException は scheduler の汎用 catch(Exception) で
clean=false に潰されるため、例外型の伝播経路の整備が要る。pending の解消は
scanner (既定 300s) に依存する liveness であることを明記。
**配線 (ここが抜けると偽修正になる)**: 型を投げるだけでは scheduler が
`catch (Exception)` で拾って `retryLater` に落とすため attempts が増え続ける。
`SearchIndexRefreshPendingException` 専用の catch を **generic catch より前**に置き、
`retryLaterWithoutCountingAnAttempt` を呼ぶところまでが 1 セット。

*検証*: RefreshCountersTest — pending のみ / 本物の失敗が混在 / 失敗ゼロ の 3 分岐、
JVM 単位カウンタ、**scheduler が専用 catch を generic より前に持ち
`retryLaterWithoutCountingAnAttempt` を呼び `markFailed` を呼ばないこと**、
**re-drive から型のまま外へ出ること**を検査する。

### P3 — multi-replica の正しさ (§0 の決定により 3.3 のサポート対象。全項目を実装する)

**P3-1**: 実装済み。**値だけ共有し、機構は分ける**方針を採った (レビュー承認済み)。

1. **TTI 停止** (実装済み): ehcache の default から `timeToIdleSeconds` を除去。
   stale 上限が「無期限」→ 最大 3600 秒になった。
2. **P3-1-2 レプリカ間無効化** (実装済み): 各レプリカが自分の世代を CouchDB の
   `cache-generation` 文書に publish し、**他レプリカのエントリだけ**を読む。
   いずれかのノードの値が前回見た値と**変わっていたら**キャッシュを落とす。

   **初版は誤りだった (レビュー指摘で判明)**。当初は「全レプリカの最大値 vs 自分の
   カウンタ」で比較し、自分の書き込みに反応しないようにしていた。しかしこの 2 つの
   カウンタは**各プロセスのローカル書き込み回数**であって共有時計ではないので、
   値どうしの比較に意味がない。結果として**書き込みの多いレプリカは自分のカウンタが
   常に先行し、他レプリカの変更に恒久的に反応しなくなる** — 例外的な条件ではなく、
   忙しいレプリカほど確実に壊れる。しかも当時のテスト (`ownWritesDoNotTriggerAClear`)
   がその誤った同値関係を固定していた。

   直し方は「自分を除外する場所」を変えること。除外を**ストア側**で行い、
   invalidator は他ノードの値の変化だけを見る。これで「自分の書き込みでは落とさない」
   と「他レプリカは必ず見る」が同時に成立する。増加ではなく**変化**を見るのは、
   他レプリカ再起動でカウンタが 0 に戻っても取りこぼさないため (減少も変化として
   1 回だけ落とす)。初めて見るノードも変化として扱う — そのノードが自分の起動前に
   何をしたかは知りようがないので、「不明」は「変わった」に倒す。

   publish は CAS せず best-effort — 取りこぼしても次の周期で republish されるので、
   リトライ嵐のほうが高くつく。読み取り側は逆に厳格で、整数として読めない値は 0 に
   丸めず警告して無視する (丸めると「変化なし」に化けて静かな未無効化になる)。

   落とす対象は `aclCache` / `contentCache` に加えて **`objectDataCache`** も含む。
   ローカルの `removeCmisAndContentCache` がこの 3 つを消すので、2 つだけでは非対称に
   なり、compile 済み CMIS オブジェクト (ACL を含む) が残る。
3. **P3-1-3 principal 世代** (実装済み): ACL epoch は ACL 確定でしか進まない
   (allocate の呼び出し元は 1 箇所) ため、パスワード変更・admin フラグ・グループ
   除名は**一切カバーしない**。別カウンタを立て、DAO 層のユーザ/グループの
   create・update・**delete** で進める (削除は剥奪そのものなので落とせない)。
   落とす先も分ける: ACL 世代 → aclCache/contentCache、principal 世代 →
   userItem/groupItem/joinedGroup。

**Codex レビュー (2026-08-10) で追加修正した 7 点**:

- **acknowledge-before-clear の回帰 (自分で入れた)**: 変化を記録してから clear して
  いたため、clear が失敗すると次の poll で「変化なし」と判定され、退避が二度と
  再試行されない。収束機構が犯してはいけない唯一の誤り (やっていない仕事を
  完了扱いする) だった。clear 成功後にだけ記録するよう分離した。
- **importer の ACL 書き込みが世代を上げない**: `AclCacheGeneration.advance` は
  `clearCachesRecursively` にしか無く、applyAcl を迂回する 3 系統 (Zip /
  Filesystem / canonical ingest) の ACL 変更は他レプリカに一切届かなかった。
  DAO 層で一律に上げると通常の更新でも全レプリカが cold になるので、
  **ACL を書く 5 箇所に限って**上げる。
- **publish の永久喪失**: `update(Map)` は例外を握りつぶして null を返すため、
  失敗を検知できていなかった。加えて fixed-delay では同じレプリカが毎回 revision
  race に負け続けうるので「1 poll 分の遅れ」は成立しない。失敗を検知して
  fresh revision で 1 回再試行し、それでも駄目なら WARN を出す。
- **principal 変更で content/objectData が残る**: UserItem/GroupItem も Content
  なので、ローカル更新は contentCache を更新し objectDataCache を消す。
  レプリカ間でも同じ 3 つを落とす。principal 変更は稀なのでコストは無視できる。
- **ノードエントリの永久増加**: nodeId はプロセスごとの UUID なので再起動のたびに
  増え、poll のたびに読み書きする文書が膨らみ、いずれ書き込みがサイズ上限で
  失敗して無効化が止まる。heartbeat を持たせて 1 時間で刈る。
- **poller の静かな死**: `store.repositoryIds()` の例外は per-repository の try の
  外だったため、`scheduleWithFixedDelay` がタスクを永久に止める。全体を包み、
  連続失敗回数を公開する。
- **壊れた値の 0 丸め**: 「無視する」と書きながら 0 に丸めており、前回値が 0 なら
  無効化が起きなかった。ノードごと落として「離脱」扱いにし、次の正常な publish を
  新規ノードとして clear させる (余分な clear 側に倒す)。

自分の検証で見つけた追加 1 点: prune を publish の**後**に呼んでいたため、刈った
結果が書き込まれず永久に効いていなかった。publish の前に移した。

**有界性の言明**: 他レプリカの権限変更がこのレプリカに届く上限は
「ポーリング間隔 (既定 5 秒) + 書き手の publish が届くまで」。従来は「エントリが
期限切れになるまで」で、TTI のため実質無期限だった。

*検証*: CrossReplicaCacheInvalidatorTest — ACL/principal の独立性、自分の書き込みで
落とさない、**自分が 100 回書き込んで先行していても他レプリカの 1 回を検知する**
(旧ロジックを一時的に戻すとこのテストは実際に落ちることを確認済み)、他レプリカ
再起動によるカウンタ後退も変化として検知する、同一世代で二度落とさない、ストア障害
でポーラが死なない。実機では本レプリカで ACL 変更を 5 回行って世代を先行させた上で、
他レプリカが**より小さい**世代 1 を publish しても検知することを確認した。

**P3-2 (D5)**: `POST /api/v1/admin/cache/{repo}/clear` を配線 (実装は既存)。
multi-replica では各レプリカに直接叩く運用手順を docs に明記。

### ビルド由来の偽陽性に注意 (2026-08-10 に 1 日で 2 回踏んだ)

台帳の課題とは別に、**検証を誤らせる 2 つの罠**を記録しておく。どちらも
「コードは正しいのにテストが落ちる」形で現れるので、回帰と誤診しやすい。

1. **テスト実行中に再デプロイしない。** TCK はライブサーバを叩くので、実行中に
   `--build --force-recreate` すると全 TCK が `Connection reset` で落ちる。
   製品の回帰と区別がつかない。
2. **WAR は IDE が監視していない場所でビルドする。** (当初「clean すればよい」と
   書いたが不十分だった — 下記) Cursor の JDT LS が `core/target/classes` を
   Maven と共有しており、**javac は通るが JDT はエラーにする**コードを
   「`Unresolved compilation problem` を throw するクラス」として書き出す。
   `mvn package -DskipTests` は増分なのでそれを再コンパイルせず WAR に混入させる。
   実例: `DataUtil.clonePropertyDefinition` の
   `Cannot cast from List<Choice<capture#N>> to List<Choice<?>>`。
   症状は**空メッセージの CmisRuntimeException** で、アプリログには何も出ない
   (`docker logs <core> | grep -A 3 "Unresolved compilation problem"` で初めて見える)。
   個別の型定義 API は 200 なのに `typeDescendants` だけ 500、という出方をした。
   **前のコミットに戻しても直らない**ので、コード側を疑い続けると時間を溶かす。
   さらに **`clean` でも足りない**: JDT LS は maven の実行中にも書き戻す
   (実測: clean 後の `mvn test` で 17 クラスが汚染され、`DataUtil.class` の mtime が
   maven 実行中の時刻だった)。確実なのは IDE の監視外へ複製してビルド・検証すること。
   検出は `CompiledClassesAreUsableTest` が自動化した — target/classes を走査して
   Eclipse が埋めるマーカ文字列を探す。落ちたら「clean 忘れ」ではなく
   「IDE が書き戻している」と読む。

### レビューで判明した横断的な弱点 (2026-08-09)

**NUL バイト混入を検出する仕組みが自動で動いていなかった。** `scripts/validate-soc-templates.sh`
の Phase 1.4.1 が `.java/.ts/.tsx/.js/.jsx` を走査するが、**手動実行のスクリプト**であり
ビルドにも git hook にも繋がっていない。同スクリプトのコメント自身が「この RC サイクル
だけで NUL 混入が 2 件」と記録しており、本作業でさらに 2 件見つかった (新規 1・既存 1)。
NUL が 1 つ入ると git はそのファイルを binary と判定し、**以後 diff が消えてレビュー
不能になる**。Java も TypeScript もコンパイルは通るので他に気づく機会がない。

対策として `SourceTreeNulByteTest` を追加し、`mvn test` で毎回リポジトリ全体を走査する
ようにした (走査対象・除外ディレクトリはスクリプトと一致させ、両者が食い違わないように
してある)。この 1 件は本計画の ACL 課題とは無関係だが、**同じ検証プロセスの穴**なので
ここに記録する。

### Codex レビュー第 2 巡 (2026-08-10) — High 2 / Medium 5

P0-3・P1-2・P2-4・P3-2 を通した直後のレビューで、以下を追加修正した。

- **[High] staleness 判定が全リポジトリ横断だった**: reconcile キューを
  `list(1)` でグローバルに見ており、**他リポジトリの terminal FAILED タスク 1 件**で
  全リポジトリのクエリが恒久的に縮退しえた。リポジトリと status
  (PENDING / LEASED のみ) で絞る `hasOutstandingWork` を足し、2 秒キャッシュも
  リポジトリ単位にした。FAILED は人を待っている状態であって伝播中ではない。
- **[High] `NemakiCachePool.clear` が非安全**: 旧 CacheService を close してから
  差し替えており、同時実行中のリクエストが閉じたインスタンスを掴む。コンストラクタが
  投げれば閉じた service がプールに残る。`HashMap` も非同期化されていなかった。
  **作ってから publish し、最後に close** の順に変え、`ConcurrentHashMap` にした。
  この API を REST で公開したのは今回なので、既存の危険を外に出す前に直した。
- **[Medium] PrincipalLookupCache が無制限**: 論理的に失効しても削除されないため
  JVM 生存中は溜まり続ける。20,000 件の上限を入れ、超えたら全消し
  (失うコストは view クエリ 1 回ずつなので、遅くなるだけで誤らない)。
- **[Medium] レガシー principal 経路が世代を上げない**: `PrincipalDaoService` の
  `createUser` / `createGroup` / `updateUser` / `updateGroup` / `delete` は
  `UserItem`/`GroupItem` 経路と別で、世代を進めていなかった。5 箇所すべてで上げる。
- **[Medium] レプリカ間 poller が principal memo を落とさない**: 世代は JVM ローカル
  なので、他レプリカでの principal 変更に対して 10 秒 TTL が**バックストップではなく
  唯一の無効化**になっていた。poller から `PrincipalLookupCache.invalidateAll()` を
  呼ぶ。
- **[Medium] verdict が `fenced:false` のままだった**: 再起動後の完了済み移行を
  `STAMPED_BY_ANOTHER_RUN` と呼び分けても、派生する `fenced` は false のままで
  スクリプトは完了を確認できない。**完全に fence 済み (remaining == 0 かつ index 非空)
  なら誰が実施したかに関わらず `COMPLETE`** を返すよう改めた。部分的に fence された
  状態は `PARTIALLY_FENCED_NO_RUN_RECORD` とし、「移行が走った証拠」とは主張しない
  (通常の ACL 書き込みが 1 件ずつ bootstrap するため、その推論は成り立たない)。
- **[Low] RELEASE_NOTES の verdict 表**に新しい値と `COMPLETE` の意味変更を反映。
- **[Info→修正] キャッシュキーが区切り文字結合**だった。principal id は外部
  ディレクトリ由来でありうるので、長さ前置の曖昧さのない符号化に変えた。

## 6. 本計画で「やらない」と決めたこと

- **BCrypt cost の引き下げ** — 前計画で棄却済み。
- **CallerRunsPolicy の除去・キュー拡大** — 凍結制約。backpressure は正しい設計。
- **認可経路の非正規化 (子孫への ACL 焼き込み)** — 読み取り時継承が即時性の根拠。
- **ragAclExecutor の単純な maxPool=N 化** — 順序前提の証明なしには不可 (P1-1 第二段)。
- **B2 (epoch 4 putBack の圧縮)** — 正典 §11.4 に触れる。別途設計レビュー。
- **objectonly 要求の constraint 拒否** — 仕様上の疑義 + 自社 UI 破壊のため撤回 (P0-1)。
- **commitWithin=1000ms の短縮** — GRANT 可視化窓 (~1 秒) を仕様として受け入れるか、
  縮めるか (searcher 再オープン増とのトレードオフ) は**オーナー判断待ちの未決事項**
  として登録する。決まるまで現状維持。
