## 判定基準

3.3.1 と同じ **非破壊** を、トラック A に適用する。トラック B は **足すだけ** で、
3.4.0 の観測可能な入口（取込・DLQ・CMIS・既存の真正性 API の応答形）を変えない。

- 3.4.0 と同じ観測可能な挙動を保つ（不具合修正を除く）
- RELEASE_NOTES に「破壊的変更」節が**増えない**こと
- 各修正は判別するテストを伴う（負のコントロール: 修正を戻すと落ちること）
- **「電帳法対応」「JIIMA 認証済み」「管理者でも書き換えられない」は書かない**
  （ロードマップ §5）。言えるのは「**アンカー済みの履歴について、事後の書き換えを検出できる**」
  と「**この成果物は版を固定した検証器を通った**」まで
- RFC 3161 は **TSA プロトコル**であって、契約した業務が認定時刻認証業務であるときにだけ
  「認定タイムスタンプ」と言える。プロトコル実装だけでは名乗らない

トラック A と B は同じブランチでよい。コミットは分ける。B が膨らんだら
3.4.1 を A だけで切り、B を 3.4.2 に送る（その判断は A のあとでよい）。

## トラック B — 改ざん検出の証明 (JIIMA を踏まえた製品化)

3.4 は部品を持っている。足りないのは **第三者が WAR 無しで同じ検査を再実行できること**と、
**認定タイムスタンプを契約したときの見せ方**である。新規の暗号層は足さない。

以前の相談どおり、次は **3.4.1 に入れない**:

- custody の **HTTP 押し出し**（状態機械と都度 SIP/bag API は 3.4 にある。パイプラインは
  RODA ジョブ / Archivematica Automation Tools 側）
- 「防止」という語。与えるのは **検出**
- 文書 1 件ごとに TSA を買うこと（現状の段 3 は **台帳チェックポイント**。件単価と
  電帳法の経路別要件を混ぜない。経路調査は下記 P0）

### いまあるもの (3.4.0 出荷想定)

| 部品 | 場所 | 証明として足りない点 |
|---|---|---|
| SHA-256 (`nemaki:contentHash`) + fixity 4 値 | 取込 / P1-2 | プロパティなので管理者は書き換えられる。検出は再計算との突き合わせ |
| 真正性レポート | `GET /core/api/v1/admin/authenticity/report` (+ `.html`) | モックではなく実装済み。節ごとの `verdict` / `limits`。**このノードが出した自己申告** |
| 証拠台帳 + 連鎖検証 | P1-3 `EvidenceChainVerifier` | アンカー前の区間は管理者が作り直せる |
| RFC 3161 / OTS アンカー | P2-0〜2-2 | **認定 TSA の選定・契約は運用**。トークンの署名・証明書鎖・失効検証は未 (trust anchor を持たない) |
| ERS (RFC 4998) | P2-3 | data object は **checkpoint の正規化バイト列**であって文書ではない。SIP に同梱した実測は **スタブ DER** |
| E-ARK SIP + `SipVerifier` | P3-1 | 内部整合（bytes ↔ digest、audit path ↔ Merkle root）。**改竄されたリポジトリから作った SIP も通る。** `SipVerifier` は **core の中**にあり、第三者は WAR が要る |
| 都度 SIP / bag API | `POST /v1/admin/eark/export`、`.../objects/{id}/bag` | スケジュール生成はしない（以前の判断のまま） |

### 3.4.1 で足すもの (番号は A の続き)

| # | ロードマップ | 何を | 完了の定義 |
|---|---|---|---|
| 9 | P0（制度） | 電帳法の経路を **電子取引** と **スキャナ保存** に分けて、この製品がどちらに載るかを 1 頁に書く。JIIMA 認証の対象ソフト区分と、いまの部品が埋める／埋めない試験項目を表にする。**申請はしない** | 国税庁の現行一問一答を出典付きで引用。スキャナ保存の要件を電子取引に混ぜない。結論が「3.4.1 では電子取引側の検出まで」ならそう書く |
| 10 | P4-1 | **WAR の外で動く検証 CLI** (`SipVerifier` の規則を独立成果物にする)。入力は SIP zip（と、あれば `.tst` / `.ots`）。NemakiWare を起動しない | 本物の export → CLI のラウンドトリップ 1 本。digest を常に真 / audit path を無条件受理 / 何も調べなくても verified、の錠。メッセージは「NemakiWare を動かさずに検証できる」まで。「私たちを信用しなくてよい」とは書かない |
| 11 | P2-3 / P3-1 | SIP に載せる ERS を **スタブではなく、このノードが持つ RFC 3161 トークンから組んだもの**にする。無い構成では `NOT_PRESENT` であり、偽の DER を入れない | 本物のトークンで RODA の `metadata/other` 経路を 1 回測る。測れなければ「未測定」と残件に残し、スタブは出荷しない |
| 12 | P2-2 | 認定 TSA を配線したときの **運用手順**（policy OID・証明書鎖・CRL/OCSP の保存場所、失敗時はアンカーしない）。製品の既定は変えない | [`docs/operations/v3.4.1-timestamp-runbook.md`](../operations/v3.4.1-timestamp-runbook.md)（新設）。フリー TSA と認定 TSA を同じ言葉で書かない |

| 14 | （任意・UI） | 管理画面からレポート HTML を開ける。新規メニュー 1 つ。CMIS の答えは変えない | Playwright 1 本。無ければ 3.4.2 に送る |

### トラック B で名乗ってよいこと / いけないこと

**よい**:

- 取込時点のバイト列について SHA-256 を記録し、あとから読み直して突き合わせられる
- 台帳のアンカー済み区間について、事後の書き換え・削除・並べ替えを検出できる
- この SIP は、同梱した digest と audit path について内部整合している（CLI で再実行できる）
- 段 3 を **認定時刻認証業務**に向けた構成では、チェックポイントに RFC 3161 トークンが付く
  （その業務の認定範囲は TSA 側の約款）

**いけない**:

- 電帳法対応 / JIIMA 認証済み / InterPARES 準拠 / 改ざん防止 / 管理者でも書き換えられない
- 取込**前**の Slack 等の内容が真正であること（HMAC は通信相手の検証）
- アンカーしていない直近区間の検出
- ERS を「この PDF の長期署名」と呼ぶこと（対象は checkpoint）

1. A #3 (R52) — mapper 一本化。R51 の錠が複製経路でも動くことを先に測る
